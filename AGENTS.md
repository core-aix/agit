# aGiTrack Requirements

aGiTrack stands for agent + git tracking. It is a Python library and interactive CLI that combines coding-agent command line tools with automatic Git commits so agentic code changes are easier to trace.

## Goals

- Provide a common interactive interface for coding-agent backends and Git commit automation.
- Support Claude (Claude Code), Codex (the OpenAI Codex CLI) and OpenCode as interchangeable backends; every aGiTrack feature works the same regardless of the selected backend.
- Keep the user experience similar to the selected backend CLI, while adding aGiTrack commands for agent switching, user commits, staging, status, and configuration.
- Make agentic code changes traceable by automatically committing code changes made after agent prompts.
- Support running aGiTrack from any folder against a target working repository.

## Documentation

- `docs/user-flow.md` holds the complete, graph-rendered map of aGiTrack's interactive user flow (Mermaid flowcharts: startup gating, base↔worktree commit/stage/sync, the agent turn and integration, copy-back, the Ctrl-G menu, self-update, exit). It is linked prominently from the README. **It must be kept in sync with the actual flow:** whenever the user flow changes — a new or reworded prompt, a changed option label, a new decision based on file/commit/session status, a new Ctrl-G command, or a changed exit/update path — update the matching diagram in the same change.

## Writing Style

- **Do not use em-dashes** (Unicode U+2014, or the `&mdash;` / `&#8212;` HTML entities) in prose aGiTrack produces or ships: the website (`docs/index.html`, `docs/docs.html`), the README, docs, and other user-facing text. Use a colon, comma, parentheses, or a period instead.

## Commit Types

- Agent commits use the `<aGiTrack>` tag.
- User-triggered commits use the user-provided subject without an aGiTrack subject tag.
- Before an agent acts, if user changes already exist, aGiTrack creates a separate user commit first.
- A commit is created only when code has changed and staged changes exist.
- **A slash command that does real file work must be committed and merged like any other turn.** Some commands are pure directives (`/model`, `/clear`, `/compact`) and produce no changes, but others — most importantly `/init`, which writes `CLAUDE.md`/`AGENTS.md` — drive the agent to edit files. Those file changes must be auto-committed and merged into the base just like a typed prompt. The trap is backend-specific transcript shape: **Claude** records a `/init` as a `<command-name>` artifact row PLUS a separate `isMeta` user row holding the command's expanded instructions, and the transcript parser drops both as non-prompts — so without special handling NO turn opens and the file-creating assistant work is silently dropped (no commit, no merge). `transcripts/claude.py` therefore detects a `<command-name>` invocation (`_slash_command_name`) and lets the following expansion row (`_command_expansion_text`) open a turn labelled with the command (e.g. `/init`); commands with no expansion still open no turn. **OpenCode** already opens a turn for any `role == "user"` message, so a completed `/init` is captured natively — but a turn only commits when it has a `final_response`, which OpenCode fills only once the run reaches its `final_answer`/`finish == "stop"` message, so an interrupted command run legitimately has none. Verified on both backends by running a real `/init` end to end (Claude writes `CLAUDE.md`, OpenCode writes `AGENTS.md`) and confirming the parser yields a committable turn. Keep this distinct from the trace-exclusion rule below: pure directive commands stay out of the trace; work-doing commands become real, committed turns.

## Manual-Commit Mode (`--manual-commits` / `-m`, config `manual_commits`)

- An opt-in, strictly additive mode (default off). It **always runs without a worktree**: enabling it forces `use_worktrees=False` in `cli.py` (`--manual-commits`/`-m` implies `--no-worktree`), so it never runs in the worktree model. Everything below runs only when `ProxyRunner._manual_commits` is true; the default worktree and existing `--no-worktree` paths are untouched.
- **Goal:** natural, user-triggered commits. The agent edits the current branch directly, but aGiTrack does **not** commit each turn onto the branch. Each turn is recorded as a hidden **latent commit** on `refs/agitrack/manual/<session_id>` (chained, first-parent = the branch HEAD / previous latent tip) while **HEAD never moves**. The working tree already holds the agent's edits, so the latent commit is a durable *record* of the turn (its snapshot tree + the usual `<aGiTrack>` subject + `# Interaction Trace` + `# aGiTrack Metadata`), used for the dashboard's pending view and for folding at commit time.
- **Latent sink.** `CommitEngine.commit_turns` takes injected `manual_gate_fn` / `manual_record_fn` (from `ProxyRunner._manual_gate` / `_manual_record`). In manual mode it skips `_ensure_turn_branch`, the `add_tracked`/`stage_untracked` staging, and the `has_staged_changes` gate — it never touches the user's index or HEAD. The gate is "did the working tree change since the latent tip" (compare `snapshot_worktree_tree()` to the tip's tree); the record does `commit_tree(snapshot, parents=[tip or HEAD])` + `update_ref`. Snapshotting uses a throwaway `GIT_INDEX_FILE` (`GitRepo.snapshot_worktree_tree`), so the real index/staging is left pristine, and drops the scaffolding dirs (`.agitrack/`/`.claude/`/`.opencode/`).
- **One commit at commit time.** When the user commits — via `Ctrl-G → git-commit` (renamed from `git-user-commit`) or an external `git commit` — a managed **`prepare-commit-msg`** hook appends the pre-rendered trailer to the message, and a **`post-commit`** hook resets the latent ref to the new HEAD, clears the trailer, and touches a signal file. So the single commit carries the user's changes **and** every pending turn's trace/metadata, with no separate cover commit and no `<aGiTrack>` commits polluting the branch. Hooks live in `agitrack/git/hooks.py` (`install_manual_commit_hooks`, same marker/chain/skip-on-`core.hooksPath` pattern as the base-commit guard) and are installed/removed in `_setup_manual_commit_mode` / `_teardown_manual_commit_mode`.
- **The trailer** (`build_manual_squash_trailer`, `commits/message.py`) is a *squashed* message: a leading `commit_type: user` block (so even a commit with no pending turns is attributed to the session) followed by each pending latent commit's full body. Because that yields several `# aGiTrack Metadata` blocks, the dashboard's existing squash parser (`metrics/collect._parse_constituents`) reads one constituent per turn, sums the tokens, and classifies the commit as agent-tracked — **no new `commit_type` was needed**. The runner re-renders the trailer file (`.agitrack/manual-pending-trailer`) and the ref-name file (`.agitrack/manual-ref`) from the durable ref every turn (`_render_manual_trailer`), so it survives restarts; the `git-commit` menu handler also folds the trailer inline so it's tracked whether or not the hook is installed.
- **Fallback (no hook).** When `core.hooksPath` is set the hooks can't be installed; `_service_manual_commit_mode` then polls HEAD (`_reconcile_manual_external_commit`) and, on a detected external commit with pending turns, adds a `cover_commit(..., tree=<new HEAD tree>)` carrying the trailer (its tree equals HEAD's, so it introduces no diff) and resets the ref.
- **Dashboard.** `collect_manual_pending` enumerates `refs/agitrack/manual/*` for commits HEAD doesn't contain and marks them `pending`; `build_dashboard` appends them when showing HEAD, and `web.py` renders a dashed `pending` badge. After the user commits, the ref resets to HEAD so nothing is double-counted (and squash-constituent dedup covers any transient overlap).
- **Recovery.** `_setup_manual_commit_mode` resets a stale latent ref whose tip is already contained in HEAD (an interrupted commit), so previously-folded turns are never re-folded.
- **The fold spans EVERY session's latent ref, not just the current one.** A session's turns live on `refs/agitrack/manual/<agitrack_session_id>`, and that id changes when the user starts a new session (Ctrl-G → + New session) or when a backend switch opens one — so folding only `self.ref()` silently DROPPED every turn recorded before the switch and the trace between two commits had a hole in it. `ManualCommitTracker.pending_refs()` enumerates `refs/agitrack/manual/*` (the same view the dashboard's `collect_manual_pending` always had) and `_pending_shas()` merges them **ordered by commit time**, so two sessions' turns interleave as they happened. Manual mode is always no-worktree, so every one of those sessions edited the SAME tree and the user's commit captures all of their work — the trace must cover all of them. `.agitrack/manual-ref` therefore lists one ref per LINE (written with **LF on every platform** via `manual._write_lf`, and the hook strips a trailing CR anyway — `Path.write_text` uses `newline=None`, so on Windows it emits CRLF, `read -r` keeps the CR, `git update-ref` refuses the invalid ref name, and the refs are silently never advanced: Windows CI caught exactly this, as a re-fold and a wrong pending count. The same applies to `manual-pending-trailer`, which is `cat`-ed straight into the commit message, and to the hook SCRIPTS themselves — `_install_hook` writes LF so the shebang can never carry a CR) and the `post-commit` hook loops over them: advancing only the current ref left the older session's turns pending, and they folded a second time into the next commit.
- **Pending means "reachable from NO branch", not `HEAD..ref`.** After a fold the post-commit hook advances the latent ref to the new commit — a real branch commit. A plain `HEAD..<ref>` walk then reported that already-folded work as pending the moment HEAD moved to a branch that doesn't contain it, so committing on a second branch folded the first branch's turns AGAIN: trace duplicated, tokens double-counted (exactly the two-branches-then-merge case). `GitRepo.unlanded_commits(ref)` is `git rev-list <ref> --not --branches --tags --remotes` — a latent commit exists only on the agitrack ref, so "no branch contains it" is the exact test for "not yet folded anywhere", in one rev-list. Tests: `tests/test_manual_commits.py::test_a_session_switch_does_not_orphan_the_turns_recorded_before_it`, `::test_work_already_folded_on_another_branch_is_never_folded_again`, `::test_unlanded_commits_reports_only_what_no_branch_contains`.
- **NEVER compare a working-tree snapshot against a raw `^{tree}` — use `GitRepo.comparable_tree(rev)`.** Every "has the working tree changed?" question in manual / no-worktree / background mode is `snapshot_worktree_tree()` vs some commit's tree, and the snapshot deliberately STRIPS the agent scaffolding dirs (`.agitrack/`, `.claude/`, `.opencode/`) while a raw `^{tree}` keeps them. In a repo that TRACKS any of them — committing `.claude/settings.json` or a `.claude/commands/` dir is ordinary practice — the two can never be equal, so every one of those tests answers "dirty" forever and each mode breaks differently: `-b` covered NO agent self-commit (`_agent_committed_own_work` bails on a dirty tree, so the whole persistent-watermark mechanism was dead), `-m` never reset a stale chain and made `prune_abandoned_refs` a total no-op, `gate()` recorded a latent turn for a turn that changed nothing, and a purely human commit made during an agent turn was stamped as agent work. `comparable_tree` strips the same paths from the commit side and is idempotent, so it is also correct on the latent tips (already snapshots) it is compared against; it falls back to the raw tree via one `ls-tree` when nothing scaffolding-ish is tracked, which is almost always. The two raw `^{tree}` reads that must STAY raw are the cover commits' own trees (`manual.py` / `runner.py` `reconcile_external_commit`), which are real trees, not comparisons. Confirmed live in all three modes, not only in tests. Tests: `tests/test_manual_commits.py` §"a repo that TRACKS the agent scaffolding dirs", `tests/test_background.py::test_daemon_covers_an_agent_self_commit_in_a_repo_that_tracks_claude_config`; matrix §6c.
- **A "defensive" guard that exempts a case is not defensive.** `record()`'s "nothing new since the tip" guard was written `tip is not None and tree == tip^{tree}`, so the EMPTY chain — whose documented baseline is HEAD — skipped it entirely and an ungated `record()` wrote a phantom first turn against an untouched tree. It now compares against `tip or "HEAD"`, still skipped for `allow_unchanged` (the agent committed its own work) and after a re-anchor past a `gc --prune`d tip, where HEAD is a fallback parent rather than evidence nothing happened. Same shape as the `has_object_local`-instead-of-`is_ancestor` anchor bug and the tree-equality invariant before it: the fix was right and the verification was weaker than the property.
- Tests: `tests/test_manual_commits.py` (primitives, trailer/squash parsing, hooks fold/idempotency/chain, CommitEngine sink, pending collection, config toggle).
- **The proxy's own `_manual_*` copy must stay in lockstep with the tracker** — it had the same two defects (single-ref fold, `HEAD..ref` walk), plus the raw-`^{tree}` comparison above, plus a MISSING one: the `git gc --prune` re-anchor lived only in the tracker, so the headless daemon survived a pruned latent tip and interactive `-m` raised on every turn for the rest of the session (`test_the_proxys_own_manual_copy_also_survives_a_pruned_latent_object`). Interactive `-m` is the path users actually type in; `tests/test_mode_switching.py::test_proxy_latent_copy_matches_the_tracker_across_sessions_and_branches` pins the two against each other. The manual latent machinery is factored into `agitrack.commits.ManualCommitTracker` (`commits/manual.py`) — `ref/gate/record/render_trailer/reset_stale_ref/service/reconcile_external_commit/setup/teardown` over a `(repo, base_repo, state)` bundle — so the headless **background** runner reuses the exact same logic. (`ProxyRunner` still carries its own `_manual_*` copy for now; both call the same GitRepo primitives + `build_manual_squash_trailer`.)

## Latent tracking = ALL no-worktree modes (fold hook, cover as backup)

- **Every no-worktree session records turns as hidden latent commits and folds them via the `prepare-commit-msg` hook** — not just manual mode. `ProxyRunner._latent_tracking` (property) is `not self._use_worktrees`; `_noworktree_auto` is `not use_worktrees and not manual_commits`. All the latent machinery (`_setup/_teardown_manual_commit_mode`, `_manual_gate/_record`, `_render_manual_trailer`, `_service_manual_commit_mode`, `_reconcile_manual_external_commit`, the `commit_turns` `manual_gate_fn/record_fn` routing, `backend_commits=[]`) is gated on `_latent_tracking`, so it runs for no-worktree AUTO too. Worktree mode is untouched (turns commit per-branch + integrate). The manual-specific **UI** (menu `git-commit` behavior, exit "commit" reminders, the pre-agent no-check fast path, the "pending" dashboard) stays gated on `_manual_commits` only.
- **No-worktree AUTO fold.** `ProxyRunner._auto_fold_latent_pending` (called from `_service_manual_commit_mode`, throttled) folds the pending latent turns into a real commit **itself** once a turn is done and the tree still holds the agent's uncommitted work — the branch advances per turn like normal auto mode, but the trace/metadata ride the SAME commit as the code (no separate cover). **The message is a CLEAN agent commit** built by `commits.build_auto_fold_message` — one pending turn ⇒ its own single-agent-commit body verbatim (subject = the prompt, or the LLM summary once `pending_bodies` folds it in; one `commit_type: agent` block), several ⇒ a squash led by the newest turn's subject. It must NOT use `build_manual_squash_trailer` here (that "squash into a user commit" format leads with a generic `<aGiTrack> commit agent turns` subject and a spurious `commit_type: user` block — wrong for aGiTrack's own agent commit). The background daemon uses the SAME helper and additionally **waits (bounded by `summary_wait_seconds`) for the summary note before folding** (`BackgroundRunner._fold_summary_ready`), since the daemon never amends HEAD, so the summary must be in the message before the commit, not amended after. When the AGENT instead makes its **own** commit, the installed `prepare-commit-msg` hook folds the pending tracking straight into that commit; a clean tree then makes `_auto_fold_latent_pending` a no-op. The old no-worktree cover pass (`_integrate_agent_made_commits_if_idle`'s `not _use_worktrees` branch) is skipped under `_latent_tracking` — `_reconcile_manual_external_commit` is the cover BACKUP (only when the hook can't run, custom `core.hooksPath`). This realizes "auto mode uses the prepare-commit-msg hook for the agent's own commits, cover as backup."
- Tests: `tests/test_manual_commits.py::test_noworktree_auto_*` (latent→fold, agent-self-commit folds via hook with no cover, reconcile cover backup when hook unavailable).

## Background Mode (`--background` / `-b`, config `background`)

- An opt-in, strictly additive **headless** mode (default off). It **always runs without a worktree** (`cli.py` forces `use_worktrees=False`; `--background` implies `--no-worktree`) and uses **auto** commits by default (like the TUI) — `-m`/`--manual-commits` (or `manual_commits: true`) opts into manual; `--auto-commit` forces auto over a configured manual. Enabled by `-b`/`--background` (const `"run"`) or the `background` config key (settable in both global and per-repo config); resolved in `cli.py` and dispatched to `agitrack.proxy.background.BackgroundRunner` **before** the TUI/json branches.
- **Not a proxy.** Background mode does NOT spawn or drive the agent. The user runs the agent from any UI; the runner polls the newest backend session transcript in the repo dir (`backend.latest_session_id`, so it follows an in-backend session switch) and records completed turns. This is the interactive-UI-agnostic tracker of issue #143.
- **Reuses the proxy pipeline.** `BackgroundRunner._process_once` builds a bare `Session` (`worktree=None`) and calls `CommitEngine.start_parse` + `finish_parse_if_ready` exactly as the proxy does — so turn detection, the per-conversation watermark, and token accounting are **identical**. The commit sink records turns latently via `ManualCommitTracker` (both modes); auto mode's `_auto_fold_pending` mirrors the proxy's `_auto_fold_latent_pending`. Summaries are written as git notes (`agitrack/commit-summary`) so the fold picks them up (never amends HEAD — the user may be committing concurrently).
- **A commit made while the daemon runs folds a FRESH trailer (no poll lag).** The `prepare-commit-msg` fold hook appends the pre-rendered `.agitrack/manual-pending-trailer`, which the daemon only refreshes on its 3s poll — so a commit that races ahead of the poll used to fold a stale/empty trailer (the trace was silently dropped). The pre-commit hook now nudges the daemon to flush synchronously before the commit finalizes (see `precommit_sync` → `request_daemon_flush` below). Since the pre-commit hook runs while the working tree is still DIRTY (the changes aren't committed yet), a just-finished turn records cleanly and folds into THAT commit.
- **The agent committing its OWN work is tracked via ONE cover commit, driven by a PERSISTENT watermark.** When the agent (or user) runs `git commit` for a turn's work, there may be no completed turn to fold at commit time (the final message lands after the commit), and once the turn finishes the working tree is clean (its code is already committed), so the tree-delta latent gate would record nothing and the trace would be lost. The daemon keeps a **persistent coverage watermark** `_tracked_head` — the HEAD up to which it has accounted for AI work — stored in `<repo>/.agitrack/tracked-head` (`_load_tracked_head` initializes it to the current HEAD on a never-tracked repo, so pre-existing history is never retroactively attributed to AI; `_set_tracked_head` persists every advance). When a turn completes with a clean tree and HEAD has advanced past the watermark, `_agent_committed_own_work()` returns the **untracked** commits on `tracked_head..HEAD` (skipping any that already carry aGiTrack metadata, via `_is_agitrack_tracked`, so the daemon's own commits and hook-folded user commits are never re-covered), and `_record_turns` passes them as `backend_commits` to `CommitEngine.commit_turns` — the **exact same `cover_backend_head` path the proxy uses for backend-made commits**: ONE merge-shaped cover commit (first parent = watermark, second = the agent's commit, tree = HEAD's, no diff) carrying the turn's trace/metadata with `covered_commits` attributing the agent's lines to AI, metadata (and tokens) appearing **exactly once**. The watermark then advances to the cover. **Persisting the watermark is the whole point: it makes coverage survive a daemon restart AND the daemon being DOWN at commit time** — the previous per-turn in-flight HEAD snapshot was lost on every restart, so a commit made while the daemon wasn't watching went permanently untracked (the bug the user hit repeatedly). **A commit that PREDATES the turn's own prompt is never claimed** (`_since_turn_start`, gating BOTH `_agent_committed_own_work` and the latent path's `_uncovered_agent_commits`): because the watermark is persistent, a purely human commit made while the daemon was down — after a crash, or while the user worked in interactive mode, or with no aGiTrack running at all — can sit between the stale watermark and HEAD, and it used to be attributed to the NEXT AI turn (a human "document the project" commit landing in a turn's `covered_commits` while that turn's own code was still uncommitted). The gate compares each candidate's committer date (`GitRepo.commit_timestamp`) against the earliest `SessionTurn.started_at` among the turns being recorded, minus a tight `_WINDOW_SLACK_SECONDS` (5s, only for clock rounding — both clocks are local, and slack only ever WIDENS what may be claimed). Only a LEADING prefix is dropped so what remains is still a contiguous range ending at HEAD (what a cover commit's parents describe). Commits made AFTER the prompt are still claimed even if the daemon was down when they landed — that is the coverage the persistent watermark exists to provide. Turns with no timestamps (a backend that records none) skip the gate entirely, keeping the old behavior rather than losing coverage. The remaining deliberate trade-off, chosen for reliable coverage over "miss it entirely": a purely human commit made DURING an AI turn is attributed to that turn — acceptable in background mode, where the user is actively driving the agent. **Must NOT reintroduce the old two-step "latent metadata commit + merge that embeds the same body" cover — that made the metadata reachable TWICE and risked double-counting tokens.** The cover commit is **summarized like every other aGiTrack commit**: because the daemon never amends HEAD (so it can't attach the summary after committing, the way the proxy does), `_record_turns` passes `summarize_fn=self._summarize_for_message` to `commit_turns`, which summarizes the trace SYNCHRONOUSLY and builds the message so it LEADS with the summary (and records the summary cost + writes the commit-summary git note). This mirrors the auto-fold path, which waits for the summary before committing. `commit_turns`'s `summarize_fn` is opt-in — the proxy/shell pass None and keep their async amend flow. Tests: `tests/test_background.py::test_daemon_covers_agent_commit_made_during_an_unfinished_turn`, `::test_cover_commit_message_leads_with_the_summary`, `::test_watermark_persists_and_covers_a_commit_made_while_the_daemon_was_down`, `::test_daemon_does_not_cover_a_pure_qa_turn`, `::test_daemon_never_retroactively_covers_preexisting_history`, `::test_stale_watermark_never_claims_a_human_commit_from_another_mode`, `::test_a_commit_made_after_the_prompt_is_still_covered_when_the_daemon_was_down`, `::test_turn_window_gate_is_skipped_when_the_transcript_has_no_timestamps`.
- **Runs as a DETACHED daemon (like `agitrack -d`), not foreground.** `agitrack -b` is a *launcher*: `cli.py` splits on the internal `--background-serve` flag — without it (the launcher) it does the interactive privacy ack, then `background.start_background_daemon` re-execs `agitrack --background --background-serve --skip-privacy-ack …` detached via `proc.detach_kwargs()` (stdout/stderr → `<repo>/.agitrack/background.log`) and returns to the shell; the detached child (with `--background-serve`) runs `BackgroundRunner(...).run()` holding the lock. The launcher releases the lock before spawning so the child can take it. Commit mode is forwarded explicitly (`--manual-commits`/`--auto-commit`) so the child's own config can't flip it. **No owner-pid watchdog** (like every aGiTrack daemon since the dashboard/backtrace unbinding): a tracker must outlive the launching terminal — stop it with `agitrack -b stop`. **Re-running `agitrack -b` RESTARTS a running tracker** (like `-d`/`--backtrace`) so a rerun after an aGiTrack update always executes the new code: the CLI's repo-lock refusal makes an exception when the lock holder is a live background tracker (`replace_running_tracker` — SIGTERM + bounded wait for its clean shutdown, then re-acquire; any other holder, i.e. an interactive session, still refuses), and `start_background_daemon` likewise replaces instead of reusing. It waits on the handshake (`wait_for_handshake`, correlated on the child pid). **A rerun asking for the OTHER commit mode is a MODE SWITCH and must replace the daemon**: `_running_tracker_is_current(..., manual=…)` compares the handshake's `mode` (via `handshake_is_manual`) as well as the version, so `agitrack -b -m` over an auto-commit daemon (or `-b --auto-commit` over a manual one) restarts it instead of printing "already running … left in place" and silently ignoring the requested mode. `start_background_daemon` derives the same answer from the `--manual-commits`/`--auto-commit` flag it forwards. Same-mode reruns still short-circuit (no churn).
- **Single instance + stop/status.** Background holds the shared repo lock (`RepoLock` at `<repo>/.agitrack/lock`) for its whole run, so only one aGiTrack (TUI *or* background) runs per repo, **in any mode** — a second start is refused (`already_running_message`). Because the lock spans modes, the refusal is often about a process the user started in a DIFFERENT mode and may have forgotten, so `already_running_message(pid, repo_root=…)` reads the mode-specific records sitting next to the lock (`background.json` / `session.json`, matched on pid) and names the holder AND the command that ends it — "aGiTrack background tracker (manual commits) … Stop it with `agitrack -b stop`" vs "An interactive aGiTrack session (auto commits) … Ctrl-G → quit". Kept dependency-free (plain JSON reads in `git/lock.py`, no import back into the proxy layer); falls back to the generic wording when no record matches (e.g. a session still in cooked-mode startup). It also writes `<repo>/.agitrack/background.json` (its pid) so `agitrack -b stop` / `-b status` (handled early in `cli.py`, `stop_background`/`background_status`) target ONLY a background tracker (never a foreground TUI). Stop sends SIGTERM; teardown records any final turn (folding it in auto mode), removes the manual fold hooks (but NOT the persistent auto-track hook — see below), and deletes the handshake.
- **Repo scoping is mandatory.** A background daemon must track ONLY this repository's backend session, never one driven in another repo. This is inherent in `latest_session_id(self.repo.repo)`: Claude reads only `~/.claude/projects/<cwd-encoded>/` (the exact repo dir), OpenCode filters `session.directory == repo`. Keep that scoping — never widen discovery to "globally newest".
- **Event log (`--log-file` / config `log_file`).** Both the daemon and the proxy append notable events (`daemon-start`, `ai-change-detected`, `commit`, `update-available`) to a user-chosen file via `agitrack.events.EventLog` (best-effort, open+append+close per line, never raises). `resolve_log_path` resolves a relative path against the repo root. `EventLog(None)` is a no-op (used as the test default so `for_testing` runners have `.events`). Must work in every mode.
- Tests: `tests/test_background.py` (latent record + frozen HEAD, fold-on-user-commit, auto self-fold, skip-when-agent-committed, follows latest session and counts once, stop/status handshake, run() writes+removes handshake, detached-daemon launcher spawn/reuse/failure, event-log emission, update-marker write/clear, precommit-sync fold/no-op/defer/autostart, precommit-sync nudges a running daemon to flush, daemon flush records+acks, commit folds a fresh turn via flush, daemon covers an agent commit made during an unfinished turn + no spurious cover for a turn never seen in flight, auto-pipeline end-to-end **regression guard**, direct `ManualCommitTracker`); `tests/test_events.py`, `tests/test_update_marker.py`; gating in `tests/test_cli.py`.

- **A turn is billed ONCE however many times its commit reaches the branch (merges, cherry-picks, rebases).** Measured, not assumed: a plain merge of two branches is already correct (git lists each commit once), a squash-merge is correct, and a GitHub PR merge that copies its PR body — and so the whole metadata block — is handled by `_neutralize_inherited_metadata` (restricted to MERGES, where an identical block on a parent means a copy; on linear history an identical neighbouring block would be a real repeated turn). The gap was the LINEAR case: `git cherry-pick` copies a commit message byte for byte, so when the source branch is also merged the same turn's metadata sits on the ref twice and its tokens counted twice. `_suppress_copied_turns` keeps the FIRST occurrence in history order and clears the copy's tokens (the commit stays in the log, so the count still matches git). Identity is the metadata block reduced to its `key: value` lines (`_metadata_identity` — `cherry-pick -x` appends a "(cherry picked from …)" line, and rebases add trailers, so raw text would not match), and ONLY for blocks carrying a `conversation_anchor`: that is a real per-turn identity which two distinct turns can never share. Without an anchor nothing is suppressed — no identity to match on means the old behaviour stands rather than risk erasing an honest turn. **No pre-merge hook is needed** (the first instinct): the duplication is a read-time question about one ref's history, so it is answered where the numbers are computed, and it works for history that already exists. Tests: `tests/test_dashboard.py::test_a_cherry_picked_turn_is_not_billed_twice_when_its_branch_is_also_merged`, `::test_two_distinct_turns_on_merged_branches_are_both_counted`, `::test_a_block_without_a_conversation_anchor_is_never_suppressed`.

## Persistent auto-track hooks + auto-start (on a commit, and on new code)

- **Problem:** a background tracker is easy to forget (e.g. after a reboot), so AI work committed while it isn't running would go untracked. **Solution:** a PERSISTENT `pre-commit` hook (`git/hooks.py`, `install_autotrack_precommit_hook`, marker `# AGITRACK-AUTOTRACK-PRECOMMIT`) that outlives aGiTrack. Installed in every no-worktree/background run (`ProxyRunner._setup_manual_commit_mode` and `BackgroundRunner._install_autotrack_hook`) and — unlike the manual fold hooks — **NOT removed on teardown**. It bakes in `sys.executable` + the repo root so it needs nothing on PATH, is a no-op inside a linked worktree, chains a pre-existing hook, and always `exit 0` (never fails a commit).
- **The worktree base-commit guard and this hook share ONE slot pair (`pre-commit` + `pre-commit.agitrack-orig`), so a mode switch must hand it over, not clobber it.** With a project `pre-commit` hook present, a no-worktree/background run leaves auto-track at `pre-commit` and the project hook at `pre-commit.agitrack-orig` — both slots taken. Installing the guard on top then found the backup slot occupied and OVERWROTE the auto-track hook, so a single interactive worktree session permanently uninstalled tracking-on-commit. `ProxyRunner._install_base_commit_guard` now detects the auto-track hook, removes it first (restoring the project hook), installs the guard over that, and records `_displaced_autotrack_hook`; `_remove_base_commit_guard` re-installs it on teardown via the shared `_install_autotrack_precommit_hook` (which also honors `autotrack_hook == "off"`). Nothing is lost meanwhile — the auto-track hook defers to a live tracker, and the session IS one. The restore is conditional, so a pure-worktree user who never had the hook does not acquire one. Symmetrically, `BackgroundRunner._clear_stale_worktree_guard` (run at daemon start and after an update restart) drops a guard left by a crashed WORKTREE run before installing auto-track, mirroring the proxy's "start from a clean hook slate" — otherwise auto-track would chain a dead guard that `--remove-hooks` would later "restore" as if it were the project's hook. Tests: `tests/test_mode_switching.py::test_worktree_guard_never_uninstalls_the_persistent_autotrack_hook`, `::test_worktree_run_does_not_hand_out_an_autotrack_hook_that_was_never_there`, `::test_background_start_clears_a_stale_worktree_guard_before_installing_autotrack`.
- **`agitrack --precommit-sync`** (internal, `background.precommit_sync`): best-effort, always returns 0. If the repo lock is held by a **live background daemon**, it does NOT record turns itself (the daemon is the single writer — recording here would race its state/refs and risk double-counting) but **nudges the daemon to flush**: `request_daemon_flush` writes a nonce to `.agitrack/flush-request` and waits (bounded) for the daemon to record any pending completed turns + re-render the trailer and echo the nonce to `.agitrack/flush-done`. This closes the poll-lag gap where a commit racing ahead of the daemon's 3s poll folded a stale/empty trailer (the daemon's `_service_flush_requests`, driven by a responsive `_wait_with_flush`, services it within ~0.1s). If the lock is held by an interactive TUI (which renders its own trailer synchronously), it just returns. Else (no tracker), when the AI made changes since the last commit (non-zero pending turns), it records the pending turns latently and renders the fold trailer + installs the manual fold hooks, **so the triggering commit itself folds in the trace/metadata** (`prepare-commit-msg` runs after `pre-commit`, so installing it during `pre-commit` still folds THIS commit). The triggering commit stays the author's own **manual** commit (they already wrote a message). A purely human commit (no pending turns) is left untouched (no footprint). Then, unless `autotrack_hook == "off"`, it **auto-starts** the detached daemon for the turns that follow (fire-and-forget, after releasing the lock) in the **same commit mode as the last run** (`read_background_mode`, persisted by `write_background_mode` — written by the background daemon at start AND by the interactive proxy at `run()`, so auto-start resumes the mode the USER last chose; without the proxy's write, switching to interactive auto-commit and then committing silently auto-started a manual-commit daemon), and prints an explicit "started automatically in {auto/manual}-commit mode … stop with `agitrack -b stop`; disable with `agitrack --remove-hooks`" message. It also prints any available-update reminder on every commit.
- **No confusing "reminder-only" middle state.** The hook == auto-start: `autotrack_hook` (`"auto"` default / `"off"`) is the single repo-scoped control (the old `background_autostart` bool was removed/consolidated). `--remove-hooks` sets it to `"off"` so a later run won't reinstall.
- **Opt out from the CLI: `agitrack --remove-hooks`** (`git/hooks.remove_all_installed_hooks`) removes EVERY aGiTrack-installed hook — the persistent auto-track `pre-commit`, the worktree base-commit guard, and the manual-commit `prepare-commit-msg`/`post-commit` fold hooks — restoring any chained project hooks. `pre-commit` is checked twice (auto-track then guard) so a guard restored by the first removal is itself removed by the second.
- **`agitrack -b` asks about the persistent hook whenever auto-start is OFF.** Because the hook OUTLIVES the tracker, the `-b` launcher (interactive TTY only) explains it and asks a **binary** enable/off (`cli._maybe_prompt_background_hook`; default = enable). It skips ONLY when auto-start is already enabled for the repo (`autotrack_hook == "auto"` AND `config.source(...) == "repo"`), so it asks on the first run (default is a global-seeded "auto", not repo-scoped) and RE-ASKS after `--remove-hooks` sets it off — the user must be able to turn it back on. Once enabled it stops nagging. The choice is the repo-scoped `autotrack_hook` (`"auto"`/`"off"`, config + settings menu). Both installers (`BackgroundRunner._install_autotrack_hook`, `ProxyRunner._setup_manual_commit_mode`) honor it: `off` REMOVES any existing auto-track hook instead of installing. Never blocks automation (no-TTY/scripted ⇒ default enable, silently). The message tells the user how to cancel it (`agitrack --remove-hooks`).
- **`agitrack status` / `--status` / `-s`** (`background.repo_status`) reports whether aGiTrack runs for the repo and the mode: background (from `background.json`, always no-worktree) vs interactive (from a `session.json` handshake the proxy writes at `run()` and clears on teardown, since the shared repo lock carries only a pid), auto vs manual commit, worktree vs no-worktree — or not running. It also reports whether **auto-start** is on/off (`autotrack_hook`) and the last-run mode — phrased without "on commit", because auto-start also fires when an agent turn leaves changes behind. Read-only; dispatched early in `cli.py`.
- **The persistent hook must call the CURRENT aGiTrack after a self-update.** `install_autotrack_precommit_hook` bakes `proc.agitrack_invocation()` — a **frozen-aware** argv prefix (`<python> -m agitrack` for pip/source, the `agitrack.exe` directly for a frozen/MSI build, since `-m agitrack` is invalid there) — plus a **PATH fallback** (`|| agitrack --precommit-sync …`). The interpreter/exe path is stable across updates (pip rewrites the package in place; the MSI reinstalls the exe at the same path), so the baked command auto-resolves the new code; the fallback covers a rare relocation. The hook is also re-installed on every aGiTrack launch, refreshing the baked path. (Same reason `updater._restart_command` branches on `sys.frozen`.)
- **Global `summarization_enabled: false` must not be shadowed.** `BackgroundRunner._summarization_enabled` reads the GLOBAL config (with repo overlay) FIRST — matching `ProxyRunner._summarization_enabled` — because `AgitrackState` defaults `summarization_enabled: True`, and that per-repo default would otherwise override a global/repo `false` (so the toggle never took effect in background mode). Fall back to state only with no global config (tests).
- **Auto-fold doesn't hang when the summarizer fails.** `BackgroundRunner._fold_summary_ready` waits for the summary note, but bails early (folds now, raw-prompt subject) once the tip's summary worker thread has FINISHED without producing a note (`_summary_threads` keyed by latent sha) — otherwise a failing summarizer would make every fold wait out the full `summary_wait_seconds`.
- **Never leak internal state into a commit.** The daemon and `precommit_sync` write `.agitrack/` files (trailer, ref) even in an otherwise-idle repo, BEFORE any `AgitrackState.save()` — so they call `state.ensure_local_ignore()` first (idempotent info/exclude setup), or a `git add -A` would stage aGiTrack's own state. Keep that call before writing any `.agitrack/` file.
- Tests: `tests/test_manual_commits.py` (autotrack hook install/chain/remove, worktree no-op), `tests/test_background.py::test_precommit_sync_*`, `tests/test_cli.py::test_autostart_optin_*`.

## Background task notifications (monitor ticks vs completions)

- The Claude harness wakes the agent with `<task-notification>` user rows when a backgrounded task reports back. Two shapes: an INTERMEDIATE monitor tick (a Monitor streaming an `<event>` payload from a still-running job) and a TERMINAL notification (`<status>completed|failed`). The transcript parser labels the turns they open `(background monitor update)` vs `(background task completed)` (`_task_notification_kind` in `transcripts/claude.py`; unknown shapes default to completed, the commit-worthy side, since deferring is the riskier misclassification).
- **Trivial monitor-tick turns are not committed one by one.** While the live loop runs, `finish_parse_if_ready` DEFERS a batch of completed turns that are all TRIVIAL `(background monitor update)` acknowledgments: update-labelled prompt AND a barely-there answer (<=100 output tokens and <=240 response chars; the real flood was ~14-token "Noted. Waiting for finals." acks with a 2-line state.json tick each, 100+ commits overnight). Deferred turns fold into the next commit-worthy batch: a real prompt (typed or queued), a terminal notification turn, a monitor turn with a SUBSTANTIVE response (a normal final message or real work commits immediately, no waiting on notifications or the liveness horizon), or the exit finalize (`require_complete=False` always commits).
- The synthetic labels are never read as user prompts downstream: efficiency insights (`_SYNTHETIC_PROMPT_MARKERS`) and the learn digest strip both.
- **A background wake-up is an EVENT in the trace, never a `## User` block.** The label is not something the user typed, and recording it under the `user` role put words in their mouth: every such commit carried a `## User` / `(background task completed)` block indistinguishable from a real message, and — because the trace is the summarizer's SOLE input — the summary read the wake-up as a request. `_is_background_event` (commit_engine) routes it to `TRACE_EVENT_ROLE` instead, and `_trace_role_lines` renders it as a blockquote note ("The agent was woken here by a background event …, not by a user message") phrased generically over the label, so a NEW harness event kind renders correctly the day it appears rather than silently reverting to user attribution. It is kept, not dropped: it is the only thing explaining a turn nobody asked for. Two knock-ons: it is excluded from `subject_prompts`, so an all-background commit falls back to `<backend> changes` instead of a subject claiming the user asked for "(background task completed)" (and `metrics/collect._extract_user_prompts` now finds no prompt, so the dashboard shows the subject too); and `_limit_trace_turns` counts an event as a turn START alongside `user`, since an event-driven turn IS a turn — counting only `user` let a long run of wake-ups read as ONE turn and keep the whole run past the limit. Historical commits keep the old rendering. Tests: `tests/test_commit_message.py::test_a_background_event_is_never_rendered_as_a_user_message`, `::test_a_background_event_starts_a_turn_for_the_trace_limit`, `tests/test_commit_engine.py::test_a_background_wake_up_is_not_attributed_to_the_user`, `::test_a_real_prompt_alongside_a_background_wake_up_still_owns_the_subject`.
- **Summarizer refusals are unusable summaries.** A model handed a trace with nothing substantive may reply "I don't have any coding session turns to analyze..." instead of summarizing; `_UNUSABLE_SUMMARY_RE` treats first-person inability openings ("I cannot/can't/am unable to/don't have...") on the FIRST LINE as unusable, so the fallback prompt-led subject is used rather than the refusal becoming the commit subject (observed verbatim in a real repo).

## Async sub-agents: the turn is not over when the reply lands

- **The reported failure mode.** The main agent spawns sub-agents, immediately posts a message that READS as final ("kicked it off", "here's the plan"), and the sub-agents keep doing the actual job — editing the tree — for minutes afterwards. The turn is complete by every other measure, so aGiTrack committed right there: a finished-sounding trace (and a summary built from it, since the trace is the summarizer's only input) over a half-done tree. Verified on a real Claude transcript: 59 consecutive poll points where the last turn was complete, had a final response, and a sub-agent was still running.
- **The gate.** `ExportedSession.live_subagent_ids` lists sub-agents that have not reported back; while it is non-empty and `require_complete` is set, `CommitEngine.finish_parse_if_ready` DEFERS — the watermark stays put, so the launch turn and the follow-up work land in ONE commit once the sub-agents report. The exit/stop finalize (`require_complete=False`) still commits everything, and `_maybe_agent_commit` only ever reaches the gate on a dirty tree, so a deferral cannot wedge the loop. Live sub-agents also join `session.live_background_task_ids`, which stands the pre-agent user-commit dialog down and keeps the auto-fold waiting for the tree to settle — a running sub-agent makes ownership of an uncommitted change just as unknowable as a background task does.
- **Only async sub-agents count.** A SYNCHRONOUS call returns the child's finished report to the launching turn, so the work is over when the turn ends and there is nothing to defer. This is why OpenCode needs no support at all: its `task` tool blocks (verified live — `• Write git poem` → `✓ Write git poem` → reply, with the file already on disk at turn end).
- **Claude.** An async `Agent`/`Task` call returns a tool result reading `Async agent launched successfully … agentId: <id>`; the sub-agent's own transcript is `<session>/subagents/agent-<id>.jsonl` (named after that same id), and its terminal `<task-notification>` carries the same id in `<task-id>`. So launch, liveness and report-back all key on one string. A synchronous call returns the report text instead and matches nothing.
- **Claude notifications arrive in TWO row shapes and both must be read.** A notification delivered while the agent is BUSY is queued, and Claude Code records a queued notification as a `type:"attachment"` row with `attachment.commandMode == "task-notification"` — not a `user` row. Both shapes occur in the same transcript across every version checked (2.1.201–2.1.233). Reading only the user shape missed most terminal notifications, which also meant the post-notification work was folded into the prior, already-committed turn instead of opening its own `(background task completed)` turn. `_notification_row_text` normalizes both.
- **Codex.** `spawn_agent` is asynchronous and `wait_agent` is OPTIONAL, so the same failure mode exists (reproduced live on codex-cli 0.147.0: spawn, reply "I kicked it off", sub-agent writes the file afterwards). The spawn's return value `{"agent_id":"<thread id>","nickname":…}` lands in the parent's own rollout — as a `function_call_output` for a direct call, or a `custom_tool_call_output` when the model drives the tool from the `exec` JS sandbox (`tools.multi_agent_v1__spawn_agent(...)`), which is also why matching on the tool NAME `spawn_agent` misses those turns entirely. The report-back is a `<subagent_notification>` user message carrying `{"agent_path":"<thread id>"}`.
- **Do NOT use Codex's `thread_spawn_edges` for liveness.** Its `status` column read `open` for a sub-agent that had already completed AND for one that had been aborted — it records only that the spawn happened. Worse, aGiTrack opens the state db `immutable=1`, so rows still in the un-checkpointed WAL are invisible: verified live, a RUNNING sub-agent's edge read back as no rows at all, and mid-session is the only time the answer matters. Liveness comes from the child's own rollout instead (a `task_started` with no `task_complete`/`turn_aborted` after it).
- **The horizon is a safety valve, not the mechanism.** `SUBAGENT_LIVE_HORIZON_SECONDS` (30 min, shared by both backends) only exists so a sub-agent killed so hard it never recorded its own end cannot defer a repo's commits forever. A working sub-agent refreshes its transcript's mtime constantly, so a long-running one keeps deferring for as long as it actually runs.
- Tests: `tests/test_claude_session.py::test_parse_rows_tracks_async_subagents_*` / `test_parse_rows_reads_a_task_notification_delivered_as_an_attachment`, `tests/test_codex_session.py::test_an_unfinished_spawned_subagent_is_reported_as_live` (+ the finish/stale cases), `tests/test_commit_engine.py::test_finish_parse_defers_while_async_subagents_are_still_running` (+ the report-back and exit-finalize cases).

## Live background tasks and the user-commit dialog

- There is no reliable per-file attribution between the user and a running background task: no OS-level "which process changed this file", and the same file can legitimately be edited by both, so path/history heuristics misattribute someone's work. aGiTrack therefore keys on SESSION STATE: the transcript's notification stream shows which background tasks are demonstrably still running (`ExportedSession.live_background_task_ids`: a task whose intermediate monitor `<task-notification>` (an `<event>` payload) arrived within the last hour with no terminal notification after it). Launch-based counting is deliberately not used: a task that finishes while the agent is mid-turn never emits a terminal notification, so launches-minus-terminals overcounts badly (81 phantom "live" tasks in a real session); the recency horizon likewise stops a notification-less death from suppressing the dialog forever.
- While any task is live, the automatic pre-agent user-commit DIALOG is replaced by a warning (`_offer_pre_agent_user_commit`): the uncommitted files could be the user's changes or the task's edits, and they will be committed after the next agent turn. The explicit Ctrl-G `git-commit` remains available to commit one's own edits separately. When no task is live, the dialog behaves exactly as before.

## Crash recovery: continued turns and the commit watermark

- Commits (and summaries) are triggered by the AGENT'S FINAL MESSAGE: the background tracker polls the transcript every ~3s, records a turn latently the cycle its final lands, and folds the real commit after the LLM summary (bounded at ``summary_wait_seconds``). Nothing waits for the user's next message; when commits appear to lag until the next prompt, suspect the watermark pathology below.
- A turn force-committed BEFORE the agent replied (backend crash, exit finalize, tracker restart) stores its USER id as the watermark. If the restarted backend then continues that very turn, its real final message and edits arrive after the commit; ``turns_after`` therefore RE-EXPORTS a user-id-watermarked turn that now carries an assistant response, so the completed form is committed (tokens re-count for that turn; never losing work outweighs the inflation in this corner). Observed live: a paper's final build sat uncommitted forever behind such a watermark.
- **The user-id anchor is keyed on the turn being MID-FLIGHT, never on "it has no assistant id yet".** A backend mints a NEW message id for each assistant response *within* a turn, so the `assistant_message_id` a force capture reads is TRANSIENT. The old guard (`not watermark.assistant_message_id`) caught only a turn captured before it had said anything; a mid-flight turn that had ALREADY spoken — the common case — was anchored on that transient id, and once the turn continued the mark matched no boundary and the `marked_at` fallback dropped the turn for having STARTED before it. History then kept only the PARTIAL snapshot the capture took: the turn's real final response and its remaining tokens were recorded nowhere, and its later edits reached history as unattributed diff in whatever commit next swept the tree. (The prompt itself survives in that partial record — the watermark only advances when the capture actually committed. Losing a prompt outright is the SEPARATE inherited-watermark bug below.) Now `anchor_on_user` fires when the turn is incomplete OR has no assistant id, and `set_partial_turn_usage` rides along so `_add_turn_usage` still adds only the delta. Easy to trigger: `uv run` reinstalls the editable package, the tracker reads that as "aGiTrack updated on disk" and restarts mid-turn. Reproduced by replaying a real transcript truncated at 25/50/75% through a turn — the turn vanished from every later commit each time (2026-08-15). Tests: `tests/test_commit_engine.py::test_a_midflight_capture_anchors_on_the_user_id_not_a_transient_assistant_id`, `::test_finish_parse_exit_commits_dangling_no_text_turn`.
- **A conversation NEVER inherits another conversation's watermark.** `backend_message_id_for` used to short-circuit to the global `last_backend_message_id` for the tracked conversation, so a BRAND-NEW conversation — `backend_session_id` already reassigned to it, nothing of its own committed — read the PREVIOUS conversation's id. That id matches no boundary in the new conversation and its `marked_at` is (rightly) absent, so `turns_after` fell through to its last-resort `turns[-1:]` branch and silently discarded every earlier turn. Seen live: commit `bccd5332` in this repo covers the second of two turns and the first was never recorded anywhere (2026-08-15). The accessor now reads the conversation's own map entry first and returns None when it has none; two behaviours are deliberately preserved — an explicit `last_backend_message_id = None` reset still clears the tracked conversation's mark (checked before the map), and a global appearing NOWHERE in the map predates the map (an upgrade) and is honoured as the tracked conversation's own. A side benefit: switching away and back is now exact for the tracked conversation too, which the old short-circuit defeated. Tests: `tests/test_state.py::test_a_new_conversation_never_inherits_the_previous_conversations_watermark`, `::test_a_watermark_predating_the_per_conversation_map_is_still_honoured`, `::test_switching_back_reads_the_conversations_own_mark_not_the_global`.
- **Do not "simplify" either fix into blanking a lost watermark.** A mark that genuinely belongs to this conversation but has stopped matching a boundary (a compaction reshaping turns) MUST survive, so `turns_after` still reaches its bounded time fallback; returning None there re-exports the whole conversation — the 31M-token 20-day commit of 2026-07-25. Pinned by `tests/test_commit_engine.py::test_a_conversations_own_lost_watermark_still_reaches_the_bounded_fallback` and `::test_lost_watermark_never_reexports_the_whole_session`.
- "No response requested." is Claude Code's synthetic filler for aborted/crashed requests and contributes NOTHING to a turn: not a final message, not a stop reason (taking its `end_turn` once made a crashed turn look complete-but-answerless). A dangling turn whose only reply is the filler stays in-flight until a real reply lands.
- A DANGLING turn with no stop reason and no final text is IN-FLIGHT, not complete: the user just typed a prompt and the agent's first assistant row has not landed yet (it can lag by many seconds), or the only reply was the skipped crash filler. The legacy "missing stop reason counts as complete" default applies only to turns that produced final text (old transcripts without stop reasons). Without this, the background tracker — which polls the transcript every ~3s and cannot see process-level agent activity the way the interactive proxy can — caught the window between the user row and the first assistant row and committed a trace holding ONLY the user's message (observed live: a pre-commit flush supplied the dirty tree at exactly that instant).
- ENFORCED: a commit's trace never ends with an unanswered user message. `finish_parse_if_ready` trims trailing final-less turns before committing (they commit on a later cycle, once answered), on ALL paths including force commits (`require_complete=False`: exit finalize, background flush, manual commit-now). The one exception is a SOLE final-less turn under a force commit, kept so exit still captures in-flight work; `turns_after` re-exports it if the conversation later continues.

## Background self-update reminders (never auto-install)

- Installing a newer aGiTrack can't be fully automated (pip/pipx/brew/MSI), so a background daemon **never** self-updates — it only RECORDS an available update and REMINDS. `BackgroundRunner._maybe_check_update` runs a throttled (`timings.update_check_seconds`) `Updater().check()` on a worker thread; on `available` it writes the shared marker `agitrack/update/marker.py` (`<repo>/.agitrack/update-available.json`) + emits an `update-available` event, and clears the marker when up to date. The interactive proxy feeds the same marker (`_consume_update_check_result`). Surfaces that read it: `agitrack -b status`, the pre-commit hook (commit-time reminder), and the dashboard banner (`metrics/web.update_notices`, rendered into the `__UPDATE_BANNER__` placeholder by `_update_banner_html`). Gated by `check_for_updates`. **The record is stamped and EXPIRES** (`written`, `_MARKER_MAX_AGE_SECONDS`, one day; an unstamped legacy marker is judged by the file's mtime): a repo is only re-checked while a tracker runs ON IT, so a project nobody has tracked since keeps its last answer forever, and the dashboard went on repeating a six-week-old comparison of two commits nobody was running. An expired record is deleted on read, not just ignored. **Every surface says what the CHECK said** (`update_reminder_line` returns the recorded `message`): the two findings that write a marker mean different things ("install a newer aGiTrack" vs "the installation is already newer than this session's code, restart it"), and rendering both as the first told people to reinstall an aGiTrack that was up to date.
- **The dashboard banner is LIVE, not just rendered once.** `/state` (both the live view and the backtrace view) carries `update_notices` alongside `agitrack_version`, and the page re-renders the `#updatebanners` container from its own poll (`renderUpdateNotices` in `metrics/ui.py`). The banner used to arrive only with the HTML, so a tab left open for hours went on showing a notice that had since been withdrawn, or an update that had since been installed, until someone reloaded by hand. The backtrace view answered neither field, so it never noticed a version change either.
- Tests: `tests/test_update_marker.py`, `tests/test_background.py::test_daemon_update_check_*` / `test_background_status_shows_available_update` / `test_precommit_sync_reminds_about_update_on_every_commit`.
- **Daemons DO auto-restart once an update has FULLY COMPLETED** (installed by pip/pipx/brew/MSI, the interactive self-update, or a source `git pull` — never by aGiTrack itself): `agitrack/update/restart.py`. Every daemon (background tracker, dashboard, backtrace) runs a watcher thread comparing an install FINGERPRINT captured at daemon start against fresh disk reads. Source checkout → the git HEAD commit ("updated" = a NEW COMMIT LANDED; while `index.lock` exists the reading is unsettled and nothing happens). Wheel install → the installed dist version (missing/unreadable metadata = pip still mid-reinstall = unsettled). On top, the SAME new fingerprint must be seen on two consecutive checks (60s apart) — a half-applied update can never trigger an exec into a broken tree. The dashboard/backtrace restart is a SPAWN-AND-VERIFY handoff (after the daemon's normal cleanup releases the port): spawn the replacement via the daemon's own spawner, wait for ITS handshake (correlated on the child pid; the backtrace wait is progress-aware), and only then exit — so a replacement that crashes on a broken update (e.g. the self-hosted dev repo, whose fingerprint moves every commit) fails VERIFICATION and the old daemon reaps it and serves on. The background tracker still restarts via its re-launch command (`daemons._daemon_command`, POSIX `os.execv`: pid preserved, CLOEXEC releases the repo lock — a spawn-verify handoff would deadlock on that lock); a crashed tracker replacement is recovered by the auto-start pre-commit hook or a rerun. Dashboard/backtrace pin their bound `--dashboard-port` so open URLs survive; the tracker's teardown skips the final force-capture on restart (`_teardown(restarting=True)`) — the replacement resumes the in-flight turn via the persisted watermark instead of committing it half-done. **A FAILED exec never strands a dead daemon**: each daemon's serve/track body is a retry loop — on failure it re-binds/resumes on the current code (handshake + `--daemons` registry restored, hooks re-installed) and retries on the next detection, until the exec succeeds or the user stops it; an explicit stop (`-d stop` / `--backtrace stop` / `-b stop`, or owner death) always wins over the retry. Tests: `tests/test_update_restart.py`. **The restarts are ORDERED, not raced: trackers first, views last.** Every daemon watches the same fingerprint, so one update wakes them all at once — and the view daemons, with the least to do on the way up, kept winning. The reader then got a page that reloaded to announce the new version and, beside it, a warning that this repo's session was still on the old one and should be restarted "when convenient": a warning about a tracker that was already restarting itself, gone by the next poll. So `watch_for_update(defer_while=…)` HOLDS a confirmed fingerprint (it is never discarded — re-running the two-sightings confirmation each round would push the restart back indefinitely) while the gate reports work outstanding, and every daemon under `agitrack/metrics/` passes `restart.stale_background_trackers`, which lists repos whose **background** daemon's lock-recorded fingerprint still differs from disk. Only `kind == "background"` counts: an interactive session holds the same lock and is deliberately never restarted, so waiting on one would keep a dashboard on old code for as long as the conversation lasts. The wait is bounded (`DEFER_LIMIT_SECONDS`, 10 min) for the tracker that never comes back, a gate that raises means "nothing outstanding", and the background tracker itself must NOT pass the gate (it would wait on itself) — a source scan in `tests/test_daemons.py` enforces both halves for daemons added later. The banner tells the two apart too: `selfupdate.stale_session_kind` answers `background` (says the tracker will load it by itself, nothing to do) or `session` (the user really is the only one who can act).
- **Dashboard and backtrace daemons are FREE-STANDING** (no owner-pid; `spawn_dashboard_daemon`/`start_backtrace_daemon` accept an optional owner but the CLI and TUI pass none): they keep serving after the launching terminal closes, until `-d stop` / `--backtrace stop` (or an update self-restart). The Ctrl-G dashboard (`_handle_dashboard_command`) spawns the same free-standing daemon, KEEPS RUNNING after aGiTrack quits, and a popup says so on the first start; the TUI teardown deliberately does not kill it (the old `_stop_dashboard` exit hook is gone). The owner-pid watchdog machinery (`_watch_owner`) remains for callers that want a bound daemon. Tests: `tests/test_proxy_dashboard.py`, `tests/test_dashboard_daemon.py`.
- **`--daemons` lists, `--daemons stop` stops EVERYTHING, everywhere** (`daemons.stop_all`). Free-standing daemons are exactly the ones a user loses track of, so the escape hatch is user-wide, not repo-scoped: it walks the whole registry across every repository. **That reach is also the hazard** — someone typing it while thinking about one repo takes down the dashboards of every other repo they have open (this happened during development, to the user's own five daemons). So the CLI **prints the full doomed list and asks `[Y/n]` before signalling anything** when stdin is a TTY; EOF/Ctrl-C is not consent. Two more invariants: the caller's own pid is skipped (`exclude_pid`, defaulting to `os.getpid()`) so running it inside a live session can't kill that session, and a daemon that ignores SIGTERM is **named, never SIGKILLed** (a wedged dashboard beats one killed mid-handshake-write) — survivors stay registered, and the CLI exits 1 so a partial stop doesn't read as success. Note `stop_all` also finds daemons by scanning the process table, so pointing `XDG_STATE_HOME` at a scratch registry does NOT sandbox it — there is no safe way to rehearse it against a fake registry on a machine with real daemons running. **The listing has to advertise the bulk stop**, with the count and the words "in every repository": someone reading `--daemons` is usually there because they have strays they cannot place, and per-daemon stop commands each need their own `--repo`. It is suppressed when nothing is running. Tests: `tests/test_daemons_stop_all.py`.

## The Enter path is on the clock

- Pressing Enter with a dirty tree HOLDS the prompt behind "aGiTrack is checking existing git changes...". Two things used to make that ~1s: the parse worker did not wake the reactor, so a parse finishing in 80 ms was still released only on the next `ACTIVE_POLL_SECONDS` tick (`start_parse(..., on_finish=self._wake_main_loop)` fixes it), and the Claude transcript was re-read in full every time (0.28 s on this repo's own 146 MB session). `claude.export_session_at` now memoizes the LAST export on `(path, size, mtime_ns, collect_edits)` with a 2-minute TTL: an append-only JSONL that has not grown or been touched cannot have changed, and the TTL means a huge session is not held resident all day. Anything added to this path is paid on every single turn.
- **The cost that survived all that was PROCESS SPAWNS, and it is why "Enter takes a long time" is always a WINDOWS report.** Measured through the real reactor on native Windows, on an empty repo with a CLEAN tree: **740 ms, 19 git subprocesses, 100% of the delay in git.** Nothing was slow — a git spawn is ~38 ms on Windows against ~5 ms on macOS/Linux, so the identical path costs ~120 ms there and passes for instant. It is also invisible to a unit test, because no single method runs anything twice: the repeats emerge from half a dozen collaborating helpers (`_pre_agent_commit_if_needed`, `has_pre_agent_user_changes`, `_base_user_edits_pending`, `_begin_agent_turn`, `_integrate_committed_turn_before_new_turn`, `_ensure_turn_branch`) each asking independently — five `rev-parse --abbrev-ref HEAD`, three `diff --quiet`, three `ls-files --others`.
  - **`git.repo.read_cache()`** de-duplicates read-only git commands for the duration of a block, and the submit path opens exactly one such block. Off unless opened; only unambiguously read-only subcommands are cached; **anything that can write bumps a process-wide epoch that invalidates every cached answer**, so a read after a write in the same scope always re-runs, and a commit made on the GIT WORKER thread is a miss rather than a stale hit (the cache is thread-local, the invalidation is not).
  - **`_tree_is_dirty(repo)`** is the other half: an EMPTY `git status` is conclusive ("no tracked edit and no untracked file exists"), so the three-subprocess precise checks are skipped entirely on a clean tree. Deliberately ONE-directional — a non-empty status is not conclusive (it lists things those checks exclude, e.g. `.agitrack/`), so it only ever means "keep asking".
  - Together: 740 → 468 ms in worktree mode, and **368 → 260 ms under `--no-worktree`**, where base and worktree are the same repo so the cache collapses both sets of checks.
  - Regression test: `test_pressing_enter_does_not_ask_git_the_same_question_twice` (composition). It counts SPAWNS, never elapsed time, so it is deterministic in CI — and it was verified against the unfixed code, which is how a first version that classified nothing as a read (`command[1]` is `-c`, not the subcommand) was caught passing vacuously.

## Commit Messages

- Agent commit subjects start with `<aGiTrack>` followed immediately by the latest user query for readability.
- User commit subjects use the user-provided commit message.
- User commit messages are required; blank user commit messages are rejected.
- Agent commit bodies include the full interaction trace since the last code-changing commit.
- The interaction trace includes full user prompts and final agent responses.
- **OTHER projects' names are redacted out of the message** (`agitrack/commits/foreign.py`, `[OTHER_REPO]`). A session is rarely about one project ("I ported this from acme-billing", "same bug as in client-portal/src/auth.ts") and a commit message is published the moment the repo is pushed. `mask_paths` already covered the ABSOLUTE path; the bare NAME is the form conversation actually uses, and it was going straight in. The candidate set is the user-wide registry (`repos.list_repos(existing_only=False, served_only=False)`) minus this repository — minus anything inside or containing it, so a session WORKTREE (`<repo>/.agitrack/worktrees/<name>`, which has its own registry entry) and an enclosing directory are never "another project". A stopped or deleted repo is still redacted: neither state means its name may now be published. Off per repo with `redact_other_repos: false`.
- **The deliberate hole: an ORDINARY WORD is never redacted.** A project called `paper`, `docs` or `here` shares its name with words the sentence needed, and blanking every occurrence would cost the reader more than the leak ever did — the message would lose more meaning to the redaction than it ever leaked. `is_distinctive` gates it: under 4 characters never; a COMPOUND name (hyphen/underscore/dot/digit/inner capital) always, since nobody writes `test-app` in a sentence by accident; a bare single word only if it is in neither the curated `GENERIC_NAMES` nor the host's `/usr/share/dict/words`. The dictionary is the wide net (it catches `queue`, `parser`, `cargo`, `flask`) and the curated list is the FLOOR, because Windows and minimal containers have no word list — without one the feature is narrower, never wrong. A live `-m` run redacted the word "here" out of "whether it exists here" because a scratch repo was called that; that is what the English half of `GENERIC_NAMES` exists to stop.
- **Redaction runs on the RAW text, in `_mask_secrets`, not only on the finished message.** `_finish` applies it again as a backstop, but it cannot be the only pass: the body is hard-wrapped to 72 columns in between and `textwrap` breaks a long token at its hyphens, so a real commit came out carrying `acme-\nbilling/lib/retry.py` — invisible to any pattern working on the wrapped result. For the same reason the MASK is `[OTHER_REPO]` with an underscore: `[OTHER-REPO]` was itself split across lines. `render_interaction_trace` takes `repo_root` too, so the SUMMARIZER's sole input is redacted before the LLM sees it — otherwise the summary puts the name back in its own words, where no pattern can find it.
- **The agent is asked as well as filtered** (`proxy_agents._NOTE_SCOPE`). The redaction is a backstop over a list of KNOWN names: it cannot recognise a project described rather than named, one aGiTrack has never run in, or a name too ordinary to redact safely. The system-prompt note therefore tells the agent that its final message is recorded verbatim in the commit and asks it to keep that message about this repository. Phrased to constrain what the agent WRITES, never what it may read or run — read as "do not look outside this directory" it would refuse work the user asked for.
- **`--backtrace commit` redacts; the backtrace DASHBOARD does not, and the difference is the point.** The dashboard is a local view of local transcripts rendered onto localhost and written nowhere, so blanking names there would only take information from the one person already entitled to it. `--backtrace commit` writes REAL commits onto a branch made to be pushed, and it builds them from months of transcripts at once — so it carries every project the user mentioned across all of it. `_annotation` takes `repo_root`; only the ANNOTATION is redacted, never the commit's own original message, because that command's promise is to preserve the history it rewrites and add metadata beside it.
- **A reconstructed turn's subject and prompts are MASKED at construction** (`backtrace._subject`, and the `prompt`/`user_prompts` on its `CommitStat`). A real commit's text reaches the dashboard through `collect._parse_commit`, which calls `mask_paths` once at the single funnel every commit enters by — and every field derives from that one masked body. A reconstructed turn never passes through that funnel: its text comes straight out of a backend transcript that no commit ever sanitized, so the subject published an absolute path verbatim (reported and reproduced: 13 turns in this repository's own reconstruction), and would have published a secret in a prompt's first line the same way. It uses the full `_mask_secrets` pipeline, not just `mask_paths`, for exactly that reason — the source was never sanitized at all — and masks BEFORE truncating, so a cut cannot split a path or a token into something no later pass recognises.
- Verified live on **all three backends** (a turn naming another project in the prompt and the reply) and, in `-m` mode with a real background tracker and a real interactive Claude session, through the `prepare-commit-msg` fold into a real user commit: the name reaches neither the subject, the LLM summary, the trace, nor the folded trailer, while `paper/main.tex` survives untouched. Tests: `tests/test_commit_foreign_repos.py`.
- **Queued follow-up messages (sent WHILE the agent is working) must be captured.** Claude Code records a message the user queues mid-turn as a `type:"attachment"` row (`attachment.type == "queued_command"`, `commandMode == "prompt"`, `origin.kind == "human"`) — **NOT** a `type:"user"` row — so the normal user-prompt path never sees it and the follow-up silently vanishes from the commit trace (a real bug: several of the user's instructions were dropped). `transcripts/claude._queued_human_prompt` recognizes these and `parse_rows` records each on the turn in flight as a DISTINCT message in `SessionTurn.queued_followups` (Claude threads it into the same response, so it belongs to that turn, not a new one — but it was sent after the agent already responded, so it is NOT merged into `user_prompt`). Excludes slash directives / non-human origins. Required for background mode (the daemon has no submit-time capture — it only reads the transcript). OpenCode needs no equivalent: it opens a separate turn per `role == user` message natively, so `queued_followups` stays empty there. Verified against a real transcript.
- **Each queued follow-up renders as its OWN `## User` heading** (`CommitEngine.commit_turns`, both the latent and proxy branches emit `("user", user_prompt)` then one `("user", f)` per `turn.queued_followups`), and they join the subject and the leftover-dedup `turn_prompts`. Do NOT merge them into `user_prompt` — an early version did, which (a) read as one giant prompt and (b) duplicated the base in proxy mode: the runner also records each submitted prompt live (`record_user_prompt` → leftovers), and when `user_prompt` was the whole combined blob the symmetric `_same_prompt` overlap missed the base and re-added it. With follow-ups kept separate, the base leftover matches the base `user_prompt` (equal) and dedups; a belt-and-suspenders `_prompt_covered_by` also skips a leftover CONTAINED in any turn prompt (≥90% word coverage, ≥3 words). **Tokens are never doubled by trace text** — `add_token_usage(turn.tokens)` runs once PER TURN (not per entry/leftover) and per-assistant-message usage dedups by message id (`_usage_once`/`counted_ids`).
- **A message the user typed, queued and then DELETED must never reach the trace.** The proxy records every submitted prompt live from its own PTY capture (`record_user_prompt` → `pending_trace`), and `commit_turns` carries any capture that matches no turn prompt through as a "leftover" so a prompt from an earlier incomplete parse is never lost. But a message queued in the composer and then removed before delivery never reaches the backend, so it is absent from the transcript — indistinguishable from that leftover, and it landed in a commit as a spurious `## User` block (a prompt meant for another window). The discriminator is `queued_followups`: a queued message the backend ACTUALLY received IS recorded (Claude writes it as an attachment row), so when the committed turns carry queued follow-ups the transcript is proven to record them and a capture matching none of them was never delivered — drop it. Without that evidence the leftover is still kept (the safety net for an incomplete parse). Tests: `tests/test_commit_engine.py::test_queued_message_the_user_deleted_before_sending_is_not_traced`, `::test_pending_capture_is_still_kept_when_the_turn_has_no_queued_followups`.
- **A turn is an EXCHANGE, and the trace limit counts those** (`_limit_trace_turns`). Something is said to the agent, the agent answers: it is the REPLY that closes a turn, so consecutive messages with no answer between them are ONE turn however many there are. The user can keep typing while the agent works — a correction, an afterthought, a second question — and none of that is a new exchange. The boundary is derived from the shape of the trace itself rather than from how an entry was recorded, so it holds for every recording path and for entries written by older installs. `state.append_trace(starts_turn=False)` marks a message known to have been queued into a turn already under way, which keeps it out of the count even where a reply happens to precede it; absent by default, so nothing older changes meaning. Counting each `## User` block instead cut the trace INSIDE a turn: a real session had one turn carrying eleven messages sent while the agent worked, so a limit of 5 kept only the last three plus the next turn — the opening prompt and eight follow-ups were dropped, and because that turn's work was committed there, the words that asked for it survived in no commit at all. A turn is also opened by a background EVENT that woke the agent with nobody saying anything, and an evicted turn takes its own messages with it rather than orphaning them under a later heading. Tests: `test_messages_sent_back_to_back_are_one_turn_not_several`, `test_a_message_queued_mid_turn_does_not_count_as_a_turn_of_its_own`, `test_a_turn_that_is_over_the_limit_is_still_dropped_whole`, `test_a_long_turns_queued_messages_survive_the_trace_limit`, `test_a_background_event_starts_a_turn_for_the_trace_limit`.
- **Every Markdown heading inside a trace message is pushed down two levels** (`TRACE_HEADING_SHIFT = 2`, `_nest_headings_under_role`): `#` → `###`, `##` → `####`. A UNIFORM shift, deliberately NOT a normalization of the shallowest heading onto some floor — the levels are the message author's own, and re-basing them rewrites what the author said about their own structure (and pushes a message that starts at `#` one level deeper than it should be). The shallowest possible result is level 3, so nothing a message wrote can outrank the `## User`/`## Agent` scaffolding. Two levels rather than one because one nested correctly but did not READ correctly — in plain-text `git log` a message's own sections sat a single `#` from the role headings, so telling the trace's structure from the conversation's content meant counting hashes. Levels cap at the Markdown maximum of 6, so a message already nesting 5 deep loses some depth at the bottom; that is the rare case and preferable to re-basing every message. **Fenced code blocks are deliberately skipped**: a `#` there is content being QUOTED (a shell comment, a Markdown example — including a literal `## User` in a message that discusses the trace format), and rewriting it would falsify what the message showed. That is the one way a `## User`-looking line can still appear inside a trace body, and it is inside a fence. The dashboard's `md()` maps source level L to `<h(L+2)>`, so a message `#` lands at `h5` and `##` at `h6` — exactly the two content styles those rules are sized for. Tests: `tests/test_commit_message.py::test_trace_message_headings_are_pushed_down_two_levels`, `::test_a_deeply_nested_message_heading_is_capped_at_six`, `::test_trace_heading_nesting_skips_fenced_code_comments`.
- **`#` section headings must survive the user EDITING the message.** Every aGiTrack body is structured with `# Interaction Trace` / `## User` / `## Agent` / `# aGiTrack Metadata`, and git's default `core.commentChar = "#"` makes its message cleanup strip every one of those lines whenever the message passes through an EDITOR — `git commit --amend`, `rebase -i` reword, `git commit -e`. The prose survives, so it looks fine while the trace runs together and the metadata block is gone, leaving the commit unparseable (it reads as untracked to the dashboard/story). It happened to a real commit. `GitRepo.ensure_comment_char_preserves_headings()` sets `core.commentChar = auto` **repo-locally** at every startup (`ProxyRunner.run`, `BackgroundRunner.run`, `precommit_sync`): git then picks a character the message doesn't use, its own editor comments still work, and the global config is untouched. Idempotent, and it never overrides a value the user already set. aGiTrack's own commits are unaffected either way (non-editor commits use `--cleanup=whitespace`, which keeps `#` lines) — this is purely about protecting the user's edits. Tests: `tests/test_git_repo.py::test_editing_a_commit_message_destroys_agitrack_headings_without_the_guard` (pins the failure) and `::test_ensure_comment_char_preserves_headings_keeps_them_through_an_edit`.
- **The dashboard filters on ANY recorded metadata field, not just the four with dropdowns** (`web.parse_meta_filters` / `_passes_meta`; the `advanced` panel under the filter bar). Committer/backend/model/date answered the questions asked most and nothing else, while every commit already carried harness version, OS, session name, compactions and token counts that were only reachable by reading `git log` by hand. Wire format is a REPEATED `meta=<key>:<op>:<value>` query parameter (`eq` exact, `has` case-insensitive substring, `ge`/`le` numeric); the value is split off with a bounded partition because ISO timestamps and `mcp__server__tool` names contain colons. Conditions on DIFFERENT keys AND together, conditions on the SAME key OR — that is what makes it a facet: a second value for `system` widens, a `backend_version` condition narrows. A malformed or unknown-operator condition is DROPPED rather than relaxed, because the filter drives every panel on the page and a silently-different slice misreports all of them. The field list is built from the commits in view (`metadata_filter_fields`), so a field aGiTrack adds later is filterable the day it lands with no dashboard change — which is exactly how `backend_version` became filterable. Fields above 100 distinct values get a text box instead of a select (a dropdown of 500 conversation anchors is a wall, not a control). **Bounds order NATURALLY, not lexically or numerically** (`_order_key` splits digit runs from the rest): the three things worth bounding are token counts, ISO timestamps and harness versions, and no single rule fits them — plain string order puts `2.1.9` after `2.1.10`, and `float()` cannot read a timestamp at all. `ge`/`le` originally parsed both sides as floats, so a date or version bound matched NOTHING and read as "no commits" rather than as a filter that could not run. `between` takes `LOW..HIGH` (inclusive, either end may be empty for an open range), which is why the value is partitioned rather than split. **The panel edits a DRAFT and `apply` commits it.** Filtering live on every change refetched midway through a half-written condition: picking a field applied that field's first value, and typing a range's low bound filtered on it before the high bound existed. `state.meta` is the APPLIED set and alone decides the URL and the page; `advDraft` is what the controls edit. The button reads `apply` when there are unapplied changes and `close` when there are none, so it is never a dead end; Enter in a value box is the same intent; applying closes the panel, which floats over the results it just changed. The badge counts APPLIED conditions, never typed ones. **A range with neither end filled in does not filter at all** — it used to select every commit that merely HAD the field, so the view shrank the instant `between` was chosen, while the badge (which already ignored an empty range) still reported nothing filtered; `parse_meta_filters` drops it, so the rule holds for a hand-written URL too. **A refetch must not re-render the panel**: every filter change lands back in `fillSelects`, and re-rendering there tore out the controls the reader was still filling in — typing a range's second bound was wiped the instant the first bound's results arrived, because the element being edited was replaced. It re-renders only when the offered fields change or a condition is pruned, and never while focus is inside the panel. The panel closes on an outside click (document `mousedown`, capture phase, so the click still reaches whatever it landed on) and on Escape. `CommitStat.metadata` carries the parsed block, filtered by `collect.filterable_metadata` to lower_snake_case keys: a commit body can QUOTE a whole metadata block (a GitHub merge copies the PR body verbatim) and carries git trailers, and without that rule the field list filled with `Signed-off-by`, dependabot's `update-type` and prose fragments like `deps(vscode)`. Served identically by the live dashboard and the backtrace, since both scopes share the payload builders. Tests: `tests/test_dashboard_advanced_filter.py`; the panel itself was driven in a real (headless) browser — 36 fields offered, picking `system = macOS 15.7.3` moved 1036 commits to 493, matching the same query against the server.
- **The commit records the agent HARNESS version, not just the backend and model** (`backend_version:`, beside `backend:`). The harness owns the tool set, the system prompt and the editing style, and it ships far more often than the model changes — so `backend: claude / model: claude-opus-5` cannot say what actually produced a change. Measured on this repository: across six weeks (Claude Code 2.1.220 → 2.1.238) the ratio of shell calls to editing-tool calls went from 3:1 to ~10:1 (two sessions at 50:1), Spearman rho = +0.82 against CLI version, with the model (`claude-opus-5`) and the permission mode (`auto`, in EVERY session back to July) unchanged. That drift is what made the shell-edit gap grow, and establishing it meant re-reading raw transcripts because no commit recorded which harness made it. Sources: Claude's per-row `version`, Codex's `session_meta.cli_version`, OpenCode's `info.version`. Per TURN, not per session, because these CLIs update themselves mid-conversation (aGiTrack's own daemons do exactly that) — a span that updated partway is described by the version that made its LATEST turn, the same newest-first rule `model` and `reasoning_effort` follow. OMITTED when the backend reports none, so an ordinary commit's metadata is unchanged; `CommitStat.backend_version` carries it so a reader can group by it, and the backtrace emits the same field so a reconstruction is comparable with a tracked history. Note what a transcript does NOT record: the system prompt. A harness change is therefore visible in its EFFECTS and never its cause, which is exactly why the version has to be written down at the time rather than inferred later. Tests: `tests/test_shell_edits.py`, `tests/test_commit_engine.py`, and `tests/test_backtrace_shell_live.py` (live: the recorded version must equal what each real CLI's `--version` prints).
- **Capabilities beyond the backend's built-ins are part of the provenance.** A repo can hand the agent extra powers through MCP servers, plugins and skills, and a change made with an `mcp__github__create_pr` call has very different provenance from one made with a plain `Edit` — so the metadata records `mcp_servers`, `mcp_tools` (`server/tool`), `plugins`, `skills` and `subagents`. `agitrack/transcripts/capabilities.py` owns the extraction; each parser only hands over the raw tool names it saw plus the skill/sub-agent each capability-invoking call names (Claude: `Skill`'s `skill`, `Agent`/`Task`'s `subagent_type`; OpenCode: `task`'s input). **Deliberately what a turn USED, not what was configured**: usage is provable from the transcript alone, so it is identical in every mode — including the background daemon, which only ever reads the transcript — needs no config discovery that could disagree with reality, and is what actually produced the commit. Lists are unioned across a commit's turns (a server used only in the first of three turns still shaped it) in first-seen order, so re-rendering a span is byte-identical, and each field is OMITTED when empty so an ordinary commit's metadata is unchanged. Long lists truncate with `+N more` (`_CAPABILITY_LIST_LIMIT`) so a fan-out turn can't bury the rest of the block. Carried by `build_agent_commit_message`, both branches of `CommitEngine.commit_turns` (proxy AND latent, so `-b`/`-m`/TUI agree), and the backtrace exporter.
- **MCP tool naming differs per backend and must never be guessed.** Claude namespaces every MCP tool `mcp__<server>__<tool>` — self-describing, split on the DOUBLE underscore so a server or tool whose own name contains one underscore still parses. OpenCode names it `<server>_<tool>` (`lore_lucky_number`), which is indistinguishable BY SHAPE from a built-in like `apply_patch`, so it is resolved only against the servers actually configured for the repo (`opencode.configured_mcp_servers` reads project + global `opencode.json`/`.jsonc`; no CLI spawn — this runs on every parse). With no configured servers nothing is claimed: inventing a server name in a commit's provenance is worse than recording nothing. Longest server name wins, so `lore` and `lore_extra` can coexist.
- **A plugin names itself only through namespacing.** Claude renders a plugin-supplied skill as `<plugin>:<skill>` (`lorepack:pack-lore`) and a plugin's MCP server as an ordinary `mcp__<server>__<tool>`, so `plugins` is lifted from the skill prefix rather than read from any plugin registry — "which plugins were in play" should not require parsing skill names. Verified live against a local marketplace + plugin supplying both a skill and an MCP server. Tests: `tests/test_capabilities.py` (split/merge rules, both parsers' real row shapes, the metadata block, truncation, and both `commit_turns` branches).
- Do not include thinking tokens or intermediate responses.
- Bare slash commands (`/compact`, `/comp`, `/model`, `/clear`, …) are backend/TUI directives, not prompts, and must be kept out of the interaction trace. The transcript parser already drops them; the proxy's own submit-time prompt capture (`CommitEngine.record_user_prompt`) must apply the same exclusion (`_is_slash_command`), or a typed `/compact` leaks into the commit as a stray `## User` / `/comp` entry — which is also redundant with the compaction lead-in note the trace already carries.
- Commit subjects and bodies must not contain terminal escape sequences or control characters; strip arrow-key/escape residue both where the prompt is captured and when building the message.
- Commit bodies include metadata such as backend, session name, backend session ID, aGiTrack session ID, model, commit type, and timestamps.
- Agent commit metadata includes the current context token count and token usage accumulated since the last code-changing commit.
- Token counts must be exact for every category (input, output, cache read/write, reasoning, and their sub-agent equivalents): count each backend message's reported usage exactly once — not more, not less. Claude splits one assistant response across several transcript rows that repeat the same usage (de-duplicate by message id), and sub-agents are recorded separately (own transcript files for Claude, child sessions for OpenCode) and must be fully included. The token counts are a headline metric, so changes to transcript parsing must be verified against real backend data, not only mocks.
- **Exactly-once holds across sub-agents and session switches.** A Claude sub-agent whose `agent-*.meta.json` is missing/unreadable has no parent tool id (keyed `None`); it must NOT be attributed to "the latest turn" on every parse (it would re-attach to each new turn and be committed again). Instead attribute it to the turn active at its file mtime (`_subagent_unmatched_mtime` → `parse_rows(unmatched_subagent_time=…)` → `_turn_index_at_time`): a STABLE home turn the commit watermark can trim after it is counted once. Likewise the commit watermark is **per conversation** (`AgitrackState.backend_message_id_for` / `set_backend_message_id`): EVERY conversation reads its own remembered mark, and None when it has never committed — so switching between conversations never replays/double-counts a conversation's committed turns, and a brand-new conversation never inherits the previous one's mark (see the crash-recovery section: doing so silently discarded whole turns). An explicit `last_backend_message_id = None` reset still governs the tracked conversation, and a global that predates the per-conversation map is still honoured. No-worktree mode now also FOLLOWS an in-backend switch: the parse worker prefers snapshot-based discovery (`_discover_spawned_session`, which returns None without a reliable pre-spawn snapshot so it can never grab a pre-existing unrelated session) over the pinned id.
- A turn's `input` is *fresh* input = uncached input **+ cache-creation (`cache_write`) tokens**, because cache-creation tokens are input the model processed once on the way into the cache. This is deliberately different from the provider's billing model (Anthropic prices cache writes, cache reads, and uncached input as three separate line items at different rates); aGiTrack folds cache-creation into `input` so the number answers "how much fresh context did this turn process?" rather than mirroring the price sheet. Keep the raw breakdown recoverable: still record `cache_write` (newly cached) and `cache_read` (replayed from cache, never folded into `input` — it was already counted when first written) on their own lines. The summarizer's cost obeys the same rule (`summary_tokens_input` includes its cache-creation; `summary_tokens_cache_read` is separate). The same fact is documented for users in the README token-accounting section — keep the two in sync.
- The summarizer must read **only** its instruction prompt plus the interaction trace (the same `## User` / `## Agent` text the commit carries) and nothing else. Run the summarizer backend in `bare` mode — a plain text completion with no tools, no project/user memory or MCP servers, and the agent's default system prompt replaced with a minimal one — so the summary isn't charged thousands of input tokens of system prompt and tool schemas it never uses (a real Claude call dropped from ~18,000 input tokens to a few hundred). `bare` is plumbed through `AgentBackend.run(..., bare=...)`; the main coding agent (and shell mode) must NOT use it, since it needs its tools. Keep this scoped to the summarizer.
- The summarizer is a mechanical text-reduction task, so its `bare` run also drops model thinking/reasoning to the floor (it gains nothing from it and it only adds latency and tokens). Each backend uses its own lever: Claude sets `MAX_THINKING_TOKENS=0` in the child env (a true off on the Anthropic API; a caller-set value still wins); OpenCode passes `--variant minimal` (the lowest reasoning effort its CLI exposes — it has no full "off"). Both are scoped to the `bare` path only and applied best-effort (a backend/provider that ignores the lever just runs as before); coding sessions keep their default thinking.
- Record reasoning/thinking token counts in commit metadata only when the backend session record reports them; otherwise omit the reasoning line. Do not add explanatory token notes to the metadata.
- Record the conversation's reasoning effort / thinking level as a `reasoning_effort:` metadata line, **only when the transcript reveals it** — neither backend records a numeric budget, so this is a coarse, best-effort signal, never asserted as "off". It lives per-turn on `SessionTurn.reasoning_effort`: Claude sets `"on"` when a turn carries a `thinking` content block (the sole transcript signal that extended thinking was active); OpenCode prefers a named effort/variant from the assistant `info` when the export carries one (`_REASONING_EFFORT_KEYS`) and otherwise falls back to `"on"` when the turn spent reasoning tokens. The commit takes the most recent turn that recorded a level (a later `None` does not erase it), so the metadata reflects the level in effect at the end of the span; the line is omitted entirely when no turn revealed one. This is the *coding* conversation's level — distinct from the summarizer, which is forced to its floor on the `bare` path.
- The interaction trace records only each turn's **final** agent reply by default. Including every user-facing message the agent sent during the turn (each as its own `## Agent` block) is opt-in two ways: the per-repo `full_agent_messages` config option (`.agitrack/config.json`, default off, mirroring `trace_turn_limit`), or the `--full-agent-messages` CLI flag which forces it on for that run only. The flag is a per-run override carried as `ProxyRunner._full_agent_messages` and passed to `CommitEngine(full_agent_messages=...)`: `None` defers to the per-repo config, `True` forces it on without persisting. The full list lives on `SessionTurn.agent_messages` (always populated by the parsers, cheap); the engine chooses all-vs-final via `_agent_messages_for`. Only conversational replies are ever included — never tool calls, tool results, reasoning, or file edits — and the trace falls back to `final_response` when a backend didn't recover the full list.
- Record a `conversation_anchor:` metadata line pointing at the backend message id of the last turn the commit covers, **only when the transcript exposes one**. Combined with `backend:` / `backend_session_id:` it pinpoints the exact place in the (locally kept or shared) transcript these changes came from, so a session can be backtracked to that moment. The commit takes the most recent covered turn that carries an `assistant_message_id` (the same id used as the parse watermark); the line is omitted when the backend exposes none (e.g. the shell path). Writer-only — the dashboard does not consume it.
- Track events that reshape the token accounting in both the interaction trace (as a lead-in note) and the metadata: context compactions (Claude's `isCompactSummary` rows, OpenCode's `summary`/`compaction` assistant messages — `context_compactions: N`, attributed to the turn whose context the compaction shrank) and a session being forked or copied from another conversation (`forked_from:` / `copied_from:` with the source and, for a copy, the contributor). A compaction resets the context and a fork/copy inherits another conversation's context and tokens, so these must be recorded to keep the token counts interpretable. The fork/copy origin is a one-shot, surfaced by the new session's first agent commit and then cleared.
- Proxy mode must baseline continued OpenCode sessions on startup so old turns do not inflate token usage for the next commit.
- When the user cancels a turn (Esc) and it produced no committable response, the agent's partial edits would normally sit uncommitted. In the live interactive path the commit engine calls back into the runner (`on_cancelled_fn` → `_handle_cancelled_turn`) which, if the worktree has changes, offers keep / commit-now / discard (discard is confirmed and runs `GitRepo.discard_all_changes`). "Commit" reuses the normal turn-commit path; on commit or discard the parse watermark advances past the cancelled turn. A "keep" answer is remembered in-memory (`_cancel_prompted`, keyed by the turn's backend message id) so it isn't re-prompted every parse cycle. Only the live path prompts — the sync/exit finalize paths pass `on_cancelled_fn=None` so no modal is raised during teardown.

- **The `-b` consent prompt must describe what THIS user's machine will get** (`cli._maybe_prompt_background_hook`, given the backend by `cli._autostart_backend`). Answering yes installs the git pre-commit hook on every backend, and additionally the Claude Code turn-end hook — so the Claude text names `.claude/settings.local.json` and the no-commit-needed trigger, while the Codex/OpenCode text says plainly that tracking resumes at the next COMMIT. Describing the `.claude` file to a user who will never get it promises an install that does not happen and hides the limitation that does apply to them. Locked by `test_the_autostart_prompt_describes_what_this_backend_will_actually_install`.

## One git-editing aGiTrack per repository

- **The rule.** At most one process that WRITES git (commits, ref updates, metadata folded into a commit message) may be active on a repository at a time. It is enforced by the per-repo lock file `<repo>/.agitrack/lock` (`RepoLock`), and it is per repo by design — different repos run independently.
- **Who takes it:** the interactive proxy (`ProxyRunner`, from startup so the VS Code extension can see a session before it finishes booting), the background daemon (handed the launcher's lock), `AgitrackShell` (json/scripted), `--recover`, the auto-track `pre-commit` hook (`precommit_sync`, which defers to a live tracker instead of racing it), and `--backtrace commit`.
- **`--backtrace commit` was the exception and no longer is.** It replays every commit onto a new branch and switches to it, and it took no lock at all — so it could rebuild history from a tree a tracker was still committing into, or move HEAD out from under a session mid-commit. It now holds the lock for the whole run, including the checks (a tree that was clean when we looked is worthless if a tracker commits while the user reads the confirmation) and git-ignores `.agitrack/` first, or its own lock file would dirty the tree it requires to be clean.
- **Read-only processes take no lock and must not.** The dashboard daemon, the `--backtrace` server and the learn/story pages serve a repo without writing its history; locking them would block the tracker they exist to observe.
- **The auto-start hooks check the lock before spawning**, so a turn that ends inside a session an interactive aGiTrack is driving cannot start a second writer beside it.

## Staging Behavior

- When starting a coding agent, if the backend CLI supports appending to its system prompt (Claude's `--append-system-prompt`; OpenCode's TUI has no such flag), append a note that the session runs inside aGiTrack, which auto-commits each turn, so the agent must not create git commits itself unless the user explicitly asks. Apply this to coding sessions only (interactive proxy spawn and the shell-mode `run`), NOT to the summarizer's bare run. It is on by default but can be disabled per run with `--no-commit-guidance` (or `commit_guidance: false` in the global config), threaded as `commit_guidance` through the runners → `spawn_command`/`run`.
- **Background mode (`-b`) delivers the same note through a Claude Code hook** (`agitrack/backends/claude_settings.py`), because there is no spawn to attach a flag to: the user drives the agent themselves and aGiTrack only watches the transcript, so without this the agent commits its own work and the turn is committed twice. The daemon writes a `SessionStart` hook into `<repo>/.claude/settings.local.json` on start and removes it on stop; `.claude/` is in `_NEVER_STAGE_PREFIXES`, so nothing it writes can reach a commit. Three things are load-bearing: (1) **every part of the hook command is quoted**, including parts without spaces — Claude Code runs hooks through a POSIX-style shell, so an unquoted `C:\Users\...\python.exe` loses its backslashes to escape processing and the hook silently never runs (measured: unquoted delivered nothing, quoted delivered the note); (2) the hook **prints nothing when no tracker is running**, since the note ("aGiTrack commits for you") is only true while one is — a hook outlives its daemon after a crash, a reboot, or a Windows `-b stop`; (3) `stop_background` removes the hook itself as well as the daemon's teardown, because Windows has no SIGTERM delivery and `-b stop` terminates the process before any `finally` block runs. Honours `--no-commit-guidance` like every other path. (4) **every injection ends with an issued-at stamp**, because Claude Code DROPS a `SessionStart` injection whose text it has already added to that conversation: on `/resume` the hook still runs and still prints, and the resumed session records nothing (measured on 2.1.235; the A/B is a resume into a conversation that lacked the note, which recorded it in full). Without the stamp a switched-to conversation kept only the copy from its own first start — thousands of turns back in a long or compaction-forked session, or already out of context — so the agent went back to committing its own work, which is what "the no-commit instruction stopped working when I switch sessions" looked like.
- **Auto-start reaches new CODE, not only new commits.** The persistent `pre-commit` hook can only fire when the user commits, so an agent that edits for an hour without committing — exactly the work aGiTrack exists to record — went untracked until the next commit. No git hook can close that gap: git hooks fire on git operations, never on a file write, and watching the filesystem needs a process already running, which is the situation auto-start is FOR. The agent's own turn-end hook is the only signal, so background mode also installs a Claude Code `Stop` hook running `agitrack --autostart-on-change` (`background.autostart_on_change`). GIT HOOKS REMAIN PRIMARY: the commit path is backend-agnostic and unchanged, and a user on Codex or OpenCode loses nothing they had. The agent hook only adds the case git cannot see. It is persistent (its job is to run when aGiTrack is not) and refuses to start for any of four reasons, each checked in the hook rather than left to the daemon: `autotrack_hook` is off, a tracker is already running, another aGiTrack holds the single-writer lock, or the finished turn left the tree unchanged.
- **Auto-start also fires when an agent OPENS a session, on every backend.** The two triggers above can only react to work that already happened (a commit; a finished turn that left changes), so after a reboot the FIRST turn was always written with nothing tracking it. Background mode therefore installs a per-backend session-start hook running `agitrack --autostart-on-agent` (`background.autostart_on_agent_session`, routed by `backends/agent_hooks.py`): Claude Code and Codex take a `SessionStart` hook (`.claude/settings.local.json`, `.codex/hooks.json`), OpenCode has no such hook but loads a PLUGIN at startup with the project directory in hand, so it gets `.opencode/plugin/agitrack-autostart.js`. All three dirs are in `_NEVER_STAGE_PREFIXES`. It passes the same four refusals as the turn-end hook (shared gate: `background._autostart_daemon_args`) minus the has-changes one, and it also PRINTS THE COMMIT-GUIDANCE NOTE when it actually started a tracker — the note hook runs beside it and checked before the daemon existed, so without this the session that starts the tracker is the one session never told aGiTrack is committing for it. Codex caveat: it will not run a hook nobody has REVIEWED and skips untrusted ones silently, so `-b` prints the one-time `/hooks` step (`codex_settings.trust_reminder`); its project layer is also only read for a repo with a persisted `trust_level = "trusted"`. Because the hooks go in for EVERY backend, that reminder is gated on a Codex CLI actually being installed and opens with "If you use the Codex backend" — a Claude-only user must not be handed a chore about a prompt they will never see.
- **`agitrack -i` borrows the session-start hooks and gives them back.** Interactive mode spawns the agent itself and is the single writer, so the backend would otherwise fire that hook at aGiTrack's OWN child and try to start a daemon beside the TUI. `ProxyRunner._displace_background_autostart` records which backends were armed and removes them at startup; `_restore_background_autostart` puts back exactly those on exit — a repo where auto-start was never enabled must not come out of an interactive session with it enabled. Same displace/restore shape as the auto-track `pre-commit` hook.
- **`-b stop` disarms everything, not just the process.** Stopping the tracker removes the auto-track `pre-commit` hook, the Claude `Stop` hook, EVERY backend's session-start hook (removal is never scoped to the current backend — a repo's backend changes between runs, and yesterday's hook would restart the tracker the user just stopped) and the session note, so nothing brings tracking back and nothing keeps telling the agent that aGiTrack is committing for it (false once the tracker is gone, and it stops the agent committing at all). The `autotrack_hook` PREFERENCE is deliberately untouched — one stop does not revoke a standing choice, so the next `agitrack -b` re-arms it; only `--remove-hooks` turns the preference off. See `background._disarm_tracking`.
- **Codex now takes the note too; OpenCode still cannot.** Codex 0.147 added lifecycle hooks whose `SessionStart` input and output are wire-compatible with Claude Code's, so `backends/codex_settings.py` writes the same two hooks into `<repo>/.codex/hooks.json` and the note arrives as a `developer` message (verified live in a session rollout). Its file shape was measured from Codex's own parser errors: top level takes `description` or `hooks`, the event key is PascalCase `SessionStart`, and each entry is a matcher group of `{type, command}` hooks. Before 0.147 it had only `experimental_instructions_file` (which REPLACES its base instructions) and a TRACKED `AGENTS.md`. **OpenCode** still gets no note: its CLI has no system-prompt flag (`--agent` swaps the whole agent), its config is a repo-root `opencode.json` or the user's global one, and the only place a plugin may add text to a turn is the user's own message parts — which would put aGiTrack's note inside the prompt aGiTrack then commits as the user's words. A half-measure in someone else's source tree, or in someone else's sentence, is worse than no note.
- The note is built by `agent_system_note(use_worktrees=...)` (`agitrack/backends/proxy_agents.py`). In the **default worktree model** it also tells the agent that **its current working directory IS the session worktree** (under `.agitrack/worktrees/`), that it should make its edits there and **not** edit the base repository checkout directly, and that aGiTrack handles **both the commit and the merge** of those worktree edits into the current branch. That clause is **omitted under `--no-worktree` and in shell mode** (the agent edits the current branch directly). The proxy spawn threads `use_worktrees=self._use_worktrees`; shell mode uses `use_worktrees=False`. `AGENT_SYSTEM_NOTE` remains as the worktree-model constant. **Word this carefully:** an earlier phrasing ("you do not need to … clean up anything under `.agitrack/`") was read by the agent as "don't write under `.agitrack/`" — so it edited the base repo checkout instead of its worktree cwd, and that work was never committed or merged. The note must make explicit that the worktree IS the cwd and edits belong there. The cwd itself is set correctly by the runner: `make_child_process(command, str(self.repo.repo))` passes the worktree as the child's working directory for both backends (on Windows via `CreateProcessW`'s `lpCurrentDirectory`), and OpenCode additionally receives the worktree as a positional CLI arg. Locked by `test_proxy.py::test_spawn_sets_backend_cwd_to_the_session_worktree` and `::test_opencode_spawn_command_embeds_the_worktree_path`.
- **Custom backend launch command (wrapper).** The backend executable that heads the spawn command (`claude` / `opencode`) can be replaced by a user-supplied launch command so the agent runs under another tool — e.g. `--backend-command "somewrapper claude"` produces `somewrapper claude …`, extending the verbatim-passthrough feature (#32) on the *front* of the command the way `backend_args` extends the *back*. It is threaded as `executable=` into `ProxyAgent.spawn_command` (which builds its head from it, defaulting to `[<binary>]`) and as `launch_command=` into the headless `ClaudeBackend`/`OpenCodeBackend` constructors, so it applies everywhere aGiTrack execs the agent: interactive proxy spawn, shell-mode `run`, and the summarizer. aGiTrack's own sandbox wrapper (`_confine_to_worktree`) still goes **on top** (outermost), and the backend's own flags + `backend_args` are appended **after** the wrapper head. Resolution: a per-run `--backend-command` (shell-split in cli.py via `_resolve_backend_command`, which fails fast on a malformed value) wins; otherwise `GlobalConfig.backend_command(backend)` — a string (any backend) or an object keyed by backend name (so a mid-session backend switch picks up the right wrapper). The runner/shell resolve it per spawn via `_launch_command()` because the active backend can change at runtime. A user-supplied launch command **bypasses** the backend install gate (`ProxyRunner._ensure_backend_available` returns early when `_launch_command()` is set) — a wrapper replaces the backend binary, so the default CLI need not be on PATH. Empty ⇒ launch the binary directly. Because aGiTrack tracks transcripts/sessions for the **selected** backend, `_confirm_backend_command_mismatch` (cli.py) warns and requires an explicit `y` when the command's tokens clearly name a *different* known backend than the selected one (basename match against `available_backends()`); an opaque wrapper that names no backend is accepted silently, and a non-interactive/scripted run proceeds with the warning rather than hanging on a prompt.
- In an isolated worktree session, offer to copy any files the agent left UNCOMMITTED in the worktree (declined untracked files, unstaged edits) or that are git-ignored into the base repo directory — they otherwise never reach where the user works (`_offer_copy_unstaged_to_base`). **Before the copy offer, `_offer_user_commit_for_worktree_edits` offers to COMMIT the user's own uncommitted worktree edits** (gated on `actions.has_pre_agent_user_changes()`) — those belong in git, not just copied — so when both a user edit and copy-able leftovers exist, BOTH prompts appear (commit first, then copy). It's a no-op in the normal turn case (the turn's auto-commit already committed tracked edits). This runs for the **active** session only (a background session is never interrupted mid-run); its files are caught instead when you **switch to it** (`_switch_active`, `context="switch"`) or on **aGiTrack exit just before the worktree is deleted** (`_remove_worktree_on_exit`, `context="exit"`, interactive exit only — skipped on a signal teardown where `screen is None`). The offer popup lists files **vertically and scrollably** (`SelectModal(detail=…)`, PgUp/PgDn). A file already accepted/left in place isn't re-offered until its content changes (`_copy_prompted` fingerprint); **declining mutes the whole current SET of paths** (`_copy_declined`) — aGiTrack won't re-ask while only those files keep changing, and a genuinely new path re-opens the whole set; the mute clears on session switch and aGiTrack restart, and the popup says so. The **exit** offer ignores the mute and warns that declining discards the files. Files that would overwrite existing base files get a single up-front choice — overwrite all / keep all / confirm each one individually. Anything not copied is reported as remaining in the worktree, with the worktree path. No-op without a worktree.
- The reverse direction (base → worktree) runs **before forwarding a prompt** (`_pre_agent_commit_if_needed`): the user's own edits live in the BASE repo working tree (the worktree is the agent's sandbox), so aGiTrack commits the uncommitted work from whichever tree holds it — this session's worktree (`_create_user_commit_popup()`, onto its turn branch) and/or the base repo (`_commit_base_user_edits_if_needed`, onto the base branch), both when both are dirty — then `_sync_idle_worktrees_to_base` merges/re-points the base commit into the worktree(s) so the agent starts from the user's edits, and only then is the prompt sent. Base detection (`_base_user_edits_pending`) counts any tracked edit **or any new untracked (added-but-unstaged) file** (`untracked_files()`, which excludes `.agitrack/`); the user is offered to stage it at the `[y/N]` prompt and, on yes, it's committed and synced. A "don't stage" answer only suppresses re-prompting for the same tree state via a fingerprint gate (`_base_edits_declined_status`, remembered until the base tree changes), so a file is always offer-able again and can never be permanently stranded. Explicit base commits (the `git-user-commit` command and the pre-prompt offer) pass `include_declined=True` to `_create_user_commit_popup` so the stage prompt re-offers every untracked file; the automatic worktree capture keeps `False` so the agent's own untracked decline still sticks.
- Worktree confinement (`agitrack/proxy/sandbox.py`, `_confine_to_worktree`) wraps the backend so its writes stay inside the session worktree (`sandbox-exec` on macOS, `bubblewrap` on Linux), keeping the base repo and sibling worktrees read-only. **It must never block the backend agent from updating itself.** Claude Code and OpenCode self-update in place by rewriting their own install/state/config/download dirs (`~/.claude`, `~/.local/share/claude`, `~/.opencode`, npm-global/Homebrew prefixes, …). `agent_writable_dirs()` enumerates those (realpath-resolved, derived from HOME/XDG + each CLI's resolved location on PATH) and both the macOS profile and the Linux bwrap command carve them out as writable — the macOS profile re-allows them after the base deny (later rule wins), and bwrap re-binds read-write any that fall **under** the read-only base (dirs outside base are already writable via `--dev-bind / /`; only existing ones are bound, since bwrap errors on a missing source). The sandbox confines the *base repo*, not the agent's own toolchain. Confinement is gated by the effective `sandbox` setting (config, or `--no-sandbox` for one run), resolved in cli.py and carried as `ProxyRunner._sandbox`. Users can also grant extra write carve-outs via `allowed_edit_paths` (config list) or `--allowed-edit-paths <p>[:<p>…]` (PATH-separated; CLI wins), carried as `ProxyRunner._allowed_edit_paths` and threaded through `sandbox.wrap_command(..., allowed_paths=…)` → `build_profile`/`build_bwrap_command` (re-allowed like the agent dirs; macOS covers non-existent paths, bwrap binds only existing under-base ones).
- Use `git add -u` by default for tracked modifications and deletions.
- When new untracked files are present, ask whether they should be staged.
- If the user declines staging untracked files, remember those files in repository-local state and do not ask about them again automatically.
- Inform the user when intentionally unstaged files exist.
- Provide an interactive CLI command to review and stage intentionally unstaged files.

## Repository-Local State

- Store state in `.agitrack/state.json` in the target repository.
- Ignore `.agitrack/` by default.
- State includes the aGiTrack session ID, selected backend, selected model, backend session ID, per-backend session IDs, declined untracked files, and pending interaction trace.
- Optional repository-local config lives in `.agitrack/config.json`; `trace_turn_limit` defaults to `5` and controls the maximum recent user turns included in an agent commit body.
- `.agitrack/tracking-gap.json` records when the user switched tracking off and when it resumed (see the stopping section). It is its own small file rather than a key in `state.json` because the process that writes it is not the one that reads it: `agitrack stop` writes after killing the tracker, and the NEXT tracker reads on startup, so sharing a whole-document store would risk a lost update between them.
- `.agitrack/numstat.cache` and `.agitrack/numstat-files.cache` are the dashboard's diff caches: per commit, how many lines it changed and which files it touched. They exist because the dashboard's cost is dominated by two whole-history `git log --numstat` walks (`metrics/collect._apply_numstat` and `metrics/files._numstat_by_commit`), and it rebuilds whenever a ref moves, which on a tracked repo is every turn. Measured on one 916-commit repo with a 10 GB pack: 76s to load, 1s once cached, against 0.04s to read every commit MESSAGE (so the log itself was never the problem). A commit's diff against its parent never changes, so entries are keyed by sha and never invalidated; only new commits are diffed. Two things keep the numbers honest: a count is only cached when git actually produced diff rows for it (unless the clone is not partial, where "no rows" is definitive), and each row records whether it was counted with every blob present (`E`) or from local blobs on a partial clone (`L`, a floor) — only an `E` row may answer the page fetch that `apply_numstat_for` exists to make exact. Both scans run a chunk of commits per git call, which is what lets the FIRST index report itself: `metrics/progress.py` holds the in-flight build per repository, the page polls `/progress` every half second while its own `/data` fetch is still blocked, and the loading screen shows a real bar instead of a spinner that says nothing for a minute (answered on another thread of the threading server, and touching no git). Chunking also banks each chunk in the cache, so an index that is interrupted resumes rather than restarting, and one build at a time is allowed per repository (`RepoScope._build_lock`) so a second tab waits for the first instead of indexing the same history again.

## Learning Page (dashboard `/learn`)

- The live dashboard serves an interactive **learning page** (`agitrack/metrics/learn.py`; routes in `metrics/server.py` AND the backtrace handler in `metrics/backtrace.py` via the shared `handle_learn_post` dispatcher, so the page works in backtrace mode too, even over a directory that is not a git repo: there repo=None, identity falls back to the gh login, progress sync reports unavailable, and the page carries a frozen amber banner, like the dashboard's, warning that suggestions are based on the backtraced reconstruction) where the **backend agent, presented to the user as their "aGiTrack coach", coaches the user from their own interaction traces**. Flow: a two-tap check-in (time available 5/15/30 min, mood fresh/okay/tired, optional free text, optional trace source: own sessions (default), a teammate's, or the whole team, plus a branch selector (default: the current branch; the trace lives in commits so the slice is per-ref, validated like the dashboard's; hidden in backtrace) and a period filter) → one bare backend call over a **trace digest** (recent prompts, efficiency-insight cards, most-changed files, repo shape, README head, prior progress) returns an assessment, evidenced **knowledge gaps** (kinds: `coding` skills for driving agents effectively, and `codebase` knowledge of this repo), and 3-4 lesson suggestions sized to time/mood, each citing its trace evidence. Under 3 tracked turns in the slice there is NO agent call: a notice explains how to get a trace ('agitrack --backtrace', preferably with commit, for history written outside aGiTrack; or running sessions through aGiTrack) and static STARTER topics are stored instead (first session, backend setup, backtrace, agent-driving habits); they flow through the normal lesson pipeline, and the next real-trace suggest clears the notice. Tapping one (behind a full-screen processing overlay; the tapped card pulses too) generates a **step-by-step lesson**: 3-7 small steps the page walks through one at a time (next/back, progress dots; quiz/exercise/links unlock at the final step), 1-3 real external links, a quick-check quiz, and an **in-page exercise**: all material to work with (code, diff, scenario) is included in the task, the learner types their answer in the page, and the aGiTrack coach reviews it (pass/fail + feedback logged). Lessons must never require running terminal commands or leaving the page; legacy single-blob lessons are split on ### headings client-side. The dashboard's agent-efficiency section carries the prominent 'Learn from these traces' CTA card that explains and opens the page. A follow-up chat is stateless (lesson + recent history ride in the prompt).
- **Progress is per user (GitHub id, git `user.name` fallback) and automatic** (opened/completed, visibility-aware time on page, quiz scores, exercise attempts) in git-ignored `.agitrack/learning.json`; completed lessons close their linked gap and feed the next suggestion round so the coach builds on, never repeats. Optional **git sync** (off by default, page toggle): the user's progress log publishes to the history-free orphan ref `refs/agitrack/learning-progress` (`<repo-fingerprint>/<github-id>/progress.json`, lease-guarded push, own entry always rebuilt from the local store) like shared sessions. The ref is also the read-back path: on a machine where the user's local profile is EMPTY, `learn_state` fetches the ref once per process, restores their entry into `learning.json`, and re-enables sync, so progress follows the user across machines; a non-empty local profile is never overwritten. Content style: the coach persona and lesson prompt REQUIRE plain language (simple everyday words, short sentences, concrete examples over abstractions, technical terms defined in plain words on first use).
- **Engine selection**: `learning_backend` / `learning_model` config keys (repo overlay > global > unset) with the **latest session's backend/model** as the default; a model id in the other backend's format is dropped (never fails the page). The page's "coach engine" panel edits the repo-scope keys and lists each backend CLI's models. All agent calls are `bare` one-shots from a scratch dir outside any repo (`~/.agitrack/learning`, summarizer-style isolation so they are never adopted as coding sessions), work on BOTH backends, use per-purpose timeouts via `timeout_seconds` on `backend.run()`, and are serialized by a lock (concurrent requests get a "busy" reply, never a queue).

## The three web pages share one UI layer (`agitrack/metrics/ui.py`)

- The dashboard, the learn page and the storyline are deliberately three SELF-CONTAINED documents (each served alone, each working from a `file://` snapshot, each with its own inline script), but they are not three designs. Everything shared lives in `metrics/ui.py` and is substituted at render time via `ui.render(template)`: `TOKENS` (one palette, one set of names), `BASE_CSS` (reset, `[hidden]`, `overflow-x`, the spinner), `BANNER_CSS` (the frozen top strip, whatever a page calls its element), `OVERLAY_CSS` (the "the agent is working" card, including the line naming the model), `COMMIT_CSS`/`COMMIT_JS` (a commit's message and diff: `commitMd`, `reflowParagraphs`, `renderDiff`), `FLASH_CSS` (`.notice`/`.error` and the fixed bottom toast they float in), `ENGINE_CSS` (the collapsed "who does the work" panel, gear included), the message/changes toggle button under all three of its names (`.diffbtn,.fdifftoggle,.cflip`, inside `COMMIT_CSS`) and `DOM_JS` (`$`, `esc`, `fmt`, `kfmt`, `postJson`). A page keeps only its own layout.
- This exists because the same detail kept being fixed once and left broken twice: a commit rendered in different colours on two pages, `hidden` boxes stayed on screen where a page lacked the rule (the dashboard's file filter in the commits view), a diff wrapped on one page and ran off the edge on another, the backtrace banner had three looks, one page could scroll sideways, the story page reported errors as a red block in the middle of the document while the learn page showed the same message as a quiet bottom toast, the two settings panels grew different gears, and the log's "show file diff" button ended up with NO rule at all - rendering as the browser's default grey chrome on a black terminal page - while the identical button in the file browser beside it was styled.
- **A page reloads itself when the daemon updates underneath it.** aGiTrack self-updates and its daemons restart on the new code, but an open tab keeps rendering the document it downloaded — old HTML, old script, old embedded payload — so a fixed bug looks unfixed until someone reloads by hand. The version rides on the `/state` poll the page ALREADY makes for the running indicator (a second endpoint would double the polling to carry one string); `noteVersion` reloads once when it changes, having stashed the new version in `sessionStorage` so `announceReload` can say why on the page that comes back. The notice box is shared (`ui.RELOAD_NOTICE_HTML` → `__UI_RELOAD_NOTICE_HTML__`) because `announceReload` gives up silently without it: a page missing the box still reloads, it just never explains itself.
- **`tests/test_web_ui.py` is the contract**: it renders all three pages and asserts they share the palette, the banner, the overlay, the commit renderer, the helpers, the phone rules and the width; that no page re-defines a shared helper or ships an unsubstituted placeholder; that each links to the other two; and that every page's script actually runs (evaluated under node against a stub DOM, skipped when node is absent). Page-specific behaviour is tested in that page's own file.

## Storyline Page (dashboard `/story`)

- **How many parts is a function of the history** (`part_target`): the middle of "a part per three weeks" and "a part per twelve sittings of work", bounded at 2 and 8. A fortnight is not five acts and two years is not five either.
- **Which DAYS to tell, not a second telling of the same ones.** The story page carries the dashboard's range control (`ui.RANGE_CSS`/`RANGE_OPTIONS`/`RANGE_JS`, shared so both pages offer the same presets and the same custom from/to popup), and it scopes the whole build: `in_range()` narrows the commits before `start_build`, so the parts, how many there are, and what counts as covered are all computed over the chosen stretch — a story of one week is that week's own story, not a week highlighted inside a year. The range is stored on the story (`range: {from, to}`) and an empty one is refused before any agent call (`_EMPTY_RANGE`). This REPLACED a "look closer" depth that re-told a part's own commits at finer grain: it spent a call to re-read what the reader had already paid for, and since a part holds at most one moment per SITTING of work it could come back with fewer moments than the view it was meant to magnify. Stories written while it existed carry `level: 2` moments over days the coarse telling already covers; `StoryStore.get` drops them on load, or the same stretch would appear twice in one list.
- **A telling COVERS its range.** `spread()` folds a part's sittings into as many even groups as the zoom asks for (`_MOMENTS_COARSE` = 6, `_MOMENTS_FINE` = 15) and each group becomes one moment, so a part is told end to end. Taking the first N sittings instead left the middle and end of a part untold with a pager as the only way in; there is no pager any more.
- **Stop means stop, and so does leaving the page.** A cancelled build's worker can stay alive for minutes (it is inside a backend CLI call that cannot be interrupted, and whatever it returns is discarded), so `_is_live` excludes any build that has been stopped or abandoned: counting it as "a story is already being written" refused the reader the one thing Stop promised. `pagehide` abandons a telling this page started via `sendBeacon` (a normal fetch dies with the page), since an unwatched build spends an agent call and then blocks the next one. The doomed call still holds the shared agent lock, so the new build's first question waits for it inside the worker rather than in the request.
- **A rewrite re-reads the history as it stands now.** `_material` computes the parts fresh for `rewrite` instead of reusing the ones stored with the old story: those end at the then-newest commit, so everything committed since fell outside every part and a rewrite silently left it out. A named-part telling still uses the stored parts, because that is the part the reader clicked on. The range control still bounds either.
- **The controls and the story on screen must agree.** A story is written with the settings of the moment it was told, so changing the voice, the days or the extra instruction marks the **tell it again** button `.stale` (and renames it "tell it again with these settings"): the change is real but nothing has happened yet. Arming that button turns it `.danger` - red, filled, pulsing - because the confirm is the SAME button one press later and must not look like the one just pressed. A finished telling clears both, and lands the reader on the PARTS (`setZoom(2)`) unless they asked for one named part, since a rewrite rewrites the parts and wherever they were standing may no longer exist.
- **The reader is TOLD that the lists open.** A hover-only affordance says nothing until the pointer happens to land on something, and nothing at all on a touch screen. Both the parts and the moments carry a `.howto` line above them, each card is a real control (`role="button"`, `tabindex`, a title, a focus ring) and Enter/Space work it. That is the only keyboard handling on the page: the old `j`/`k` shortcut scheme was removed because nobody could discover it.
- **Two depths, walked one step at a time, and NO zoom control.** `2` the parts, `3` the moments inside one (spread across its whole span); opening a moment is the last step in, to its telling, the developers' own quoted asks, and the commits themselves. You go IN by clicking a part and OUT with one `.zback` button that names where it lands; `#z<level>.<part>` still deep-links. A row of zoom stops used to sit above all this and was removed: depth 3 only means something INSIDE a part, so pressing it from the parts view either did nothing visible or landed in a part nobody had chosen. `normalizeZoom()` runs before EVERY paint, so a depth that needs a part always has one (and a story with no parts falls back to the flat moment list as its top). The stored key is `moments` (a story written before the rename is migrated on load).
- The third web UI beside the dashboard and the learn page (`agitrack/metrics/story.py`; routes in `metrics/server.py` and, through the shared `handle_story_post` dispatcher plus a `story_view(branch)` callable, in the backtrace handler too). It tells **the repo's history as a story**: an arc (title, tagline, eras) over **moments** the reader zooms into for the full telling, **what they asked for** at the turning points (their own quoted prompts), the commits behind it, and each commit's real diff (reusing `/diff`). Both dashboards serve it from their OWN data: the live one from a branch's commits, the backtrace one from the reconstruction (with the same frozen amber "this is a reconstruction" banner the learn page carries).
- **Two passes, both small.** An OVERVIEW call reads the whole history once (`_era_rows` splits it into eras deterministically, `_overview_prompt` only NAMES them) and produces the coarse story: title, tagline, arc, and the eras with span/commits/sparkline that always cover the entire project. An OUTLINE call then writes moment headlines for ONE part (`_MAX_BATCHES=1`): a first build is ~20 seconds and yields a handful of moments, not forty-five. `earlier` tells the part before that, on request.
- **One telling is ONE call.** `spread()` already bounds a telling to `_MOMENTS_FINE` episodes, so `_BATCH_EPISODES` (15) and `_BATCH_CHARS` (24k) exist only as a ceiling — but they must stay above what a spread produces, because only `_MAX_BATCHES` batches are ever sent and a second batch would silently drop the tail of the part (`test_one_telling_is_always_one_call` guards this; it has bitten twice).
- **The writer is given time, and does not pick commits.** `_episode_headline` lists a sitting's commits OLDEST FIRST, each stamped to the minute (`_stamp`), sampled evenly across the sitting (`_sample`, `_HEADLINE_COMMITS`) so a long one shows its end as well as its start, and the prompt asks for ONE moment per episode, named by `"n"`. Commit ids are not in the material at all: `_normalize_moments` maps `n` back to the episode and takes its shas. Before this, the material carried one DAY and one subject per sitting and the model merged sittings itself — which produced "storyline lands, the TUI stops scrolling wrong, and a release patch fails" for a stretch where the release patch came FIRST. Replies naming `shas` are still accepted, for stores and fixtures written earlier.
- **Lazy, bounded pipeline.** `segment_episodes` groups commits into sittings of work (a new episode after a >6h pause, and never more than 12 commits). The outline writes HEADLINES only (title/kicker/emoji/summary); `expand_moment` writes a moment's paragraph and quoted asks the first time a reader OPENS it, over that moment's own material (also oldest-first and stamped), and stores it. Depth is paid for only where someone reads. Which part those calls cover depends on the mode: `rewrite` takes the newest, `extend` continues forward from the story's newest covered commit, `part` tells one named part. (There was an `earlier` mode behind a "go further back" button; both are gone - nobody could tell what it would give them, and the range control says the same thing precisely.) `_material` always works from commits the story does NOT already cover, so no commit is told twice and no tokens are spent re-telling.
- **The overlay goes up at the click, not at the reply.** `build()` calls `showOverlay()` before its POST: starting a build has to reach the daemon and hand the work to a thread, and waiting for that left ~1s in which "tell it again" had visibly done nothing, so people pressed it again. It names the model (`showEngine()`, also refreshed by `renderBuild` for a build this page did not start) and can be stopped from the first frame.
- **The quoted asks are never invented.** The agent names pivotal commits and writes one sentence about each; the QUOTE is read back from that commit's own `## User` trace entry (`_thoughts`), and an id the model made up is dropped, falling back to a real prompt from the moment. Likewise `_resolve_shas` keeps only ids that exist in the batch, and `_absorb_unclaimed` folds any commit the model forgot into the nearest chapter, so a chapter's counts always match real history.
- **Never a blank page and never a lost build.** `outline()` groups the history with no agent at all and is always shown (it is also what a repo with no backend configured gets); moments are persisted per batch as they land, so an interrupted or failed build keeps what it wrote (`partial: true`); an unusable reply is retried once with an explicit nudge and then told plainly from the commits (`auto: true`) rather than leaving a hole. Builds run on a background thread (`start_build`, one at a time per process) and the page polls `/story/state` for progress, so no HTTP request is held open for minutes.
- Stored per branch in git-ignored `.agitrack/story.json`, with the tone it was told in (`plain` / `playful` / `epic`). Engine selection, the scratch-dir isolation and the agent lock are the learn page's (`resolve_learning_backend`, `learn._AGENT_LOCK`), so one backend CLI runs at a time and both backends work. The page carries its own **"who tells it" panel** writing the SAME `learning_backend` / `learning_model` repo keys through the learn endpoints (`/learn/config`, `/learn/models`), so one choice covers both pages.
- **The storyteller has a persona** (`_STORY_SYSTEM`): a documentary narrator who has read every commit and every prompt, writes short sentences in everyday words, prefers one concrete detail to three general ones, may be wry, may not exaggerate, and never writes a sentence that would fit any project. The three tones flavour it further.
- **Destructive actions explain themselves before they run**: "tell it again" and "forget this story" arm on the first click and say exactly what is deleted (how many moments, how many already written out) and what is not (the commits).
- **Eras are ours, names are theirs.** `act_slices` splits dated items into even, contiguous eras, nudged onto the biggest pause between them; the arc call only NAMES each one (`{"n", "title", "blurb"}`). Letting the model group AND name put 26 of 44 chapters in one act titled after its first three. An era carries its span, chapter/commit counts and a sqrt-scaled sparkline.
- **The numbers are drawn, not described**: a green/red bar for what a moment moved, a dot per commit, a token pill, so the prose can stay at 2-3 sentences (summary <=200 chars, detail <=600). Cards reveal as they are scrolled to (`IntersectionObserver`, one-shot, disabled under prefers-reduced-motion) instead of animating all at once on load; the typewriter is gone (it typed for ten seconds on a long quote and read as a hang). Waiting states everywhere: a spinner until `/story/state` lands, a shimmer skeleton while a first build runs, a spinner in a moment being written; story mode waits on a moment that is still being written.
- **A build never repaints the world.** The poll used to call `load()` + full `render()` every 2.5 s, which flashed the whole page, lost the scroll position, restarted the reveal animations and made the stop button hard to hit. It now updates only the build bar, re-renders the timeline only when the moment count changed, never auto-scrolls, and the stop button reports "stopping..." immediately. The page's visuals (bars, dots, sparklines) draw at full size independent of the reveal class, since the era rows live outside the observed timeline and stayed flat.
- **The whole page is one inline script**, so anything throwing at its top level takes the page with it and looks exactly like a server that never answered (a `const` declared below the `state` object that read it did this: ReferenceError, blank page). `tests/test_story.py::test_the_page_script_runs` evaluates the script against a stub DOM under node (skipped when node is absent).
- The page: a hero with count-up counters, era rows, a NEWEST-FIRST timeline of moment cards (expand in place, and the moment is written if it has no body yet), each moment's commits opening on their commit MESSAGE with a button to flip to the file changes (`/diff` carries the message too), keyboard navigation (j/k, enter, esc), a cinema "play the story" mode, `#ch-<id>` deep links, and full phone layout. The deterministic outline shows only BEFORE a story exists: once moments do, every commit is reachable through its moment. The page uses the dashboard's own aG favicon, not a page-specific one. The dashboard links it from the header AND an amber `storycta` card above the log; the learn page links it too.

## Modes are chosen, not defaulted into (`-i`, the mode menu, `agitrack stop`)

- **`agitrack` with no mode named, on a terminal, shows a MENU** (`agitrack/modes.py`): every mode, one per row, with a one-sentence summary of what it is for and the exact command it stands for. Arrow keys move, Enter takes it, a digit or a mode name jumps straight there, `q` quits. Where raw keys are unavailable (a pipe, a test, a terminal that refuses cbreak) the same menu is printed once and answered by typing; where there is NO terminal at all the historical behaviour stands (launch the TUI), so scripts and editor front-ends are unaffected.
- **The modes are DATA, in one table** (`modes.MODES`), which the menu renders, the README documents and the website quotes. A new mode is one entry. Interactive-with-worktree and interactive-without-worktree are SEPARATE rows, as are the manual-commit variants: they behave differently enough that collapsing them hides the choice that matters most.
- **Background with auto commits is the default** (first row, what a bare Enter takes). It asks least of the user: the terminal stays theirs, the agent stays whatever they already use, and the tracking happens anyway.
- **Interactive mode is `-i` / `--interactive`.** It is no longer what a bare `agitrack` starts.
- **`agitrack stop` stops aGiTrack for THIS repository whatever mode it is in** (`agitrack/stop.py`): the background tracker (through its own stop path, so its teardown still runs), any interactive session (asked about first, since that is a live conversation), and this repo's dashboard view. It is scoped: `--daemons stop` is still the machine-wide sweep. Exit 0 covers "stopped it" and "nothing was running"; a stop with nothing running still disarms the auto-start hooks, because "not running" and "will restart itself on the next commit" are not the same state.
- **An interactive session BORROWS the hook slots and gives them back exactly as it found them.** Both of them: the backends' session-start hooks (`_displace_background_autostart` / `_restore_background_autostart`) and the persistent auto-track `pre-commit` hook (recorded in `_setup_manual_commit_mode`, given back in `_teardown_manual_commit_mode`). `-i` spawns the agent ITSELF and is the single writer while it runs, so a hook that would start a daemon for that very session must be out of the way. The symmetry matters in both directions: these hooks OUTLIVE aGiTrack, so a session must not be what silently UNINSTALLS one — and the pre-commit hook also AUTO-STARTS a tracker on the next commit, so leaving one behind in a repo that had none would be an interactive session quietly turning a standing preference ON, from a command that says nothing about it. `_autotrack_hook_will_survive_exit` reads the same record, so the exit prompt never promises a later fold through a hook that teardown is about to remove. Tri-state (`None` = no setup has run) because `_reset_hook_slate` tears down BEFORE it sets up, and that first sweep must not touch a pre-existing hook. Verified live on all three backends, in both directions. Tests: `tests/test_agent_session_hooks.py`, `tests/test_mode_switching.py`.
- A bare command word is only recognized as a COMMAND at argv position 0 or as the single leftover argument (`agitrack --repo X stop`); anything after `--`, or with a word in front of it, is still a prompt for the agent. Promoting a word to a command steals it from every prompt that starts with it, so the theft is bounded to exactly the phrase typed as a command.
- **A bare word that is NOT a command is reported, not run** (`_looks_like_a_command` / `_unknown_command` in `cli.py`, exit 2). Unrecognized arguments are forwarded to the backend, so `agitrack statsu` used to launch a full interactive agent session with the typo as its prompt — a mistyped command is the last input that should start an agent. The line between the two is shape, not a guess: ONE word, no whitespace, letter first, no leading `-`. A sentence (`agitrack "fix the bug"`), a path, and anything after `--` are untouched, so a one-word prompt is still sendable as `agitrack -- refactor`. The message lists the known commands, since the only reason to type a wrong one is not knowing the right one. Checked twice — before argparse for position 0, and on the single leftover after it — because `agitrack --repo X statsu` is the same typo.
- **`agitrack status` is the bare-word spelling of `-s` / `--status`** (same `background.repo_status`; the command sets `args.status` right after parsing). Someone who has learned `agitrack stop` will try `agitrack status`, and answering that with "unknown command" would be the CLI knowing better and saying less. The mode menu offers the command form (`modes.MODES`), so its listing reads as commands rather than a flag beside a command.
- Tests: `tests/test_modes.py`.

## Stopping means stopping: nothing said while stopped reaches a commit message (`agitrack/tracking_gap.py`)

- **A turn PROMPTED between an `agitrack stop` and the next start is never written into any commit message.** Not its prompt, not the agent's reply, not its tokens, model or capabilities. This is not achievable with the watermark alone: the per-conversation watermark is PERSISTENT by design (that is what makes crash/self-update recovery work), so every turn after it looks committable however long aGiTrack was down, and the conversation almost always carries straight on in the backend's own UI, writing into the very transcript the next tracker reads. A conversation STARTED during the stretch was worse: no watermark at all, so the next `agitrack -b` adopted it as "the newest human-driven session here" and exported it whole. Git history is not something a later command can take that back out of.
- **How.** `agitrack stop` and `agitrack -b stop` record the stop in `<base repo>/.agitrack/tracking-gap.json`; the next start a PERSON types stamps `resumed_at` (`start_background_daemon` for `-b`, `ProxyRunner.run` for `-i`). `CommitEngine` splits turns against that floor in BOTH `finish_parse_if_ready` (before anything reads the turn list: the in-flight trailer, the trace, token accounting and the cover path all take their input from it) and `commit_turns` (the last gate before turns become message text), and advances the watermark past the skipped ones so they are not re-exported and re-dropped on every poll.
- **A turn is placed by when it BEGAN.** One prompted during the stretch and still running when tracking resumed was asked for while recording was off, so it is excluded whole rather than half-recorded. A turn carrying no timestamps cannot be placed and is KEPT, the same way `turns_after` errs toward exporting: real transcripts always stamp times, and dropping every turn on a backend that did not would silently stop committing altogether.
- **Deliberately NOT covered.** The file changes: work done while aGiTrack was off is still in the working tree and still needs committing, so the next commit's diff carries it. History before the stop. And `--backtrace`, which is an explicit "reconstruct that conversation" request rather than automatic tracking.
- **Only a start THE USER TYPED closes the stretch, and while it stands nothing may auto-start.** `_autostart_daemon_args` and `precommit_sync` both refuse while `gap_is_open`, so neither a backend's session-start hook nor the git commit hook can put a tracker back. Removing the hooks is not enough on its own and this is not theoretical: removal cannot reach a backend that has ALREADY loaded its plugin, and with an OpenCode server outliving the command that started it a tracker was measured back **1.6 seconds** after `agitrack stop` — it then closed the stretch itself and committed the very conversation recording had been switched off for. The recorded stop is the authority the hook files are not. A dashboard opened mid-stretch records nothing and must not end it either. A tracker restarting ITSELF (a crash, a self-update swap, `agitrack -b` replacing a running tracker) is continuing the same run: it never marks a stop, so the floor the user's own restart put there stands and an in-flight turn survives the swap. Marking is idempotent within one stretch, so `agitrack stop` calling through to `stop_background` does not move the moment it began.
- **While the stretch is OPEN the floor is `inf`: nothing at all is recorded.** Not redundant with the auto-start refusal, because a stop can FAIL to reach a wedged daemon (`agitrack stop` names the survivor and exits 1). The user has still said stop, so a tracker that outlives the command must not go on quoting the conversation into commit messages.
- **`agitrack stop` removes the auto-start hooks whatever was running.** The disarm used to hang off the "nothing was running" branch, which a running dashboard or interactive session makes false — so a stop reported success on a repo whose OpenCode plugin and git hooks were still armed. It is now unconditional, and the report names it.
- Verified live end to end on **all three backends** (a tracked turn, `agitrack stop`, a conversation driven in the backend's own TUI while stopped, `agitrack -b`, another tracked turn): the gap prompt reaches no commit message, the post-restart turn is tracked normally, and the gap's FILE change still lands in the next commit. Codex needs its hooks trusted (`/hooks`) before any of its tracking works at all, and keeps ONE global session store keyed by directory PATH, so a test that reuses a path sees the previous run's conversation as that repo's own.
- Tests: `tests/test_tracking_gap.py`.

## One dashboard on one port, every repository, switched by path (`agitrack/metrics/hub.py`)

- **There is ONE dashboard process per user.** It binds a single port (8765, scanning up) and mounts every repository under a path: `/r/<slug>/` is a repo's LIVE (tracked) view, `/b/<slug>/` its BACKTRACE view, `/` redirects to the repo used last, `/repos` is what the page header's switcher is built from. Previously each repo got a daemon per view on its own port: a port to remember per project, a separate `ssh -L` line each, and no way from one project's dashboard to another's.
- **The trailing slash on a mount is load-bearing.** Every page fetches with RELATIVE URLs (`data`, `log`, `learn/state`), which is exactly what lets the same page code serve from the root of a standalone daemon AND from a mount point. A mount reached without the slash REDIRECTS rather than being fixed up, so the address bar and the page's own links never disagree.
- **Request logic lives in SCOPES, not in handlers** (`server.RepoScope`, `backtrace.BacktraceScope`): `get(path, query) -> Response | None`, no socket anywhere, so the same logic serves a standalone daemon, a hub mount, or a test that never opens a port. `metrics/routing.py` holds the `Response`; `server.write_response`/`read_json_body` are the one wire layer. `None` means "not mine" and becomes a 404 at whatever edge holds the connection.
- **What the switcher offers = every repo aGiTrack is RUNNING on, unioned with every repo it remembers.** Both halves are needed and the first was missing: `repos.remember` was reachable ONLY through `ensure_hub_for`, so a repo was recorded only when a dashboard was opened for it, and `_open_dashboard_on_start` returns early for a scripted run, a non-TTY stdout (the autotrack hook, a script, SSH) or `open_dashboard_on_start: false`. A headless tracker therefore ran indefinitely on a repo the dropdown never listed (seen live). Fixed at the source — the background tracker and interactive session remember the repo where they register themselves as daemons, and the shell/scripted runner does the same — and made self-healing in `hub._served_repos`, which unions in `daemons.running_repos()` and REMEMBERS anything it had to add, so a tracker predating the fix repairs its own entry on the first poll. `running_repos` reads the daemon REGISTRY only, never the `ps` scan: it is consulted while drawing a dropdown the page header polls. A repo the user stopped with `agitrack stop` (`served=False`) is never resurrected, even if a daemon survives — only a repo with no entry at all is adopted.
- **A repository is LISTED while aGiTrack is doing something for it, or would** (`hub.repo_list`): tracking it right now, ARMED to start on the next commit or agent session (`background.autostart_armed`), or open in this hub — which always includes the page doing the asking, so the switcher can never contradict the header above it. A repository that is none of those is finished with, and listing it forever is how a dropdown ends up mostly scratch directories from months ago (measured on a developer's machine: five of eight rows were temp repos from previous sessions). The REGISTRY ENTRY is kept, not deleted, so working in the repo again — or opening it with `agitrack -d`, which mounts it — brings it straight back with its remembered view intact. `/` redirects to the most recent LISTED repo for the same reason.
- **"Armed" is a state of its own, spelled `auto-start`, not `off`.** Both an idle project and an abandoned one have no process running, and calling both "not tracking" was wrong in the direction that costs work: with the hook in place the next commit records the agent's turns, and a reader told "not tracking" goes and starts something. `running_mode` carries `armed` and a `kind` of `armed` for it, so the page header and the switcher say the same thing. `autostart_armed` applies the SAME refusals `_autostart_daemon_args` applies when a hook actually fires — the `autotrack_hook` preference off, a recorded `agitrack stop` that still stands — because a hook that would be turned away is not armed; a stopped repo therefore does not reappear wearing "auto-start" if a hook file survives the stop. Anything unreadable answers False: claiming a repo will restart itself when it will not is the worse of the two mistakes.
- **The switcher resolves "is it running" toward LISTING it.** `running_mode_for` reads handshake files and `daemons.running_repos()` reads the daemon registry, and the two can disagree — a tracker that died without tearing down leaves a stale handshake, one that predates them leaves none. A repo the daemon registry names is listed and marked live even with no handshake to describe it; the row says what is certain ("tracking") and does not invent the mode.
- **Armedness is read from the FILESYSTEM, never from `git`** (`git.hooks.hooks_dir_for_path`). `GitRepo.hooks_dir()` is the authority and shells out to `rev-parse --git-common-dir`, which is right when a repository is already open and wrong here: this is asked once per row on an endpoint the page header polls, so it would put a `git` subprocess per project on the path of drawing a dropdown. The layout it reads is git's own — `.git` a directory in a checkout, a `gitdir:` file in a linked worktree whose `commondir` names the shared git dir — and anything it cannot parse is None, i.e. not armed.
- **The switcher's order is a convention: MOST RECENTLY UPDATED FIRST** (`repos.last_activity`, used by `list_repos` so every reader agrees — the switcher, `/` redirecting to a repo, `hub_status`). "Updated" is the mtime of the repo's `.git/logs/HEAD`: git rewrites the reflog on every commit, it is one `stat` rather than a walk of history (this draws a dropdown), and it counts the user's own commits too. `last_seen` is only the FALLBACK, for a repo with no reflog (opened with `-d` alone, reflogs off, or not a git repo at all) — it means "when a tracker last started here", and one self-update sweep restarts every tracker within the same second, so ordering on it collapsed the list to a tie broken by position in the file. Two candidates were rejected with measurements: `max(last_seen, reflog)` puts the list straight back on that tie (a start stamp is nearly always later than the last commit), and `.agitrack/state.json` looks like an activity signal but is poll noise — the tracker rewrites it on every poll that finds a backend session, so idle repos with a live conversation advanced every ~15s while genuinely idle ones stood still.
- **EVERY daemon restarts by SPAWN-AND-VERIFY, on every platform — including POSIX, which used to `os.execv`.** exec is the one mechanism that cannot keep the "a failed restart leaves the previous version running" promise: it replaces the process image, so a successor that dies on import leaves nothing to fall back to. Measured on a real pip install with a broken upgrade staged (dist-info version bumped, `__main__.py` made unparseable): the background tracker logged "restarting on the new version", exec'd, the successor died on a SyntaxError, and **the repository was left with no tracker at all** — while the dashboard hub in the same experiment survived, because it verifies. `exec_replacement` now spawns on both platforms (detached via `detach_kwargs` on POSIX so the successor outlives the process that exits the moment it is verified), waits for the successor's handshake, and RETURNS on failure — which is what makes `BackgroundRunner`'s already-correct "take the repo lock back and keep tracking" path reachable at all. The cost is that the tracker's pid now changes across a restart; nothing depended on it being preserved, and anything wanting the successor's pid reads the handshake, which is what `verify` waits for. Re-verified live afterwards in both directions: the same broken update leaves the tracker serving, retrying and still holding its repo lock, and a WORKING update still hands over cleanly to a new pid. Tests: `tests/test_update_restart.py::test_posix_does_not_exec_into_an_update_it_has_not_verified` and the two beside it.
- **A FAILED update restart leaves the previous version running, and holding its lock.** All three daemons restart by SPAWN-AND-VERIFY rather than exec, precisely so a replacement running a broken update cannot leave nothing behind: the old process only exits once the replacement provably serves, otherwise it reaps the corpse and serves on. The hub is the only one holding a process-lifetime lock, and it is the only one that got this wrong: it hands the lock over before spawning (or the two deadlock, each waiting on the other) and used to loop straight back into `bind_scanning` without taking it back. One failed restart therefore left the hub serving while holding NOTHING, and the next `agitrack -d` walked in through the free lock and started a SECOND hub on a second port, each serving a different subset of its own caches with the handshake naming whichever wrote last — the exact state `run_hub_daemon`'s docstring says the lock exists to prevent. It now re-acquires before serving again, and if the lock is gone (a successor that came up later than the 30s verification window) it EXITS rather than serving beside it, the same call `BackgroundRunner` makes when it cannot take its repo lock back. The spawn is wrapped too: `_spawn_hub` answers None for the OSError it expects, and anything else it raised came straight out of the loop and ended the process. It also now PRINTS "update restart failed; still serving on the current version and retrying" like the other two daemons — its silence is why a hub that had quietly failed an update was indistinguishable from one that had died. Tests: `tests/test_hub.py::test_a_failed_update_restart_keeps_the_dashboard_serving` and the three beside it.
- **A tracker whose repository is DELETED stops itself** (`BackgroundRunner._repo_is_gone`, checked at the top of each poll cycle). Nothing else could stop it: `-b stop` and `agitrack stop` both work through files under `<repo>/.agitrack/`, which went with the directory, so only `kill` could reach it — and it is invisible in the switcher, since a deleted repo is dropped from `list_repos`. Temp-dir repos make this routine (six orphaned trackers for removed `pytest` temp repos were found alive on a developer's machine). Only the DIRECTORY vanishing counts: removing `.git` alone leaves a repo the user still has and may re-init, and an `OSError` while asking (permissions, a stalled mount) is never read as "gone". It sets `_explicit_stop`, so the update-restart path cannot resurrect it, and teardown skips its final commit capture — there is nothing left to commit into.
- **`agitrack/repos.py` is the user-wide list of repositories** (`~/.agitrack/repos.json`, honouring `AGITRACK_CONFIG_DIR`). The slug is DERIVED from the resolved path (readable name + short hash), never allocated, so every process computes the same URL without asking the hub. `served` is cleared by `agitrack stop` and set by working on the repo again: the entry survives, so the remembered view and the once-only switch below survive a stop/start cycle. Unknown keys written by a newer aGiTrack are carried through on save.
- **Which view opens is decided per repo, once** (`hub.preferred_view`): nothing tracked + reconstructable sessions ⇒ BACKTRACE (an empty page is the worst answer when the history is in the transcripts); the FIRST time the repo has a commit carrying non-zero token counts ⇒ switch to the tracked view, exactly once (`tracked_seen`); after that whatever view the user last chose stands. A page that keeps overriding the reader's choice is a page arguing with its reader.
- **A reconstruction that reads only the EDITING tools sees a fraction of the work** (`agitrack/transcripts/shell_edits.py`). Agents edit through the shell constantly — a `cat` heredoc for a new file, an inline Python `read_text`/`replace`/`write_text` script to patch one, `sed -i` for a one-liner — and Claude Code's auto mode explicitly INSTRUCTS it to. Measured against this repository's own tracked commits: one session ran 405 Bash calls against 42 Edit/Write calls, and the backtrace reconstructed **31.5%** of the lines those commits recorded; with the shell read it is ~99% per commit (whole-repo reconstruction went from +38,190 to +55,075 lines). The whole gap was invisible — a shell-only turn looked like a turn that changed nothing, which also starved `--backtrace commit` of the file overlap it attributes commits by. Recovered idioms: `cat`/`tee` heredocs (both `cat > f <<EOF` and `cat <<EOF > f`, plus append and `tee -a`), inline Python via heredoc or `-c`, `sed -i` (including BSD/macOS's mandatory empty backup suffix, the spelling every Mac-recorded session uses), `echo`/`printf` redirects, and `mv`/`cp`/`rm` of files the session itself wrote. **Nothing is executed** — every recovery is a parse of recorded text, and `ast` is used to READ inline Python, never `exec`. Replaying commands off a transcript to draw a dashboard is not a trade this makes, which is why `uv lock`, formatters and codegen stay unrecoverable; the exact numbers, and the two other sources that could close the rest (Claude Code's `~/.claude/file-history` backups, and the real `git` numstat when the directory is a repo), are in the analysis behind this change.
- **A sub-agent's file edits belong to the turn that delegated them** (`claude._subagent_edit_map`, `opencode._collect_subagent_work`, `codex._subagent_work`). A sub-agent's transcript is a separate file that nothing else reads — it is not a conversation the user can resume, so it appears in no session listing. Its TOKENS were already recovered on all three backends; its EDITS were recovered only on Codex, so on Claude and OpenCode every file a delegated agent wrote was missing from `--backtrace` entirely and a turn that fanned all of its work out looked like a turn that changed nothing. Each sub-agent gets its OWN `file_state`: its work runs concurrently with the parent turn, so there is no true ordering to share a baseline with, and an isolated one can only ever MISS an overlap rather than corrupt the main reconstruction with edits interleaved at the wrong point. Attribution follows the same rule the tokens already use (Task `tool_use` id / `task` child session id, falling back to the turn running at the transcript's mtime), because a turn reporting a sub-agent's tokens beside none of its files describes half of what happened. The OpenCode walk collects tokens and edits in ONE pass — each child costs an `opencode export` subprocess — and Codex's sub-agent pass reads the shell as well as `apply_patch`.
- **Two SPELLINGS decided whether a whole session reconstructed or not**, which is why per-session recovery looked like it varied by date. `_PYTHON` matched a bare word, so `python3 - <<PY` was read and `./.venv/bin/python - <<PY` — the identical script — was invisible; one session ran 60+ that way and went from 46.7% to 70.8% of its tracked lines once an interpreter path counted. And an agent that names a directory once (`SP=/tmp/work` … `cd $SP`) had every `$` treated as unknowable even though the value is right there in the command; tracking `NAME=value` assignments and expanding them took another session from 64.4% to 78.4%. A command substitution (`SP=$(mktemp -d)`) and a name the command never assigns still decline, so the "exact or absent" rule holds. The lesson generalises: when a whole session reconstructs near zero, suspect the pattern before suspecting the transcript.
- **Judge recovery per SESSION, not per commit.** An aGiTrack commit covers one turn or several (measured on this repo: 1.0-2.5 turns per commit, max 12), and `conversation_anchor` names only the LAST — so scoring a turn against "its" commit credits one turn's edits against several turns' work, and a turn whose work lands in the neighbouring commit reads as a miss twice over. Both are attribution artifacts, not recovery failures: one session scored 43.6% per commit and 97.3% per session, having reconstructed ~16,100 insertions against 8,907 tracked. Repo-wide the two measures are 71.4% and 81.4% of authored-source lines. Anything comparing the reconstruction to git history has to say which denominator it used, and must exclude generated/bulk artifacts (`docs/demo/story.json`, `*.bak` whole-file copies, lockfiles) — 45% of this repo's tracked insertions, 0% recoverable without executing recorded commands, and including them silently halves every number.
- **`cd` is followed, or the reconstruction INVENTS paths** (`shell_edits._apply_cd`). A shell tool call records one `cwd`, and the command routinely moves: `cd /tmp/scratch && cat > notes.md` was resolved against the SESSION's directory and recorded as a repo-root `notes.md` that has never existed — scratch work done outside the repo counted as changes to it, under filenames git has never seen. Following `cd` cut never-tracked paths in the reconstruction from 6.1% of recovered lines (82 distinct paths) to 1.5% (12). Two rules keep it honest: a target the text cannot pin down (`cd $VAR`, `cd -`, a bare `cd`) makes every later relative path on that command unresolvable and therefore SKIPPED, rather than resolved against the directory it just left; and a **subshell** `cd` is scoped to its own line, since `(cd pkg && …)` moves nothing for the caller and letting it persist resolved a later `pkg/mod.py` to `pkg/pkg/mod.py`.
- **The recovery must be exact or absent, never approximate.** `file_state` is the running per-file reconstruction every LATER diff is taken against, so a wrong recovery corrupts everything after it — worse than recovering nothing. Hence: a computed replacement, a `re.sub` or any other unmodelled transform, a write whose content came from somewhere unseen, a BRE-only `sed` pattern (`\(` is a group to sed and a literal paren to Python's `re`), a `printf` with format specifiers, or a `$VAR`/glob/`~` in a path all DECLINE that file whole. Two rules earn their keep: paths resolve against the command's recorded cwd, so the file a heredoc wrote and the editing tool later patched land on ONE `file_state` key instead of being counted twice; and the inline-Python analysis walks STATEMENTS in order tracking which variable holds which file's content, because one script routinely patches the code and the note about it together and a flat scan cannot say whose replacement is whose. Each backend reaches it through its own shell tool — Claude `Bash`, OpenCode `bash`, Codex `exec_command`/`shell`/the JavaScript `exec` sandbox — so `tests/test_backtrace_shell_live.py` drives all three REAL CLIs and rebuilds the reconstruction twice, once with the recovery neutralised, because a mocked transcript cannot tell us the shape a live backend actually records. Tests: `tests/test_shell_edits.py`, `tests/test_backtrace_shell_live.py` (live).
- **The two views stay separate, and each points at the other.** They are never merged, because a reconstruction is inferred and merging would drag the recorded history down to the inferred one's accuracy. The backtrace says plainly that it is NOT the active tracking and is less accurate (banner, on all three pages). The tracked view says when the backtrace holds agent work no commit covers (`metrics/pending.py`) — cheap session-level estimate by default (one directory listing + one `git log`, cached), exact turn count when the reconstruction happens to be built already; it NEVER builds one to decorate a page nobody asked to decorate.
- **The branch selector offers every branch you could look at, including ones only the REMOTE has** (`collect.viewable_branches`). A branch someone has just fetched exists solely as `refs/remotes/origin/<name>` until it is checked out, and the selector listed `refs/heads/` only — so a newly pulled branch never appeared, however long you waited, and the commits were visible in `git log` with no way to open them here. Local branches come first; a remote branch that HAS a local counterpart is dropped rather than listed twice, and `origin/HEAD` (a symbolic alias for the default branch) is never offered. `GitRepo.list_remote_branches` is deliberately NOT folded into `list_branches`: everything that checks out, merges or deletes a branch means a LOCAL one, and handing those callers a read-only remote ref would be a new class of bug. ONE function backs both the selector and `RepoScope._ref`'s validator, because offering a branch the validator then refuses falls back to HEAD silently, which reads as the selector being broken.
- **A remote-tracking branch the remote no longer HAS is not offered** (`agitrack/metrics/remote_branches.py`). Git never removes those refs on a plain `git fetch` — only `--prune` does, and most people never pass it — so a clone keeps `refs/remotes/origin/<name>` for every branch ever pushed, and the selector filled up with branches merged and deleted months ago. Only the remote can answer that question, so `git ls-remote --heads` is run per remote on a BACKGROUND thread and cached for 300s, the same shape as the GitHub login crawl beside it: a render never waits, the first paint shows what the clone has, and stale entries drop off a poll or two later (the `_ref_state` fingerprint holds branch names, so the pruned list rebuilds the dashboard by itself). Three rules make it safe: **fail open** — a remote that is unreachable, needs a credential we do not have, or is not configured is left UNCHECKED and all its branches show, because hiding a branch over a network failure is the worse error; **never prune** — the user's refs are not ours to delete, only the display is filtered; and **no remote-only branches means no network call at all**, so a repo whose remote branches are all checked out locally never dials out. Matching is on the actual remote name, not the first slash, so `origin/release/2.1` resolves correctly. `GIT_TERMINAL_PROMPT=0` plus a timeout keeps a credential prompt or a stalled connection from wedging the refresh. Verified live against a real GitHub repo: a branch deleted through the API stopped being offered on the next poll while the local ref stayed put. Tests: `tests/test_dashboard_branches.py`.
- **The dashboard cache fingerprint includes the branch NAMES** (`RepoScope._ref_state`). It was the shown branch's tip plus the latent refs — and a branch arriving does not move the branch you are looking at, so even a new LOCAL branch stayed out of the selector until the current branch happened to commit. Names, not tips: a branch merely MOVING changes nothing the selector shows, and rebuilding the whole history for it would be pure churn. Each request runs under one `read_cache()` scope so the branch list and the shown tip are asked of git once, not once per consumer.
- **GitHub identities are resolved for the branch being VIEWED, not just the default one** (`github.resolve_logins(..., ref=)`). `repos/{owner}/{repo}/commits` lists the DEFAULT BRANCH's commits and nothing else, so every contributor whose work was only on a newly pulled branch got no login at all and fell back to their raw git name. The same person then carried two labels depending on which branch you were on, and filtering by their GitHub ID dropped their branch-only commits entirely — they read as missing from the commit list. The viewed ref's commits are now crawled too (`?sha=<tip>`, a SHA because a remote-tracking name means nothing to the API) and merged over the default branch's map, cached per `(repo, ref)` and refreshed in the BACKGROUND like before, so no poll ever waits on it. An unpushed ref 422s and falls back to the email heuristic, exactly as a repo with no GitHub remote does. Verified against a real private GitHub repo: a contributor with commits only on the pulled branch resolved from `Bob Builder` to `bobknob23987 (Bob)`, and filtering by that ID returned his commits instead of none.
- Tests: `tests/test_dashboard_branches.py`.
- **An empty dashboard always gives a reason** (`pending.empty_state`): sessions exist but nothing tracked ⇒ the "commit this work" notice; no sessions but the repo has commits ⇒ say there is no agent history to trace and let the commits stand; nothing at all ⇒ say there is nothing to show yet.
- **The dashboard opens when aGiTrack starts on a repo, in EVERY mode** (`open_dashboard_on_start`, default true; never for scripted/non-interactive runs). One hub means that costs a browser tab, not another server.
- **An already-open dashboard tab is STEERED, not stacked on** (`hub._Clients`, `_steer_open_tab`). Pages ping `/clients` while they are open; a launcher asks `/steer-candidate` who is there, raises that browser, then POSTs `/navigate` and waits for the page to take it. Three things make it work on the tab that actually exists, all of them learned the hard way: (1) **the raise comes FIRST.** Every current browser throttles timers in a hidden tab to roughly one tick a minute, and the tab worth reusing is hidden by definition (the user is in the terminal); queueing a navigation and waiting seconds for it to notice is waiting for nothing. Raising the window makes the tab visible, its timers run again, and it pings. (2) **`_CLIENT_TTL_SECONDS` is sized for a throttled tab** (90s, not 15s): at 15s the tab was outside the liveness window most of the time and the launcher opened another. The page also pings on `visibilitychange`/`focus`, which is what makes the raise pay off within a second. (3) **A hub the launcher just started has an EMPTY registry** (nothing is persisted) while the surviving tabs are one ping away from re-registering, so `open_dashboard` passes `_COLD_HUB_CLIENT_WAIT_SECONDS` and `_await_dashboard` waits that long for one to appear. A hub too old to answer `/steer-candidate` falls back to ask-then-raise. Only DASHBOARD pages are steered (a story or learn page is somewhere the reader chose to be), and every failure just opens a tab. Tests: `tests/test_hub.py`.
- **The header controls are shared, once** (`ui.HUBBAR_*`): the repo switcher and the tracked/backtrace toggle are identical on the dashboard, learn and story pages, and switching either one KEEPS the page you were reading. The strip removes itself when the URL is not a hub mount, so the standalone daemon and the static export are unaffected.
- **The header carries three controls, and they are shared** (`ui.HUBBAR_*`): a repository selector, a tracked/backtrace toggle, and a status light saying whether aGiTrack is running on the repo being shown and in which mode (`background.running_mode`, served at each scope's `/state`). The selector is a custom listbox, not a `<select>`: a native one cannot scroll at a bounded height, cannot carry a two-line row (name + state on one line, path under it), and cannot pin the "show another repository" item that opens the how-to dialog. EVERY row carries its own repo's tracking state, re-read each time the menu opens and updated in place (rebuilding would move the reader's cursor and scroll position); `/repos` answers it via `background.running_mode_for`, which reads the path alone, because putting git on the path of drawing a dropdown would make the switcher the slowest control on the page and some listed directories are not repositories at all. Switching repository navigates through `/go/<slug>/`, which redirects to whichever view suits THAT repo — carrying the current view across is what lands you on another project's empty page.
- **Every way into the dashboard answers with something actionable** (`cli._dashboard_without_a_repo`): a missing path says so, a file says so, a non-repository directory that HAS agent sessions is shown its backtrace (which needs no git), and one with nothing at all gets the two commands that change that. "Not a Git repository: ." was the whole answer before.
- **The dashboard opens after the LAST startup question, not in the middle of them** — handed to `ProxyRunner` as `on_startup_complete` rather than fired from `cli.py`, because the interactive path asks its final questions (privacy, the pre-agent commit) inside the runner.
- **A directory recreated at an old path does not inherit the old project's conversations** (`backtrace._drop_sessions_predating`): sessions whose TRANSCRIPT FILE stopped changing before the directory was created are set aside, and the banner says how many. mtime, not the recorded `updated` (which comes from inside the transcript and can be anything); no filtering where the filesystem records no creation time; `AGITRACK_BACKTRACE_ALL_SESSIONS=1` overrides.
- **The static export can open a story chapter's commits.** Shipped moments carry no `detail` (that is written per moment by a live agent), and the page answered a click by asking one — so every chapter of the public demo opened onto an error about a feature the reader cannot use, hiding the commits sitting in the data. The shim sets `window.AGITRACK_STATIC`, and the page renders what it has, saying which part is missing.
- Tests: `tests/test_hub.py`.

## MVP Interface

- `agitrack -i` starts proxy mode in the current repository (a bare `agitrack` shows the mode menu first), launching the native OpenCode TUI through a pseudo-terminal and rendering it through an internal terminal screen with an aGiTrack status line.
- `agitrack --repo PATH` starts the interactive CLI for another repository.
- `agitrack --json` uses the structured JSON prompt-loop fallback (mainly for testing / programmatic drivers; `--mode json` is a deprecated hidden alias kept working for existing scripts). Internally still `args.mode == "json"`.
- `agitrack --json --ui-bridge` runs a long-lived **bidirectional JSON-RPC bridge** over stdin/stdout (`agitrack/shell/bridge.py`: `BridgeServer` + `BridgeUI`) for programmatic GUI drivers. The driver sends `prompt`/`command`/`answer`/`exit` lines; aGiTrack streams `ready`/`response`/`commit`/`no_changes`/`notice`/`error`/`turn-complete`/`bye`, plus `ask` events (`kind`: select/multiselect/input/confirm) when it needs interactive input. Bridge mode is interactive even though stdin isn't a TTY: `AgitrackShell` injects `BridgeUI` into `AgitrackActions.ui`, so the untracked-file review and user-commit-message prompts (and the summarizer-model prompt) are asked of the driver instead of `input()`. `BridgeUI._ask` blocks on a thread-safe queue until the matching `answer` arrives. The terminal/`--prompt` paths are unchanged (`ui` defaults to `None`). `_emit`/notices route through the one lock-serialized bridge stdout channel. Covered in `tests/test_bridge.py`. NOTE: the VSCode extension in `editors/vscode/` does NOT use this bridge — it is a thin launcher that runs the real proxy-mode CLI in an integrated terminal (full parity). The bridge/`--json-events` remain as standalone programmatic interfaces. The TypeScript extension is not exercised by the Python gate (compile/package/F5 only).
- `agitrack --verbose` shows aGiTrack diagnostic messages; normal mode should avoid debug/status chatter.
- Plain text input is sent to the active agent backend.
- In proxy mode, all printable input is forwarded to the backend; aGiTrack controls are opened with `Ctrl-G` only. `:` is not an aGiTrack command trigger in proxy mode and is forwarded to the backend like any other character.
- Proxy mode command palette previews aGiTrack commands; Up/Down selects, Tab completes, and Enter runs the selected command.
- In JSON mode, aGiTrack commands use `:` instead of `/` so OpenCode-native slash controls are not intercepted.
- The interactive UI should show status information and contextual command hints for both `:` aGiTrack controls and `/` OpenCode-native controls.
- Intentionally unstaged-file notices should live in the status bar, not in the main transcript.
- Proxy mode renders the backend screen itself, so it must reproduce each cell's colors and attributes (bold/italic/underline/reverse) exactly as the backend emitted them.
- **Faint (SGR 2) must be reproduced.** pyte 0.8.2 has no slot for faint and silently drops `\x1b[2m`, so dim text would re-render at full intensity — most visibly Claude's grey autosuggestion ghost text, which then looks identical to what the user typed (#113). `_BackgroundColorEraseScreen` carries a `dim` flag on an extended Char (`_DimChar`): it overrides `default_char`/`reset` so every cell has the slot, tracks faint in `select_graphic_rendition` (2 sets it; 0/22 clear it; last wins), clears it on background-colour-erase, and `cell_sgr` re-emits `2`. **The `2` must be parsed positionally, exactly as pyte consumes SGR params — never matched anywhere in the list:** in a 24-bit colour like `38;2;r;g;b` (or `48;2;…`) the `2` is the colour selector, not faint, so `select_graphic_rendition` skips 38/48's parameters before testing for faint. Missing this dimmed all normal truecolor text (e.g. the user's own white input), not just Claude's suggestion. Any future pyte upgrade that natively supports faint should retire this shim.
- **Mouse: aGiTrack only owns the wheel; text selection is the terminal's.** For a backend that doesn't drive the mouse itself (Claude), aGiTrack enables host mouse reporting (`\x1b[?1000h`) purely so the **wheel** scrolls its rendered history (`_handle_mouse` → `_scroll`); PageUp/PageDown do too. It must **not** act on left-button press/drag/release — it used to drag-select-and-copy, but that path only ran in terminals that forward a plain drag to the app under mode 1000, where it both suppressed the terminal's native selection and popped an unwanted "Copied N char(s) to clipboard" message (#112). Terminals that select natively never forward the drag, so they were unaffected; dropping the behaviour removes only the harmful case. Mouse report bytes are still stripped from the input forwarded to the backend (`_intercept_scroll`). OpenCode drives its own mouse (`child_mouse`), so none of this applies to it.
- **A corrupted mouse report must ABORT, not wait forever.** `_update_passthrough_prompt` (the reconstruction of what the user typed, for the interaction trace) accumulates an SGR mouse report (`\x1b[<Cb;Cx;Cy` + `M`/`m`) byte by byte into `passthrough_escape` until `_escape_sequence_complete` (`proxy/modal.py`, the single source of truth also used by the popup modals) says it's done, then discards the whole thing. That check used to be *only* "does the last byte seen so far equal M or m" — open-ended, with no bound besides the terminator ever showing up. A report cut off before its terminator (a dropped byte, a multiplexer splitting it oddly) then never completed: the accumulator kept swallowing every keystroke typed afterwards, waiting for an M/m that would never arrive on its own, until an UNRELATED 'm' the user happened to type next (e.g. the one in "model") satisfied the same check and got mistaken for the sequence's own end — landing a raw `[<35;124;48` fragment in a real commit's interaction trace, with the real keystrokes in between silently eaten. A genuine report's body is only digits and `;`; `_escape_sequence_complete` now treats ANY other byte as proof the sequence has gone off the rails and completes (aborts) right there, sacrificing only that one byte rather than everything after it. Defense in depth: `commits/message.py`'s `_mask_secrets` also strips a malformed/unterminated fragment of this shape (`MOUSE_REPORT_FRAGMENT_RE`), since the sanitizer must not depend on the capture being perfect.
- Proxy mode must re-emit colors in the same encoding/depth the backend used, chosen from the shared terminal color support (truecolor stays 24-bit; 256-color stays a palette index so the host terminal's own palette renders it; named ANSI stays named). Upconverting 256-color output to truecolor breaks terminals without truecolor support (e.g. Apple Terminal) and shifts colors on terminals with customized palettes.
- Proxy mode must answer the terminal capability queries the backend makes (foreground/background via OSC 10/11, palette via OSC 4, cursor position, device attributes) using the host terminal's real responses, so the backend detects the same theme it would in a native session. Without this the backend cannot match the host terminal's light/dark theme and colors render wrong. The one exception is a **forced** `agent_background` (`dark`/`light`), which is reported in place of the terminal's real colours so a self-theming backend agrees with the canvas aGiTrack paints; under the default `terminal` the relay stays truthful — the terminal's own answer, or, when it answers nothing at all (Apple Terminal), the one `host_background.py` derives from the platform. That truthful relay is load-bearing: it is what makes a self-theming backend match the user's terminal without aGiTrack having to adapt anything. Tests: `tests/test_agent_theme.py::test_what_the_runner_answers_the_backend_with`, `::test_a_silent_terminals_derived_background_is_what_the_backend_is_told`.
- **Those answers must be in the backend's hands within ~100 ms of it asking.** A backend asks in its first milliseconds and gives up quickly (codex: measured working at a 50 ms reply and already given up at 150 ms). aGiTrack spawns the backend EARLY on purpose, so it loads while aGiTrack finishes starting — but nothing read its output until the reactor's first `select`, one or two slow startup steps later (`_reset_hook_slate` alone measured 0.33 s; spawn→reactor measured 346 ms). The query therefore expired unread in the pty buffer and the backend fell back to its no-information defaults: **codex drew its DARK palette, and stopped tinting its panels at all, in a white terminal, in EVERY session** — the invariant above broken outright, and it also fed the agent-theme inference a screen that misrepresented the agent, so aGiTrack painted a dark canvas over a light terminal to match it. Polling between startup steps cannot fix it (the query arrives DURING one), so `_start_early_capability_service` answers from its own thread for exactly the startup window: it is the child's only reader until `_stop_early_capability_service` joins it immediately before the reactor takes over, and everything it read is handed to the normal output path there, so nothing is lost from the screen. It is also stopped in `run()`'s `finally`, so a crash between the spawn and the reactor cannot leave a second reader on the child's fd. Tests: `tests/test_agent_theme.py::test_the_backend_is_answered_before_the_reactor_starts`.
- **The terminal's own colours are the default AND the fallback ("Agent background", `renderer.py`). aGiTrack never decides on its own to repaint the user's screen.** aGiTrack paints every cell itself, and a cell the backend left at the terminal default is emitted as such — so it shows the host terminal's background, which is the terminal profile the user chose. The only override is an explicit `agent_background` of `dark`/`light`: aGiTrack then fills the unpainted cells (and its own chrome — status bar, popups — via `reset_sgr`) with that colour, AND reports that colour to the backend in place of the terminal's (`forced_canvas_osc_values`) so a self-theming agent paints to match. `agent_background` = `terminal` (default) | `dark` | `light`; `apply_agent_background` is a one-line pure function of the setting, called at startup and when the setting is saved, **and nowhere else** — not from `render`, not from a timer. That is what makes oscillation impossible rather than rare: there is no sample, no vote, no throttle and nothing read off the screen, so the background a session opens with is the background it ends with. Nothing needs adapting to in the first place, because backends that theme themselves ask the terminal what background they are on (OSC 10/11) and aGiTrack answers **truthfully** — including from the platform when the terminal itself will not answer (`host_background.py`; Apple Terminal answers no colour query at all) — so they agree with the terminal by construction. Tests: `tests/test_agent_theme.py`.
- **Never infer the agent's theme from what is on the screen. It was tried; it oscillated; it is not fixable by tuning.** aGiTrack used to read the agent's light/dark scheme off the frame — dark fills and light text meaning "this agent expects a dark background" — and repaint the terminal to match, with minimum cell counts, a 60% majority, an alphanumeric-only text signal and `CANVAS_VOTES_TO_SWITCH` agreeing samples to steady it. It read the screen's CONTENT, so the decision moved with the content: a turn that printed a code block (its own dark fill) voted dark, the prose after it voted light, and the whole background flipped every couple of seconds for as long as the session ran — reported as "the color keeps switching between light and dark, which makes the TUI unusable", with the user's own correct diagnosis: "it shows dark if the view doesn't have a code snippet, and it switches back to bright when there is". Mid-tone terminals made the other half of the rule a coin toss too: Terminal.app's `Novel` is cream (`#dfdbc3`) and `Silver Aerogel` is `#808080`, exactly the 50% the luminance comparison was against. No per-backend tuning of minimums, majorities or which glyphs count fixes this, because the input itself is what changes. Every knob it needed is gone (`agent_theme_is_dark`, `update_canvas`, the `CANVAS_*` constants, `_canvas_votes`/`_canvas_decided`, the per-backend `agent_theme_seen` memory, `_service_agent_theme`); `agent_background=auto` is gone with them and old configs holding it read as `terminal`. **When in doubt, use the terminal's colour** — and there is no case that is not "in doubt".
- **Handing stdin over must not wait out the pump's poll cycle.** `_pause_pump_and_wait` set `_paused` and waited for `_parked`, but the pump only notices when its 0.2 s `select` returns — so *every* hand-over (the startup capability round trip, every cooked-mode prompt) cost up to a full cycle. At startup that is dead time on a blank screen, and it was most of the delay before the session appeared in the agent's colours. A second self-pipe (`_pause_r`/`_pause_w`, the mirror of the reactor wake pipe) is watched alongside stdin: the pauser pokes it, the pump drains it and loops, and the top of the loop parks. The invariant is unchanged and load-bearing — when that pipe fires the pump must `continue` **without** reading stdin, or it would steal exactly the replies the round trip is waiting for. Tests: `test_handing_stdin_over_does_not_wait_out_the_pumps_poll_cycle`, `test_the_pause_pipe_never_swallows_a_keystroke`.
- **Nothing may sample the screen on a timer.** `_service_agent_theme` ran in the reactor's timers phase on EVERY tick and rebuilt + re-scanned the whole visible screen (`_visible_lines()` → a per-cell scan): measured 0.56 ms at 24x80, **2.95 ms at 50x200 and 4.20 ms at 60x240**. The `CANVAS_SAMPLE_INTERVAL` throttle did not bound it, because the throttle was gated on `_canvas_decided` and an abstaining or opinion-less session never set that — so on a terminal that answers no OSC 11 (Apple Terminal, i.e. the reporter's) it ran unthrottled for the whole session, up to ~60x a second while output flowed (`_select_timeout` returns 0.016 s whenever a render is pending), on the same thread that handles stdin. Every flip also wrote the shared `~/.agitrack/config.json` (read + merge + atomic rename) from that same phase. Both are gone: the reactor now does **no** per-tick work proportional to screen size, and `render` builds the visible screen exactly once per frame. Tests: `test_nothing_samples_the_screen_on_a_timer_any_more`, `test_a_frame_builds_the_visible_screen_exactly_once`.
- **Renderer methods that `ScreenRenderer` calls on `self` must be re-exported by `ProxyRunner`.** The runner is not a subclass — it duck-types the renderer host — so a hook it doesn't re-export (`reset_sgr`, `canvas_sgr_body`, `apply_agent_background`) makes *every* frame raise inside `_render`, which only logs "render failed": the screen silently freezes on the last good frame. Tests: `tests/test_agent_theme.py::test_the_runner_exposes_every_canvas_hook_the_renderer_calls`.
- Proxy mode commands after `Ctrl-G` (bare names, no `:`), in this order: `sessions`, `agent-backend`, `summarizer`, `git-unstaged`, `git-user-commit`, `dashboard`, `update`, `exit`. Order matters because the palette selects by typed prefix.
- Only `sessions` starts with `s`, so pressing `s`+Enter jumps straight to the session picker. Git-specific commands are grouped under a `git-` prefix.
- `sessions` opens an interactive menu of the live concurrent sessions to switch between them, start a new one (in its own worktree; under `--no-worktree` it shares the base directory instead), or stop one. Each entry shows whether the session is `running` (a turn is in flight / it produced output recently) or `idle`. Typed forms: `sessions new`, `sessions <n>` (switch to the n-th).
- **`--no-worktree` allows multiple sessions too.** `_new_session` branches on `_use_worktrees`: with worktrees it opens/creates a worktree; without, the session runs on the base tree (`worktree=None`, `repo=self.base_repo`, `state=AgitrackState(base_repo.repo)`), committing to the checked-out branch. They share the directory with no isolation (the per-turn commit captures whatever is in the tree); `_warn_parallel_no_worktree_sessions` shows a one-time caveat — raised from the TOP of `_new_session`, **before** `self.active = Session.bare()`. That ordering is load-bearing: the bare Session has no screen and no PTY, so any dialog opened after the swap renders NOTHING. The user then sees the PREVIOUS popup frozen with every key doing nothing while the runner sits blocked on an invisible modal — indistinguishable from a hang ("aGiTrack died" when creating a second `--no-worktree` session; a blind second Enter was the only way out). **Every dialog `_new_session` needs must precede the swap.** The name prompt's hint follows the mode (`_prompt_session_name`: "its own git worktree" vs "shares this directory") so it never promises a worktree that will not exist. A blank no-worktree session resets the shared base state to a fresh conversation; resuming one routes through `_stage_backend_resume`, which (for a conversation first run in a worktree) retargets the transcript's recorded cwd to the base dir via the backend's `retarget_working_dir`, so it runs in the base directory rather than the gone worktree path.
- `agent-backend` selects the agent backend (`opencode` or `claude`); with no argument it shows a picker. Switching relaunches the backend TUI, restores that backend's previous session for the repo if known, and updates the saved global default.
- `git-status` shows Git status; `git-stage` reviews/stages untracked files; `git-unstaged` shows intentionally unstaged files; `git-user-commit` creates a user commit.
- `dashboard` serves the metrics dashboard (`agitrack/metrics` `build_server`) as a **separate background process**, not an in-process thread (#110) — so recomputing metrics from `git log` on every poll charges its CPU/IO/energy to that child, not the TUI. `agitrack/metrics/daemon.py` owns the lifecycle: the launcher spawns `agitrack --dashboard-serve --dashboard-owner-pid <pid>` (detached via `start_new_session`), the child binds its port and publishes a handshake file (`<repo>/.agitrack/dashboard.json`, atomic write), and the launcher reads it back (`wait_for_handshake`, correlated on the child pid) to learn the URL. The dashboard is **killed when its owner exits** by two mechanisms: the owner terminates it explicitly (the TUI's `_stop_dashboard()` in the `run()` finally; `agitrack -d stop`), and the child runs an owner-death watchdog (`_watch_owner`, `pid_alive` poll every `_OWNER_POLL_SECONDS`) that shuts the server down if the owner pid vanishes — covering a SIGKILL of the owner where no explicit stop runs. For the Ctrl-G dashboard the owner is the TUI process (`os.getpid()`); for `agitrack -d` it is the **launching shell** (`os.getppid()`), so it dies when that terminal closes. CLI verbs: bare `-d`/`-d html` start (or reuse) the background daemon and return to the prompt; `-d stop` / `-d status` manage it; `-d text` is still a one-shot foreground report. The browser is opened only when it would land on THIS machine: `metrics.server.browser_is_local()`/`open_dashboard_in_browser()` skip opening on a remote/SSH/Mosh/headless host (honoring `$BROWSER`), and `remote_browser_hint()` tells the user to use the forwarded URL. The launcher passes `_dashboard_email_logins()` (current user's git email → GitHub login) into the child via the `AGITRACK_DASHBOARD_EMAIL_LOGINS` env var → `build_server(..., email_logins=)` so the session's fresh, unpushed commits — which `gh` can't map until they're on the remote — still show the user's GitHub ID. The VSCode extension also exposes `agitrack -d` as an "Open Dashboard" command (VSCode forwards the port to the local browser).
- **Dashboard by-backend / by-model exclude non-informative labels.** `Dashboard.group_by` (`agitrack/metrics/collect.py`) omits a turn whose backend/model is not a real value rather than bucketing it under "unknown"/"<synthetic>". Two layers: (1) the metadata is normalized at parse — `_build_stat`/`_constituent` run `backend`/`model` through `_real_metadata_label`, which maps the writer's "unknown" placeholder (`commits/message.py` writes `model: {model or 'unknown'}`) and Claude's `<synthetic>` marker to `None`; (2) `group_by` then simply skips falsy labels. The root cause of `<synthetic>` is fixed at the source too: `<synthetic>` is the literal model Claude Code stamps on synthetic (non-LLM) assistant messages (compaction/interrupt markers), so the transcript parser (`transcripts/claude.py`, `SYNTHETIC_MODEL`) and the headless `_model()` selection (`backends/claude.py`) refuse to let it become the turn's model — the real model is kept. The parse-time normalization still scrubs already-committed history that recorded the placeholder before this fix.
- Closing the terminal (SIGHUP/SIGTERM — the VSCode/SSH/Mosh terminal closed, including a system restart) runs `_handle_exit_signal`, which now best-effort `_finalize_pending_work()` (suppressing render by nulling `self.screen`, fully guarded) before teardown, so a just-completed turn is committed/integrated rather than stranded. The VSCode extension opens sessions as editor-area terminals so VSCode's `confirmOnKill` prompts before the close.
- **A busy resumed session forks instead of crash-looping; other launch failures are surfaced (#114).** aGiTrack resumes the last claude session by default. When that session is still held by a running background agent, `claude` refuses to attach and exits, printing a message containing "running as a background agent"/"--fork-session". In proxy mode that error lands on the alt-screen, which teardown discards, so without handling the runner just crash-loops (`_relaunch_backend_or_exit` relaunches up to 3×) and exits with a silent flash. Fix (from PR #115): `_relaunch_backend_or_exit` first checks `_should_fork_after_busy_exit()` — claude backend, a recorded `backend_session_id`, that message in `last_child_output_sample` (`_FORK_HINT_RE`), and not already forked — and if so sets `_fork_next_spawn` and re-spawns **once** with `--fork-session` (claude's own remedy: branch off a copy, leaving the busy agent untouched). `_spawn` snapshots existing session ids when forking so the new id is discovered/adopted on the first parse, exactly like a backend that assigns its own id; `_forked_for_busy` guards against re-forking, so a fork that also dies falls through to the normal crash-loop guard. As a safety net for cases forking doesn't cover (other backends, other launch failures), the crash-loop bail builds `_backend_exit_notice` via `_format_backend_exit_notice()` (the backend's last readable output + how to get unstuck, e.g. `--new-session`), which `run()` prints on the restored host screen instead of leaving only a flash. `spawn_command` gains a `fork` parameter on all backends (claude appends `--fork-session`; opencode accepts and ignores it — no fork concept).
- **Forced-exit prompt (host terminal closed mid-work).** Because the TUI is already gone when SIGHUP/SIGTERM arrives, the user can't be asked anything *inside* the terminal, so `_handle_exit_signal` surfaces a blocking confirmation through the OS window server instead — but only when the close interrupted live work. It captures `_had_unfinalized_work()` (agent turn in flight, a background session running, or any tracked tree dirty) **before** finalizing (which commits that work away), then after teardown calls `_prompt_forced_exit()`. That delegates to `agitrack/proxy/host_prompt.py`: `can_show_dialog()` gates on macOS + `osascript` (SSH/headless/Linux stay silent and fast — no window server), and `confirm_forced_exit()` runs an `osascript display dialog` with a "Reopen aGiTrack"/"Quit aGiTrack" choice and `giving up after 25`, so a system restart is never blocked or hung (timeout/dismissal/any error ⇒ `QUIT`). "Reopen" sets `_reopen_after_exit`; once `run()`'s teardown has released the management lock, `_reopen_in_new_window()` opens a fresh Terminal window running `python -m agitrack <argv>` in the repo root (so the last session auto-resumes). Everything here is best-effort and guarded — a clean close, or any platform without a GUI, exits exactly as before.
- **GitHub sign-in from the VSCode extension.** aGiTrack uses `gh` for the dashboard's committer identities and session sharing, and its TUI warns when `gh` is unauthenticated and says to run `gh auth login` — but its full-screen TUI owns the terminal, so there is no shell prompt to run that in, and a GUI-launched VSCode's terminal child often can't read `gh`'s credentials at all (e.g. a token in the macOS Keychain), so the user gets stuck with no way to authenticate. The extension (`editors/vscode/`) must therefore provide a way to sign in: a `agitrack.ghLogin` command ("Sign in to GitHub (gh)") opens a plain terminal running `gh auth login` (run in the shell so `gh` resolves from the user's real PATH and writes credentials that environment can read), and after a session launches `maybePromptGithubSignIn` shows a one-click "Sign in to GitHub" notification **only** when it is actionable — `gh` installed but unauthenticated (strict `gh auth status` exit-code check, mirroring the CLI's `gh_status()`), the repo has a GitHub remote, the user hasn't permanently dismissed it, and it hasn't already prompted this activation. Pure decision logic lives in `editors/vscode/src/github.ts` (`shouldPromptGithubSignIn`, `hasGithubRemoteUrl`) with tests in `github.test.ts`; the terminal/notification plumbing is in `extension.ts`. Backend-agnostic (it concerns `gh`, not claude/opencode).
- **Startup gh-availability prompt (before the TUI).** Because aGiTrack's full-screen TUI takes over the terminal, the gh warning must be surfaced *before* it starts, while stdin is still an ordinary shell. `cli._check_gh_availability(repo)` runs right after the privacy acknowledgment (proxy mode only, not json/bridge): when `gh` is missing or unauthenticated (strict `gh_status()`) **and** the repo has a GitHub remote (`commit_url_base` non-empty — gh only matters there), it prints why gh matters and prompts the user to **log in now** (`'l'` → `gh auth login` runs inline in the still-cooked terminal), **continue without it** (Enter), or **quit** (`q`). It returns `(proceed, handled)`: `proceed=False` only on quit (caller aborts startup, releasing the lock); `handled=True` whenever the prompt was shown, which is threaded to `ProxyRunner(gh_prechecked=…)` so `run()` skips its background in-TUI gh notice (no double-nag). Never blocks automation: without an interactive TTY, or in scripted mode, it does nothing and returns `(True, False)` (the in-TUI transient notice still applies). Drains injected input first (like the privacy ack) so a stray newline can't auto-answer. This is the CLI half of the GitHub sign-in story; the VSCode-extension command/notification above is the other half.
- `exit` exits (with confirmation; finalizes pending commits first).
- **Startup menu-key conflict check + pre-TUI key test (before the TUI).** The aGiTrack menu key (default Ctrl-G) can be claimed by the host editor/terminal — notably VS Code binds Ctrl-G to "Go to Line" — so it never reaches aGiTrack; once the full-screen TUI starts there is no way to open the menu if its key doesn't work. `cli._verify_menu_key(config)` runs right after the gh check (interactive proxy launches only): `settings.detect_menu_key_conflict(key, env)` flags known host conflicts (conservative — currently VS Code + Ctrl-G via `host_is_vscode`), and when one is found (and not already acknowledged for this key) it lets the user **[t] test** the key, **[c] choose a different one** (with `suggest_menu_keys` offering rarely-grabbed letters), **[Enter] keep it**, or **[q] quit**. The **test is authoritative**: `_read_menu_key_press` puts the terminal in raw mode and waits for the exact bytes (`settings.menu_key_bytes_for`) the TUI matches against stdin — True if they arrive, False on timeout (the host swallowed the key), None if cancelled/no-tty; a key intercepted by VS Code simply never arrives, so the test fails exactly when the TUI would. A chosen key is persisted as `menu_key` (global) and the resolved key is stored as `menu_key_acknowledged` so the next launch stays quiet. Never blocks automation (no-TTY/scripted ⇒ returns True silently). The pure, testable helpers live in `agitrack/config/settings.py` (`normalize_menu_key`, `menu_key_label_for`, `menu_key_bytes_for`, `menu_key_is_shift`, `host_is_vscode`, `detect_menu_key_conflict`, `suggest_menu_keys`); the `GlobalConfig` menu-key properties delegate to them. Backend-agnostic.
- **Startup privacy warning wraps to the terminal.** The acknowledgment warning is stored as one flowing paragraph (`_PRIVACY_WARNING_TEXT`) and rendered through `_privacy_warning(width)`, which wraps at the authored width (`_PRIVACY_WARNING_WIDTH`, 73) on a normal/wide terminal but **re-wraps at the terminal's actual width when it is narrower**, so the line breaks land differently and the text never overflows or is chopped mid-word on a small terminal. Width defaults to `shutil.get_terminal_size().columns`; a leading blank line is preserved. On wide terminals the line breaks are identical to the previous hand-wrapped message.

## OpenCode Backend

- Use the OpenCode CLI, initially through `opencode run --format json`.
- Proxy mode uses the native OpenCode TUI and recovers metadata through `opencode session list --format json` and `opencode export`.
- Parse the final response, backend session ID, and model when available.
- Preserve only the final response in commit messages.

## Claude Backend

- Use the Claude Code CLI: proxy mode launches the native `claude` TUI; JSON mode uses `claude -p <prompt> --output-format json`.
- Proxy mode starts a fresh session with an explicit `claude --session-id <uuid>` so aGiTrack knows which transcript to read, and continues an existing session with `claude --resume <id>`.
- Recover metadata by reading the session transcript JSONL under `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl` (override the base directory with `CLAUDE_CONFIG_DIR`); the project directory name is the absolute working directory with every non-alphanumeric character replaced by a dash.
- Parse turns into user prompts and final assistant text responses; exclude thinking blocks, tool calls, tool results, sidechain (subagent) messages, and slash-command artifacts.
- Map Claude token usage (input/output/cache-read/cache-creation) onto the shared token model; reasoning/thinking tokens are not reported separately.

## Codex Backend

- Use the OpenAI Codex CLI: proxy mode launches the native `codex` TUI (`codex -C <dir>`, resume via the `codex resume <id>` **subcommand**); headless/JSON mode uses `codex exec --json` (and `codex exec [OPTIONS] resume <id> <prompt>` — the options must precede the `resume` subcommand or the CLI rejects them).
- Codex stores each conversation **twice**: an append-only rollout JSONL at `~/.codex/sessions/<YYYY>/<MM>/<DD>/rollout-<stamp>-<uuid>.jsonl` (the source of truth; `CODEX_HOME` overrides the root) and a SQLite index (`~/.codex/state_<n>.sqlite`, table `threads`) mapping id → rollout path / cwd / model / last activity. aGiTrack treats the db as an INDEX ONLY, opens it `immutable=1` (never lock the store a live Codex is writing), and falls back to a filesystem scan for every query — so a schema bump degrades to "slower", never "broken".
- A resume **appends to the same rollout file and keeps the same id** (verified live), like Claude and unlike OpenCode. That makes the rollout mtime a true per-session liveness signal, so `session_transcript_path` works for turn-end detection.
- Turn boundaries are Codex's own `task_started` / `task_complete` events (a shared `turn_id`) — a boundary the backend *declares*, not one aGiTrack infers from idleness. A trailing turn with no `task_complete` is `complete=False`.
- Token mapping needs two conversions, both verified against live counters: `input_tokens` **includes** `cached_input_tokens`, and `output_tokens` **includes** `reasoning_output_tokens`. aGiTrack subtracts each back out so `input` means fresh input and `output`/`reasoning` don't overlap.
- File edits come from `patch_apply_end`, which is better evidence than the other backends' tool ARGUMENTS — it is what actually landed. Note the shape depends on the kind: an `add` carries whole-file `content`, an `update` carries a `unified_diff`. Reading only the diff silently recorded zero edits for every new file.
- Sub-agents (`spawn_agent`, the stable `multi_agent` feature) run as their **own threads with their own rollout files**, so their tokens are absent from the parent's counters. Child ids come from `wait_agent`'s `targets`, the db's `thread_spawn_edges`, and — the only source that works mid-session — the spawn's own return value `{"agent_id":…}` in the parent's rollout; the agent's name is `threads.agent_nickname`. A sub-agent's rollout is marked `thread_source: "subagent"` and must be excluded from session listings — it is usually the newest file for the cwd and would otherwise be adopted as "the session" on restart. `spawn_agent` is ASYNC and `wait_agent` optional, so a sub-agent routinely outlives the turn that launched it — see § "Async sub-agents: the turn is not over when the reply lands".
- A child rollout's `session_meta.session_id` is the **parent's** id; the id in the FILE NAME is authoritative.

## Backend Differences (gotchas)

**Claude, Codex and OpenCode have genuinely different mechanisms** (CLI flags, session storage, resume semantics, self-update, headless I/O). A feature that works on one can silently no-op or break on another — most of the gotchas below were exactly that. So **every feature must work on ALL THREE backends**, and that must be **verified by actually invoking each backend with the feature** (a real `claude`/`codex`/`opencode` run, not just unit tests with a mocked backend) before considering it done. Unit tests that stub the backend prove the wiring, not that the real CLI behaves as assumed.

Non-obvious places where the backends diverge. Each has caused a real bug; keep them in mind when touching any backend.

- **Codex: sandboxes don't nest.** Codex wraps each command it runs in macOS `sandbox-exec`, and aGiTrack wraps the whole backend in `sandbox-exec` to confine writes to the worktree. Seatbelt cannot nest, so with both on every filesystem probe failed, Codex escalated to asking the user to approve each command, and the turn produced **no edit at all** (observed live). `ProxyRunner._relax_nested_backend_sandbox` therefore appends `-c sandbox_mode="danger-full-access"` to the codex command **only when aGiTrack's own confinement is actually active** (`sandbox.will_confine`) — the outer sandbox is the stricter of the two and stays fully in force. Same family of problem as the Homebrew nesting issue below.
- **Codex: no way to APPEND to the system prompt.** `experimental_instructions_file` REPLACES the agent prompt (it is the only lever; `base_instructions` is not a settable key — `--strict-config` rejects it). Great for bare/summarizer runs, where replacing the coding-agent persona is exactly what's wanted and cut a live summary from 40,837 to 8,284 input tokens. Useless for the commit-guidance note, which must therefore **not** be sent on Codex (using it would delete Codex's own instructions).
- **Codex: `exec` reads stdin.** `codex exec` folds a piped stdin into the prompt as a `<stdin>` block. aGiTrack's stdin is the user's terminal, so the headless backend must pass `stdin=DEVNULL` or the summarizer blocks forever waiting on EOF and the agent eats the host's keystrokes.
- **Codex: per-directory trust prompt.** Codex asks "Do you trust the contents of this directory?" for any new directory, and every aGiTrack worktree is new. `transcripts/codex.trust_args` propagates the **already-granted** trust of the base repo onto the worktree (`-c projects."<path>".trust_level="trusted"`) and does nothing otherwise — it never invents a grant the user didn't make.
- **Codex: `minimal` reasoning effort can be rejected.** The API returns HTTP 400 ("The following tools cannot be used with reasoning.effort 'minimal': web_search") whenever web_search is attached, and web_search is not one of the features `--disable` can remove. Bare runs use `low`, the cheapest effort that is always accepted.

- **System prompt / bare (summarizer) runs.** Claude takes the summarizer's task instruction via `--system-prompt` and strips tools/memory/MCP for bare runs. **OpenCode `run` ignores `system_prompt`** (no flag to replace its system prompt or drop tools), so the instruction must be **folded into the prompt positional** for OpenCode — otherwise it never learns to summarize and the result is rejected by the echo/usability guards.
- **Resume working directory.** OpenCode records a per-session `directory` and on `--session <id>` resume **restores that recorded directory, ignoring the launch path / positional `project` arg**. A session whose dir moved (repo renamed, old worktree) resumes *outside* the worktree. Fix: retarget the session's recorded dir before spawn — `OpenCodeProxyAgent.retarget_working_dir` exports (unsanitized) and re-imports with the worktree as cwd; `opencode import` retargets dir to the import cwd and **overwrites the same id (no duplicate)**. Claude instead records cwd in its transcript (`retarget_session_cwd`). **Both resume paths must stage**: the multi-session path stages via `_new_session`, and the startup resume (`run()` → `_spawn()`) must call `_stage_backend_resume` itself, or the most common "resume my previous session" case is missed.
- **Self-update on macOS.** Codex self-updates with `codex update`, writing under `~/.codex/packages/standalone/releases/<version>/` and repointing the `~/.local/bin/codex` launcher — both carved out of the sandbox in `agent_writable_dirs()`. A Homebrew-installed OpenCode self-updates via `brew upgrade`, which runs Homebrew's own `sandbox-exec` — and **macOS forbids nesting `sandbox-exec`**, so it can never work inside aGiTrack's sandbox. There is **no env escape** (no `HOMEBREW_NO_SANDBOX` for macOS formula builds; `HOMEBREW_AVOID_NESTED_SANDBOXING` hard-errors at the default `/opt/homebrew` prefix). aGiTrack therefore drives the update itself from its **unconfined proxy** for a brew-managed backend on macOS — **regardless of the sandbox toggle** (sandboxed: the backend can't; unsandboxed: it only nags with a prompt), and sets `OPENCODE_DISABLE_AUTOUPDATE` on the backend child to suppress OpenCode's own (redundant/failing) prompt. Claude's native install self-updates fine (writes to `~/.claude`, no `sandbox-exec`).
- **Update command quirks.** `claude update` / `opencode upgrade`. `opencode upgrade` **exits 0 even when its brew step failed** — judge success by comparing CLI version before/after, not the exit code. Don't pre-gate on `brew outdated`: its local tap is stale until `brew update`, and it prints the **tap-qualified** name (e.g. `anomalyco/tap/opencode`, not bare `opencode`).
- **Session ids & store.** Codex assigns its own ids too (`new_session_id()` → None; time-ordered UUIDv7, discovered after the run — its CLI has no flag to pin one) but, unlike OpenCode, keeps a readable per-session file. OpenCode assigns its own ids (`new_session_id()` → None; discovered after the run via a pre-spawn snapshot; ids are `ses_`-prefixed) and keeps sessions in a global DB (not plain files): `opencode export <id>` is global by id, `opencode session list --format json` is global (aGiTrack filters by `directory`), `opencode session delete <id>` exists. Claude forks a **new id on `--resume`**.
- **Headless process model.** OpenCode `run` streams JSON events via `Popen` and reads to EOF (a plain `timeout=` won't interrupt a stalled read — needs a watchdog that kills the process). Claude uses a blocking `subprocess.run` (add `timeout=` directly). Both summarizer paths need a timeout, or a hung call wedges the per-session one-at-a-time summary queue.

## Adding a New Backend (checklist)

A backend is more than a CLI wrapper — it shares the host terminal and the reactor with whatever ran before it, and **switching backends at runtime is a first-class case** (Ctrl-O → agent-backend). Most subtle bugs come from state or terminal modes that belong to one backend leaking into the next. Work through this list; verify on a real run of **every** existing backend plus the new one, proxy AND headless, on each platform touched (a mocked-backend unit test proves wiring, not behavior).

**Register it in the two registries, and nowhere else.** `backends/proxy_agents._AGENTS` (the TUI/transcript side) and `agitrack.backends._registry` (the headless `run()` side, reached via `make_backend`/`backend_class`/`backend_name`). Everything else — the `--backend` choices, the first-run picker, the Settings menu, the learn/story engine pickers, shell mode's `BACKENDS` — reads one of those, so a registered backend appears everywhere at once. The Codex work removed four copies of `OpenCodeBackend if state.backend == "opencode" else ClaudeBackend`; that ternary is not just repetitive, it silently routes any *third* backend to Claude, so a Codex session would have summarized itself by shelling out to `claude`. If you find yourself adding a backend name to an `if`, check whether a registry lookup belongs there instead. Genuine per-backend DATA tables still need an entry: `backends/setup._BACKEND_INSTALL`, `cli._BACKEND_COMMANDS`, `cli._RESERVED_PASSTHROUGH`, `proxy/sandbox._BACKEND_EXES`, `git/repo._NEVER_STAGE_PREFIXES`, `summaries/model_select`.

**State ownership — per-session vs. shared.** This is the rule that prevents cross-backend leakage:

- **Per-session (auto-isolated): put it in `Session.FIELDS` (`session.py`), with a default in `Session.bare()`.** Every per-turn / per-input / per-view field (`agent_in_flight`, the parse/commit trackers, `passthrough_prompt`/`passthrough_escape`, `pending_forwarded`/`pending_prompt_text`, `child_mouse`, `scroll_back`, `last_status`, selection state, …) lives there and is read as `runner.X` through the property layer. `_new_session` does `self.active = Session.bare()` and `_switch_active` swaps `self.active`, so any FIELDS state starts clean for the incoming backend automatically. **Never add new per-backend state as a bare `self.X` on the runner** — that's process-global and WILL bleed across a switch. (`_restart_agent`, the no-worktree restart-in-place path, additionally calls `_reset_agent_tracking` because it reuses the same `Session` rather than creating a bare one.)
- **Shared / process-global (the real carryover surface): the host terminal.** There is one console for the whole process, so its state is NOT per-session and a switch does not reset it for free:
  - **Raw/cooked mode, code pages, the saved-mode snapshot** — `_winconsole.RawConsole`. Its `enter()`/`leave()` are idempotent on purpose (see Native Windows); don't reintroduce per-call flushing/re-saving.
  - **Mouse reporting + ownership.** aGiTrack renders the screen itself (pyte), so the host never sees a backend's mode switches unless `_sync_terminal_modes` mirrors them, and `_enable_host_mouse` (re-)asserts host wheel reporting on spawn/switch. `child_mouse` (per-session, detected from the backend's `?1000/1002/1003h` output) decides whether a wheel event is forwarded to the backend or kept by aGiTrack for scrollback. A new backend that uses mouse differently (or not at all) must be handled in `_sync_terminal_modes`; if a switch leaves the host asserting mouse the new backend didn't ask for, its codes can leak into the prompt as literal text. **On Windows aGiTrack forwards all mouse (button/wheel/click/motion) + focus to the backend, the same as POSIX** — full pass-through, no Windows special-casing in `_sync_terminal_modes`. Motion (1002/1003) is mirrored too: the backend needs it for drag-select / copy. A deterministic ConPTY harness (`devtools/winmouse/`, run via `Start-Process` — the non-interactive agent shells can't give a ConPTY child a real console) proved conhost passes clean SGR mouse and focus events through to a VT-input backend verbatim, and end-to-end injection into live claude/opencode confirmed no leak; **a single backend works fully (mouse, scroll, copy).** **Neither backend uses win32-input-mode** — the `\x1b[?9001h` in their output is conhost's unconditional startup emission, not the backend, so encoding input as win32-input-mode would fix nothing. See `devtools/winmouse/FINDINGS.md`. **Open issue:** *switching* backends (e.g. Claude→OpenCode) leaks mouse codes and corrupts keyboard input (phantom char on Enter, Ctrl-C stops working) — process-global host/terminal state carried over from the first backend that the second doesn't reset; under investigation (a single backend is unaffected). On exit, `_finalize_pending_work` disables host terminal modes up front so a scroll during the (cooked, stdin-unserviced) "Finalizing…" teardown can't echo its raw report.
  - **Mirrored DEC modes** generally — bracketed paste (`?2004`), alt-screen (`?1049`), synchronized output (`?2026`), kitty keyboard — are tracked in `_sync_terminal_modes`. A new backend's mode requests must be recognized there or the host and the backend disagree about terminal state after a switch.

**Launch & process model.**

- Resolve the executable through `which_executable` (Windows: PATHEXT-aware, `.exe`/`.cmd`/`.bat`/`.com` only); a `.cmd`/`.bat` npm shim must run via `cmd.exe /c` for ConPTY. See the four `_conpty.py` invariants in Native Windows — all four broke a real launch.
- **No Ctrl-C may reach the backend during startup.** A false backend-exit (e.g. the reader thread raising on normal output) triggers a relaunch whose teardown `interrupt()` sends Ctrl-C; the result is the "exited repeatedly on launch" loop. The reader must never raise on well-formed output.
- Headless: give the run a real timeout/watchdog (see Backend Differences); `system_prompt` handling, session-id assignment, and resume-cwd semantics differ per backend (also above).

**Input handling caveat (open issue).** The wait-with-cancel loops (`_read_stdin(32)` while a fetch/parse/export thread runs) read stdin only to detect Ctrl-C/Esc and **discard** anything else, so keystrokes typed while such a wait is active are dropped rather than forwarded to the backend. This is the **suspected** cause of an observed bug: the first burst of keystrokes typed right after a Claude→OpenCode switch in worktree mode is lost (`switchtest…` → `s     st…`), and adding any per-character latency makes it disappear — i.e. it's a throughput race against a background operation, not a state-carryover bug (session state is correctly reset). The fix is to buffer non-cancel input and replay it to the backend once the wait ends rather than discarding it; it still needs a reliable repro to confirm the exact loop and verify the fix.

## Session Tracking

- aGiTrack tracks exactly one backend session per repository and pins to the session it launched, rather than chasing whichever session is globally newest.
- For backends that accept an explicit session id (Claude), aGiTrack pins at launch. For backends that assign their own id (OpenCode), aGiTrack adopts the newly created one on the first parse. Either way it then FOLLOWS the conversation the user is actually driving — see the snapshot rules below.
- **Following an in-backend switch (all modes).** When the user starts/resumes a different conversation *inside* the backend, aGiTrack follows it: worktree mode via `backend.latest_session_id` (the worktree dir is unique to the session), no-worktree mode via snapshot-based discovery (`_discover_spawned_session`), background mode via `latest_session_id` each cycle. Combined with the per-conversation watermark (see the token exactness note), switching back and forth counts each conversation's turns exactly once.
- **The pre-spawn snapshot is `{id: updated}`, is taken on EVERY spawn, and both halves matter.** `_spawn` records what existed and *how recently each was written*; `_discover_spawned_session` then adopts the most recently written session that has moved **since launch**. That covers the two shapes a native session switch takes, and neither is optional:
  - **onto a NEW conversation** — Claude `/clear`, OpenCode `/new`: an id absent from the snapshot. (Verified against the real Claude CLI: `/clear` writes a brand-new transcript under a new id the instant it runs, before the next prompt.)
  - **BACK onto an EXISTING one** — Claude `/resume`, OpenCode's switcher / `run --session <id>`: the id **is** in the snapshot, so an id-only snapshot can never see it; only a moved mtime can. (Verified against the real OpenCode CLI: resuming an older session advances its `updated` past the newer one's.)

  "Since launch" is the safety property — a directory can hold conversations belonging to something else entirely, and those are exactly the ones nobody has written to, so they can never be adopted however recent they look. Use `>` not `>=` or an untouched session compares equal and leaks back in.
- **Never skip that snapshot.** It used to be skipped in the two most ordinary cases — Claude pins its id up front, and every relaunch is a resume — which left `_discover_spawned_session` returning `None` and the parse falling back to the pinned id **forever**. Everything after a `/clear` was recorded against the conversation the user had just thrown away: no prompts, no tokens, no trace. Taking it unconditionally is also strictly *safer* than skipping it, since the snapshot is the very thing that excludes unrelated sessions. Tests: `tests/test_proxy.py::test_every_spawn_snapshots_the_sessions_that_existed_first`, `::test_switching_BACK_to_an_existing_conversation_is_followed`, `::test_an_untouched_conversation_is_never_adopted_however_recent`.
- **Detecting the switch is not the same as KEEPING it — three things must all hold.** Discovery alone left the reported bug in place:
  1. `_discover_spawned_session` finds the new conversation (the snapshot rules above).
  2. `finish_parse_if_ready` must adopt it **even when the export is empty**. `/clear` writes its transcript instantly but leaves it with no turns until the first prompt, so `exported_session` is falsy and the early return threw the adoption away. Only the pin moves on that path; nothing is recorded, and the per-conversation watermark keeps it safe.
  3. **Startup must re-check the pin** (`_resync_pin_to_the_live_conversation`, called before `_stage_backend_resume`). In-session discovery only runs when a turn COMPLETES, so `/clear` followed by a quit before typing never reaches it — and the next launch resumed the discarded conversation and applied the new session's name to it. Startup asks once what worktree/background mode ask continuously: what is the newest human conversation in this directory? A pin the directory's listing does not know (worktree, renamed repo) is left to the retargeting path.
- **A fix here cannot be tested by the running aGiTrack.** It is an editable install, so the source on disk is the source of truth, but Python loaded the modules at process start: the live session keeps running the OLD code until it is fully RESTARTED (see [[running-agitrack-is-editable-needs-restart]]). A "still broken" report right after a change is this, until proven otherwise.
- **Verifying this needs real transcripts, not a TUI harness.** Driving the interactive proxy through a pty to reach `/clear` is unreliable (startup notices swallow the first prompt; a stray Escape kills the backend — three attempts, three harness failures). What works: run the *backend* CLI in a temp dir to produce a genuine pre/post-switch pair of transcripts, then point `_discover_spawned_session` at that directory with a snapshot representing "the world at launch". That exercises the real backend `list_sessions`, real transcripts and the real discovery code, in seconds.
- The `session` command (proxy) lets the user start a new session, switch the tracked session to another existing one, or sync tracking to the most recently active session (useful after starting a new session inside the backend TUI). Switching or starting a new session relaunches the backend TUI and re-baselines so existing history is not re-committed.
- Session detection, listing, and switching must work identically for both OpenCode and Claude.
- Shared-session conflicts (two contributors pushing the same session concurrently) are resolved by a best-effort **union merge** of the diverged copies rather than silent last-write-wins: `merge_transcripts` keeps the shared prefix and appends each side's unique rows by id (Claude JSONL; OpenCode's single-object export isn't line-mergeable, so it falls back to last-write-wins). **Before a merged transcript is uploaded** it must pass `_transcript_is_readable(text, backend)` — the backend's own parser (`parse_rows` / `parse_exported_session`) must still yield ≥1 turn — or the merge is discarded and last-write-wins is used, so a corrupt merge is never pushed. This runs in `store._add_and_push` before the push, for both backends.
- **Sharing onto a newer shared copy (overwrite).** The recency guard (`_would_regress`) normally refuses to replace a longer shared copy with a shorter one (`PublishResult.behind=True`) so a stale machine can't rewind everyone's copy. When a *manual* share is refused this way, the user is asked whether to overwrite it: `_share_session`'s background outcome stashes the refusal in `_pending_share_conflicts`, and `_service_share_conflicts` (a main-loop tick run AFTER `_service_background_share_ops`, so it never mutates that list mid-iteration) pops a prompt via `_resolve_share_behind`. Choosing overwrite re-shares with `store.publish(..., overwrite=True)`, which syncs the remote first (so the lease matches), then **skips both the union merge and the recency guard** to replace the shared copy wholesale. Only overwrite-or-keep is offered, by design: copies that CAN be combined are union-merged automatically during a normal publish (the superset never trips `behind`), so the only sessions reaching this refusal are non-mergeable (OpenCode) ones where replace-or-keep is the real choice. Auto-share never overwrites — it stays conservative and just refuses to regress.

## Concurrency and Locking

- Only one aGiTrack process may auto-commit/merge in a given working tree at a time. A process acquires a single-writer lock at `<tree>/.agitrack/lock`, released the instant the owner dies: an `fcntl.flock` on POSIX, an `msvcrt.locking` byte-range lock on native Windows (`agitrack/git/lock.py` picks the primitive by `sys.platform`; the Windows lock sits on a byte far past the pid JSON so a reader — e.g. the VS Code extension — can still read it). A second aGiTrack process on the same repo **refuses to start**: it prints `already_running_message` (which names the holding PID and tells the user to stop it first) and exits non-zero. Wired into both proxy and JSON modes.
- Quitting a proxy instance asks for confirmation before exiting.
- Concurrent sessions are isolated with git worktrees so changes are never attributed to the wrong session; see Concurrent Sessions below.
- **Idle low-power loop (battery).** The reactor's `select` timeout is set by `_select_timeout()` to "time until the next thing must happen", never a fixed busy-poll: `ACTIVE_POLL_SECONDS` (a coarse **1s** — every background sweep already self-throttles to its own interval, ≥2s, so polling faster buys nothing) while there is work to service, backing off to `IDLE_POLL_SECONDS` (`timings.idle_poll_seconds`, default 30s) once `_is_idle()` is true — no turn in flight (active or background), no pending per-turn pipeline work (file-change event, parse/commit, deferred Enter/queued prompt), no live worker thread, no timed notice on screen, and no keystroke or backend output for `timings.idle_after_seconds` (default 30s). Two sub-second exceptions: a queued repaint flushes at `0.016` (the coalesced-output frame), and a deferred prompt-submit (`_pending_enter_at`, scheduled 0.4s out) collapses the timeout to its exact remaining time so the injected Enter isn't stretched to a full second. `select` watches stdin **and every session's PTY** (active + all background fds), so it returns the instant the user types or **any** session — foreground or background — emits output; idle ends with no lag and commit/integration timers resume immediately. Waking is unavoidable for readable fds, but only a **real keystroke** resets the idle backoff: `_reactor_stdin_phase` gates `last_user_input` on `_is_real_keypress(data)`, so a mouse wheel / move / click or a focus report wakes us just long enough to redraw the scrolled view and then drops straight back to the low-power cadence (passive reading needs no commits or polling). Crucially, `_is_idle()` only goes true 30s after the last keystroke AND once output is quiet AND nothing is pending, so during active back-and-forth work aGiTrack never idles and every aGiTrack-triggered commit/integration runs at the active cadence — the long idle block only happens when the user has genuinely stepped away. Every deferred-commit/integration path that waits (parse thread, summary worker, `parse_pending`/`file_change_event`, background-session debounce) is itself a non-idle condition in `_is_idle()`, so a pending commit can never get stranded behind the 30s block. A sticky message (one that waits for a keypress) does **not** keep the fast loop, since the dismissing keypress wakes `select` on its own. This stops the process waking several times a second when nothing is happening — which is what made the host editor (e.g. VS Code) report aGiTrack as a significant energy user.
- **File/folder checks stay cheap.** Change detection is event-driven (watchdog `Observer`, native FSEvents/inotify) — never a tree walk; the `Observer is None` fallback is an interval-gated `git status_short()`. Session discovery globs `*.jsonl` and orders by `stat().st_mtime` (no file reads), and a session's label reads only the head of its transcript (`_session_label`, 100-line cap with an early break). Per-loop sweeps each gate on their own `*_SECONDS` interval before shelling out to git, so the 1s active poll never spawns a check more than its interval allows. The base-repo polls also **mtime-gate** their git subprocess: `_check_base_branch_drift` only runs `current_branch()` when `.git/HEAD`'s mtime moved (a checkout — not a commit), and `_poll_base_advanced` only runs `rev-parse` when the base ref / `packed-refs` mtime moved (`_newest_mtime`/`_base_git_dir`), so a steady repo costs a couple of `stat()`s per tick, not a `git` fork.
- **The git pipeline runs on a dedicated worker thread — never the main thread.** The foreground session's automatic `git status`/commit/merge runs in `_git_worker` (`_git_worker_loop` → `_run_git_pipeline`, started in `run()`), so a git subprocess can **never** block the reactor thread that echoes the user's keystrokes — typing is always instant, even right after an edit. The worker sleeps on `_git_wake` (set by the file watcher on a worktree write, and once per reactor tick) and backs off to the idle cadence via `_is_idle()`. **Marshaling rule:** the worker must never touch stdin or the screen. Any dialog it raises (merge-conflict resolve, copy-file/untracked offers) goes through `_run_modal`, which when off the main thread enqueues an `_ModalRequest` on `_modal_mailbox` and blocks; the main thread presents it inline (`_drain_modal_mailbox` → `_run_modal_inline`) and returns the answer. `_render` off-thread just sets `_render_pending` (the main loop flushes it); `_set_message` only writes fields, so it is thread-safe as-is. A self-pipe (`_wake_r`/`_wake_w`, in the `select` set) lets the worker wake the reactor at once to present a dialog. PTY writes are serialized by `BackendProcess._write_lock` so a worker-injected conflict prompt can't interleave bytes with a forwarded keystroke.
- **`self.active` is single-threaded; the worker never swaps it.** The whole runner keys per-session state off one `self.active` pointer that `_with_session` temporarily swaps. To stay safe with a concurrent worker, the worker's pass operates **only on the foreground session and never swaps `self.active`** (verified: `_maybe_agent_commit`/`_maybe_complete_agent_merge`/base polls reach no `_with_session`/`_switch_active`). Background / multi-session servicing — which *does* swap `self.active` (`_service_background_sessions`, the background loops of `_service_commit_summaries`/`_sync_idle_worktrees_to_base`, and `_check_base_branch_drift`'s dir-change path, plus `_ensure_worktree_alive`'s PTY/watcher work) — **stays on the main thread**, inside `_reactor_timers_phase` under a **non-blocking** `_pipeline_lock.acquire(blocking=False)` (skip-this-tick if the worker holds it, so the reactor never stalls). The worker holds `_pipeline_lock` across its pass; user-initiated foreground swaps (`_switch_active`) and exit acquire it via `_acquire_pipeline_lock_from_main`, which **drains the modal mailbox while it waits** so a worker blocked on a dialog can't deadlock the acquirer. Exit/restart calls `_stop_git_worker` (joins, cancelling any pending dialog) *before* `_finalize_pending_work`, so exit-time commits are the only git that runs on the main thread — teardown, never the live path. Scope note: prompt-submit-time git (`_integrate_committed_turn_before_new_turn`/`_ensure_turn_branch` on Enter) and user-initiated commands (`git-user-commit`) stay inline on the main thread — they are at a keypress the user is waiting on, not the typing hot path.

## Native Windows (#118)

- aGiTrack runs natively on Windows (PowerShell / Windows Terminal), not only via WSL. The POSIX-only mechanics sit behind a platform layer so the ~9,400-line reactor stays platform-agnostic; macOS/Linux keep their exact existing path.
- **Ask about a path's SHAPE, never with `startswith("/")` (`agitrack/paths.py`).** aGiTrack reads paths it did not write — a transcript records whatever the machine it ran on used, and a shared session is read somewhere else entirely — so `is_absolute` / `under` / `relative_to` / `contains_segments` answer from the string, in either shape, case-folded on Windows. Every POSIX-only version of those questions answers a confident NO for a Windows path, which is worse than raising: `_display_path` classed every Windows path as "already relative", so a reconstruction showed `diff --git a/C:\Users\…\hello.py` AND `backtrace commit` matched no edit to any commit ("no untracked AI work to annotate" for a repo full of it), while `retarget_session_cwd` left a resumed session editing the worktree it had just been moved out of. `tests/test_paths.py` drives Windows-shaped strings on EVERY platform, which is the only way these stay fixed.
- **`SO_REUSEADDR` means the opposite thing on Windows** — "bind even if someone already has this port", not "reuse a TIME_WAIT port". So `bind_exclusively` (`metrics/server.py`) asks for `SO_EXCLUSIVEADDRUSE` there and `_DashboardServer` sets `allow_reuse_address = False` to keep socketserver from adding it back. Without this two dashboards bound 8765 together, the consecutive-port scan never stepped past a taken port, and requests landed on whichever socket the OS picked.
- **A directory's stat cannot answer "did an entry appear?" on Windows.** NTFS does not reliably bump a directory's write time when a file inside it is created, and a directory's `st_size` is 0 there, so the backtrace daemon's cheap poll compared two byte-identical signatures and never ran a fresh discovery pass: a reconstruction silently stopped keeping up with the sessions being recorded beside it. `_dir_signature` hashes the entry NAMES instead (one directory read, no per-entry stat). The test freezes the directory's mtime after adding a file, so a POSIX run reproduces the Windows behaviour.
- **A rename over an existing file is retried (`agitrack/fileio.py`).** POSIX `os.replace` always succeeds; Windows refuses it with `PermissionError`/`ERROR_ACCESS_DENIED` while ANY other handle to the DESTINATION is open without delete sharing — the other writer microseconds into its own replace, a reader loading the file, the virus scanner or indexer that woke when the tmp file appeared. All of those clear in milliseconds, so `_replace_when_allowed` waits them out (12 attempts over ~0.85s, doubling then capped) and only then raises. Without it, "several aGiTrack processes on one repo" — the setup that module exists for — crashed a save on Windows roughly once in a few hundred writes.
- **File comparisons read CONTENT, not `(size, mtime)`.** Windows' coarser file timestamps make `filecmp.cmp(shallow=True)` call two different files identical routinely, and the copy-back offer used that as proof — silently stranding a user's work in the worktree. Size first (free), then a real comparison.
- **Platform package `agitrack/proxy/platform/`.** `base.py` defines the `ChildProcess` / `HostTerminal` / `ReactorWaker` Protocols both platforms satisfy; `make_child_process` / `make_host_terminal` / `make_waker` (in `__init__`) dispatch on `os.name`. `posix.py` thinly wraps today's `BackendProcess`/`TerminalHost`/`os.pipe`; `nt.py` + `_winconsole.py` are the Windows implementations (imported only on Windows).
- **The socket-bridge insight.** Windows `select()` accepts **sockets** but not console/pipe/ConPTY handles, and `socket.socketpair()` works on Windows. So the reactor keeps its `select`-based loop: every native input source (the backend's ConPTY output, host-console stdin, the resize watcher, the worker waker) is bridged through a reader thread into one end of a `socketpair`, and the reactor selects on the other end. The fd vocabulary (`master_fd`, `stdin_fileno`, `wake_fileno`) is preserved, so the reactor changed by only a handful of identifiers (`_stdin_fileno()`/`_read_stdin()` helpers; `make_waker()`).
- **`NtChildProcess`** spawns the backend under a ConPTY using **our own raw `CreatePseudoConsole` driver (`_conpty.py`), NOT `pywinpty`** — pywinpty's ConPTY backend kills every child with `STATUS_CONTROL_C_EXIT` (`0xC000013A`) when the app is PyInstaller-frozen (the MSI), so no backend can launch from the MSI. A daemon reader copies the pseudoconsole output into the bridge socket (same back-pressure as the POSIX PTY). `_resolve_windows_command` resolves the backend via `which_executable` (PATH/PATHEXT-aware; returns only a runnable `.exe`/`.cmd`/`.bat`/`.com`, never a `.ps1` or extensionless shell shim) and wraps a `.cmd`/`.bat` (npm's `claude.cmd`) through `cmd.exe /c` — the only way ConPTY's `CreateProcess` runs a batch shim — so **both** backends launch. `interrupt()` writes ETX (Ctrl-C) to the ConPTY; `poll()` reports the child gone only after the reader thread has finished draining (so a fast child's trailing output isn't lost). **Four non-obvious `_conpty.py` invariants, each of which broke a real backend launch — keep them:** (1) read into an **unsigned `c_ubyte`** buffer — a signed `c_byte` array indexes to −128..127, so `bytes(buf[:n])` raises `bytes must be in range(0, 256)` the instant the backend emits any byte ≥ 128 (its UTF-8 TUI), which the reader catches as "child gone" → false exit → relaunch → teardown's `interrupt()` Ctrl-Cs the backend → "exited repeatedly on launch"; (2) pass the `HPCON` to `UpdateProcThreadAttribute` **by value**, not `byref` — `byref` stores the handle's address as the pseudoconsole, so the child never attaches and its output goes to the parent console (interactive: handed off to a new Windows Terminal window; headless: lost); (3) creation flags are **`EXTENDED_STARTUPINFO_PRESENT` only — do NOT add `CREATE_NO_WINDOW`**, which also breaks the attachment; (4) `bInheritHandles=FALSE` so the child takes its std handles from the pseudoconsole, not the parent's (otherwise stdout isn't a TTY and the backend drops to non-interactive mode).
- **`NtHostTerminal` + `_winconsole`** drive the Win32 console: VT raw mode via `SetConsoleMode` (`ENABLE_VIRTUAL_TERMINAL_INPUT`/`PROCESSING`, code pages set to UTF-8 / 65001 so box-drawing renders), a `ReadFile`-on-the-console reader thread feeding the stdin bridge, `GetConsoleScreenBufferInfo` for size, and a polling **resize watcher** that replaces `SIGWINCH` via `consume_resize_pending()` in the select phase. SIGWINCH/SIGHUP installs are guarded off on Windows. **`RawConsole.enter()`/`leave()` are idempotent** (guarded by an `_entered` flag): `set_raw()` can be called again while already raw (a render/resume that didn't pass through `set_cooked`), and a naive re-entry would (a) re-save the already-raw modes over the real cooked ones so `leave()` could never restore the terminal (garbled output, notably over RDP after a turn), and (b) re-`FlushConsoleInputBuffer` and discard keystrokes the user just typed. The one-time flush on a genuine cooked→raw entry is still correct (it drops input typed into a cooked-mode prompt, including a stray Ctrl-C that would otherwise launch-kill the backend).
- **Process primitives `agitrack/proc.py`** (`detach_kwargs`/`pid_alive`/`terminate_pid`) abstract `start_new_session`/`os.kill` for the dashboard daemon and self-update (`CREATE_NEW_PROCESS_GROUP|DETACHED_PROCESS|CREATE_NO_WINDOW` + Win32 `OpenProcess`/`TerminateProcess` on Windows). The repo lock uses `msvcrt` (see Concurrency). OpenCode's transcript export falls back from `pty.fork` to a `subprocess` pipe on Windows.
- **Graceful shutdown.** A closing VS Code window can't deliver a catchable signal to aGiTrack on Windows, so the extension writes `<repo>/.agitrack/shutdown`; the reactor polls it (`_check_shutdown_request`, ~1 s, in the timers phase), finalizes the turn, and exits — the cross-platform equivalent of SIGTERM (the extension also `taskkill`s as a last resort). **Confinement where the OS sandbox is unavailable (Windows, or POSIX without `bwrap`/`sandbox-exec`).** No OS filesystem sandbox, so two prompt-independent mechanisms take over, both gated on `_base_commit_guard_active()` (worktree mode + confinement on + `not sandbox.is_available()`): (1) a **base-repo `pre-commit` guard hook** (`agitrack/git/hooks.py`, installed by `ProxyRunner._install_base_commit_guard`, removed on teardown) that **hard-blocks the agent from committing into the base repo**; and (2) `_warn_if_base_edited`, which warns about uncommitted base writes. The hook attributes reliably — the only way to, since agent and user share one git identity and the user can edit/commit at any time — via the `AGITRACK_WORKTREE_GUARD` env marker set in `_backend_child_env` ONLY on the agent child in worktree mode: every `git` the agent runs inherits it, while the user's shell, agents run outside aGiTrack, and `--no-worktree` agents don't have it, so they commit freely (and a hook left behind by a crash is a no-op for them). Commits inside a linked worktree are allowed; only base/main-repo commits are rejected (detected via `git rev-parse --absolute-git-dir` containing `/worktrees/`). It chains any pre-existing `pre-commit` hook (moved to `pre-commit.agitrack-orig`, restored on removal), is skipped when `core.hooksPath` is set, is bypassable with `git commit --no-verify`, and is disabled by turning confinement off (`--no-confine`/`--no-sandbox`/`sandbox: false`). A full *filesystem* sandbox (blocking arbitrary writes, not just commits) still isn't feasible for a *same-user* child on Windows — Job Objects govern CPU/memory not ACLs; AppContainer needs per-capability SIDs and breaks Node/`git`; a restricted-token + deny-ACE scheme is heavy/fragile — so on these platforms writes are *monitored* (warned) while commits are *prevented*.
- **VS Code extension** (`editors/vscode`): native Windows is un-gated; launch uses PowerShell-aware quoting + a `$LASTEXITCODE` exit suffix (not `&& exit`); liveness uses `Get-CimInstance Win32_Process` (not `pgrep`/`ps`); install-path resolution targets `agitrack.exe` in `Scripts`/pipx dirs.
- **CI**: a dedicated `windows-latest` job (`.github/workflows/ci.yml`) runs an import smoke + a curated, platform-relevant subset (`test_proc`/`test_dashboard_daemon`/`test_shutdown_request`) and a real ConPTY spawn/read check (`test_windows_conpty`, `skipif os.name != "nt"`). Windows-only branches are kept mypy-clean via `sys.platform`-narrowing and targeted `# type: ignore` (the POSIX gate `./scripts/check.sh` stays green).

## Concurrent Sessions (worktrees + auto-integration)

This is the design aGiTrack targets for running several sessions at once. Foundations (`agitrack/git/lock.py`, `agitrack/git/worktree.py`, and the worktree/branch/merge helpers in `agitrack/git/repo.py`) are implemented and unit-tested; the multiplexer wiring in `agitrack/proxy/runner.py` is the remaining integration.

- A single aGiTrack process multiplexes several live sessions; one is displayed, the others keep running and integrating in the background.
- The main working tree / base branch is mutated only by the serialized merge coordinator; every session runs in its own worktree under `.agitrack/worktrees/<name>`.
- A session creates a transient turn branch (`agitrack/<name>/t<n>`) when it receives a prompt; on the turn's final agent message the branch is integrated into the base and deleted.
- Integration is serialized and completion-ordered. It runs inside the owning session's worktree (merge base into the turn branch) so the agent can resolve conflicts in place; aGiTrack auto-prompts the agent with the conflicting commits' context and pauses for the user if it cannot resolve.
- A `session` view shows running/idle/merging status and can stop sessions; a `base` command switches the base branch after stopping sessions and draining pending integrations; on restart aGiTrack offers recovery for stale `agitrack/*` branches and worktrees.
- The `--delay-merge` flag (`ProxyRunner._delay_merge`, off by default) holds automatic integration: after a turn commits, the in-session auto-merge paths (`_integrate_session_turn`, `_integrate_committed_turn_before_new_turn`, `_integrate_agent_made_commits_if_idle`) defer and a notice names the **working directory** (the worktree path, which the user may not otherwise know) so they can review/edit. The merge runs only on explicit confirmation via the session menu ("Merge reviewed changes into &lt;base&gt;" → `_integrate_active_session`). Exit still finalizes (`_integrate_session_on_exit` is not gated) so committed work isn't stranded, and unmerged work is surfaced again next run.
- **A user-requested merge is best-effort — it must not dead-end on uncommitted changes.** `_integrate_active_session` only refuses while a turn is GENUINELY in flight (`_agent_is_active()`, after a `_clear_agent_in_flight_if_idle()` refresh so a finished-but-not-yet-cleared turn doesn't falsely block). Otherwise it commits the worktree's committable leftovers itself (`_commit_latest_turn_sync`) and proceeds; anything still uncommitted afterward is non-committable (git-ignored / intentionally-unstaged) and simply stays in the worktree rather than aborting the merge of the committed work. The commit-before-merge lives in this one place; `_merge_active_into` just retargets the base branch and delegates here. (Earlier the guard refused on any `repo.has_changes()`, stranding the user with a misleading "finish or stop the current turn" message even when no turn was running.)
- **A session's worktree must never be stranded as an "open end" by uncommitted leftover files.** On exit (`_remove_worktree_on_exit`) a worktree is kept only for a genuine reason to preserve work: an in-progress merge (`merge_ctx` / `merge_in_progress()`), or commits still ahead of the base (`log_range`). Uncommitted leftover FILES (untracked, git-ignored, or files the user declined to stage) do NOT keep it — they are what the copy offer handles, and since a copy leaves the source in place, refusing removal on `repo.has_changes()` left dirty worktrees lingering forever even after the user copied the files out. On an interactive exit (`screen is not None`) the copy offer runs (`_offer_copy_unstaged_to_base(context="exit")`, which warns that declining discards them) and the worktree is then force-removed (`WorktreeManager.remove` already uses `force=True` with a `shutil.rmtree` fallback). The single exception is a **signal teardown** (terminal/window closed, `screen is None`): with no UI to rescue the files, a worktree that still has leftover files is KEPT so the next startup surfaces them instead of silently discarding the user's work.

## Backend Selection and Global Config

- The selected backend is stored per repository in `.agitrack/state.json`.
- A user-wide config at `~/.agitrack/config.json` (override the directory with `AGITRACK_CONFIG_DIR`) stores `default_backend`, used when a repository has no backend recorded yet.
- **Settings precedence + menu.** `GlobalConfig` carries a repo-local overlay loaded from `<repo>/.agitrack/config.json` (`load_repo_overlay`), so the effective value of any setting is **repo-local > global > built-in default** (every getter reads through `_raw`). `source(key)` reports which layer a value comes from; `set(key, value, scope=…)` / `unset(...)` write the global file or the repo file (`save_repo` preserves other keys the repo file holds, e.g. AgitrackState's). The `settings` Ctrl-G command (`ProxyRunner._settings_menu`, a declarative `_settings_specs` registry) edits **all** options — backend, sandbox, allowed_edit_paths, use_worktrees, commit_guidance, summarization, check_for_updates, menu_key, and a timings sub-menu. It is a **form**: each edit picks its own scope ("Apply to: This repository / Global") and is held as a **pending** change in `_settings_pending` / `_settings_pending_timings` (shown as `· UNSAVED → scope`); pending edits are written only when the user **confirms save on close** (`_confirm_save_pending` → *Yes, save / No, discard / ← Keep editing*). Launch-resolved settings (sandbox, allowed_edit_paths, worktrees, commit_guidance, backend, menu key, timings) note "won't take effect until YOU restart"; nothing is live-applied to the running process.
- **Menu navigation: Esc = up one level, everywhere.** Every Ctrl-G menu is one `while True` loop returning just **two** signals: `_MENU_UP` (Esc/back → the caller shows itself one level up) and `_MENU_DONE` (a context transition — switch/new/resume a session — unwinds to the agent). Authoring rule: build options → `_select_popup` → dispatch; Esc → `return self._MENU_UP`; a transition → `return self._MENU_DONE`; any other action (config, or a child menu the user backed out of) → `continue` (re-show this menu). A child menu is entered by **calling** it: `if child() == self._MENU_DONE: return self._MENU_DONE` else `continue`, so the child's Esc lands back on this parent while a transition unwinds past every level. `_after_menu_command` turns a top-level menu's `_MENU_UP` into "re-open the Ctrl-G palette" (the parent of every command menu). Navigation is **silent** (no "closed"/"cancelled" message on the way up) and modal closes don't repaint the bare screen (`_run_modal` flags `_render_pending` instead of `_render()`), so stepping between levels is instant and flicker-free. Parent→child: `_run_command` → {`_session_menu`, `_settings_menu`, the summarizer menu, backend picker}; `_session_menu` → {`_rename_session_menu`, `_change_session_merge_branch_menu`, `_share_session`, `_manage_shared_sessions_menu`, `_resume_session_menu`, `_resume_shared_session_menu`, `_prompt_new_session`, …}; `_manage_shared_sessions_menu` → `_manage_one_shared_session`. The convention is documented in a comment above `_run_command`.
- **Popups wrap and scroll to fit any terminal.** `renderer._wrap_markup` and `textwrap` break even a long unbroken token (e.g. a path) so it never overflows the box border. `SelectModal` windows BOTH its `detail` list and its `options` list (keeping the selected row visible, with ↑/↓ "more" hints) so a tall menu scrolls instead of being truncated. `append_box(scrollable=True, scroll=…)` windows an over-tall popup **message**; the runner tracks `_message_scroll`/`_message_max_scroll`, resets scroll in `_set_message`, and `_reactor_stdin_phase` routes PgUp/PgDn to message scrolling (refreshing its expiry) whenever a message overflows the screen.
- On the first run (no global default yet and no `--backend`), `select_default_backend` lists the backends alphabetically with each one's install status and **asks whether to install any of the not-installed ones** — a single one (by number) or all of them (`all`). Already-installed backends are shown as installed and never offered for reinstall, and skipping is always allowed. The default becomes the first installed backend (or the first listed when none is installed yet — the launch gate then offers to install it).
- **Automatic backend install (`install_backend`, opt-in).** When the user chooses to install a backend — at first-run or at the launch gate (`ensure_installed_backend`, "Press Enter to install … now") — aGiTrack installs ONLY that one backend, cross-platform: the backend's official install script on macOS/Linux (`curl … | bash`, self-contained, no Node), npm everywhere (`npm install -g …`), and a **winget Node bootstrap** on Windows when npm is absent. Crucially, the freshly-installed CLI's directory is added to **this process's** `PATH` (`_add_dirs_to_path` over `_candidate_bin_dirs` — npm's global prefix from `npm prefix -g`, `~/.local/bin`/`~/.opencode/bin` on POSIX, `%APPDATA%\npm` + the Node dir on Windows) so the backend is runnable immediately, with no aGiTrack restart — the OS installers only update the registry/profile PATH that *new* shells inherit. `install_backend` is dependency-injected (`run`/`which`/`output_fn`) so it is fully unit-tested on POSIX, and never raises. This matters most for the MSI install path: a fresh Windows machine has aGiTrack but no agent, and aGiTrack sets one up on first run.
- **The in-process PATH is not enough — offer to persist it (`agitrack/path_setup.py`).** Patching `os.environ["PATH"]` makes the agent runnable *inside aGiTrack*; the user's other terminals still report "command not found", because the `curl | bash` installers only print a note about the PATH and npm's global prefix may be nowhere in the user's profile. The first person to hit this had to work out the right rc file themselves. So after a successful `install_backend`, `offer_to_persist_path` asks (default yes) to add the directory the CLI **actually landed in** — resolved from the executable via `_installed_bin_dir`, not guessed from the broad `_candidate_bin_dirs` list — to the user's shell profile (`$SHELL` → `~/.zshrc` / `~/.config/fish/config.fish` / `~/.bash_profile` on macOS vs `~/.bashrc` on Linux / `~/.profile`) or, on Windows, to `HKCU\Environment`'s `Path` (**never `setx`**, which truncates a long PATH at 1024 chars). Three properties matter: the offer is skipped when `proc.INHERITED_PATH` — the PATH captured at import, *before* any install mutates it — already contains the directory, which is the only way to tell "the user's shells find it" from "only this process does"; the written line is marked (`path_setup.MARKER`) and `$HOME`-relative, so a re-install doesn't duplicate it; and a **failed** write prints the manual instructions and requires an explicit acknowledgment, because that is the one outcome that silently leaves the CLI aGiTrack-only. Consent is required (it edits the user's file), so a non-TTY run only prints the instructions. Tests: `tests/test_path_setup.py`.
- Check that the backend's CLI is installed (on `PATH`) before launching it (`ensure_installed_backend`). If it is not, this is a GATE, not an installer (`ensure_installed_backend`'s own docstring): it offers to switch to a different (installed) backend or shows manual instructions, and does not install anything itself. The first-run backend chooser (`select_default_backend`) is the one that can install, and only after an explicit y/N; backend switching is likewise blocked for backends that are not installed.
- **System prerequisites — git, gh, and git identity (`agitrack/system_tools.py` + cli.py).** On an interactive launch aGiTrack also helps set up its non-backend prerequisites. `_maybe_install_tool` (cli.py) offers to install missing **git** (required, gates launch) or **gh** (optional, in `_check_gh_availability`) via `install_system_tool`, which uses the platform package manager — winget on Windows, Homebrew/`xcode-select` on macOS, the detected distro manager with `sudo` on Linux — and PATH-augments in-process like the backend installer. `_ensure_git_identity` (cli.py, proxy + TTY only) prompts for a missing global `user.name`/`user.email` and sets them, because git refuses to commit without them and aGiTrack commits every turn. gh sign-in is offered inline (`gh auth login`) when gh is installed but unauthenticated. All of this is TTY-gated and skipped for scripted/json runs (no prompts, no polluted machine-readable output).
- `agitrack --backend <claude|codex|opencode>` selects the backend for a run and saves it as the new global default.
- Switching backends saves the current backend's session id and restores the target backend's last session id for the repository, so each backend keeps its own conversation.

## Self-Update

- aGiTrack can update itself in place. It detects how it was installed: **source-linked** (importable from a git checkout of its own source — the editable `pip install -e .`) or **package** (installed as a wheel). Implemented in `agitrack/update/`.
- Source-linked: compare the current branch against its upstream remote branch (after a `git fetch`); an update is available when the local branch is behind. Package: compare the installed version against the latest published one (`pip index versions`, run through the resolved pip invocation; reading the index is safe even on an externally-managed Python).
- Check for updates at startup and periodically while running (every `timings.update_check_seconds`, default 300s). The periodic check runs on a worker thread so the terminal never blocks on network I/O.
- When an update is available, prompt the user — at startup (before launching) and during a session (a status-bar notice plus the `update` command in the `Ctrl-G` menu).
- Never surface an update prompt while a merge / conflict resolution is in progress in any session (active or a background session integrating its turn); the notice is held until the merge is done, and an accepted update is likewise deferred.
- If the user accepts during a session, apply the update only once **every session has finished and all commits are integrated** (no agent in flight, no pending parse/merge/summary, no running background session), then re-exec aGiTrack (`restart_agitrack` → `_restart_command`) so the new code loads. The re-exec runs `python -m agitrack` for a normal install, but **a frozen MSI build re-runs `agitrack.exe` directly** — `-m agitrack` is not a valid argument to a PyInstaller executable, so passing it (the old behaviour) broke both self-update restart *and* the settings-menu "restart now" on MSI installs. `_restart_command` branches on `getattr(sys, "frozen", False)`; `tests/test_updater.py` locks both shapes.
- Source updates are fast-forward only and abort (with a message) when the checkout is dirty or has diverged from upstream, so an automatic update never clobbers local development.
- Package updates are deliberately **package-manager-independent** wherever possible: the primary path upgrades with the *running interpreter's own* pip (`<python> -m pip install --upgrade`), which upgrades a plain `pip` install, a venv, a `--user` install, and a pipx venv identically — no need to detect or shell out to pipx/brew/apt. It falls back to a `pip3`/`pip` on `PATH` only when that interpreter has no `pip` module. The single case pip can't handle is an externally-managed (PEP 668) Python — Homebrew's or a distro's — where pip refuses by design; there aGiTrack defers to the owning system manager (`brew upgrade`, the only system manager that ships aGiTrack — distro managers don't carry it), and when no automatic path works it reports a **full enumeration** of every manual route (pip, pipx, Homebrew, and `--break-system-packages`). Never auto-add `--break-system-packages` (it can corrupt a system/Homebrew Python). Install-method detection keys off where the running code physically lives (resolved package path, `sys.prefix` backstop), checking the pipx-venv marker before the Homebrew prefix.
- **Every long-lived daemon checks for updates ITSELF** (`watch_for_update(..., self_update=True)`), not only reacting to someone else installing one: the dashboard hub, the legacy repo/backtrace dashboards, AND the background tracker. Watching the on-disk fingerprint alone is enough only on a machine where something else updates; the tracker is the daemon most likely to be the ONLY aGiTrack running (`-b` is the default mode, it is meant to be left alone for days, and it has no TUI whose startup check would fire), and it had been left out — so a `-b` user on the PyPI package sat on their starting version while release after release went by. `tests/test_daemons.py::test_every_long_lived_daemon_checks_for_updates_itself` is a SOURCE-level check, so the next daemon added has to opt in too.
- **After an update every daemon comes back on the new code**, two independent ways: `restart_agitrack` calls `daemons.restart_all()` (SIGTERM + re-spawn from each daemon's recorded argv), and each daemon's own watcher notices the changed fingerprint and hands over to a replacement. A kind is restartable only if its serve flag is in `daemons._SERVE_FLAGS` (the identity proof against pid reuse) and its kind is in `_STOPPABLE_KINDS` — a new daemon missing either is silently skipped by every update. An interactive `session` is the one deliberate exemption: restarting someone's conversation is not an update.
- Update checks are on by default; the user can turn them off via the "stop checking" choice or `check_for_updates: false` in `~/.agitrack/config.json`. Scripted/non-TTY runs never prompt.
- An interrupted update must never leave aGiTrack **uninstalled**. `pip install --upgrade` removes the old version before writing the new, so a kill between the two would strand the package. The upgrade subprocess (pip, and the `brew upgrade` fallback) therefore runs with `start_new_session=True` (`updater._apply_package`), so a terminal-close **SIGHUP** — the user quitting VS Code / closing the window mid-upgrade — is not delivered to it and it runs to completion. The in-session apply path is also protected: `_handle_exit_signal` **returns without tearing down while `self._update_applying`** is set, so a SIGHUP/SIGTERM during the apply can't unwind `subprocess.run` and kill the (now detached) pip child. (Root cause of an earlier "aGiTrack uninstalled itself after I quit VS Code" report: the startup `Update aGiTrack now? [Y]` upgrade was interrupted between uninstall and reinstall.)
- A failed update must never take aGiTrack down or block work. `Updater.apply()` never raises — any failure (subprocess timeout, OS error, pip/git crash, PEP 668 refusal) becomes an `error` status carrying manual-update instructions (`Updater.manual_update_instructions()`), and aGiTrack keeps running the current version. On a failure aGiTrack records the target version in `pending_manual_update` (global config): the next startup shows a **single** manual-update reminder (and clears it once aGiTrack is actually at/above that version), while the regular in-session update notice is suppressed for that version so the user isn't nagged repeatedly. The explicit Ctrl-G `update` command can still retry.
- Running aGiTrack inside the VSCode extension does not change any of this: the extension launches the real CLI in an integrated terminal (a real PTY), so the startup TTY-gated update offer and the Ctrl-G update both work, and the `python -m agitrack` re-exec lands cleanly in the same terminal.
- **VSCode extension version is locked to the CLI version.** `pyproject.toml` is the single source of truth; `scripts/sync_vscode_version.py` stamps `editors/vscode/package.json` (and `package-lock.json`) to match, enforced by `tests/test_version_sync.py`. `agitrack --version` (cheap, no repo/privacy side effects) lets the extension detect a CLI that has self-updated past it and prompt the user to update the extension.
- **Releases ship the backend CLI and the VSCode extension together.** `release-patch.yml` (on merge to main) and `release-tag.yml` (on a `v*` tag) run the version sync, commit it with the bump, build and publish the CLI to PyPI, create a GitHub Release, and — when the `VSCE_TOKEN` repo secret is set — publish the extension to the Marketplace at the matching version, so a CLI release and its extension move together. `release-patch.yml` picks the bump level from the merge commit / squash-PR title: `[major]` bumps major (minor+patch→0), `[minor]` bumps minor (patch→0), and neither marker is a patch bump (default); markers are case-insensitive and the title is read via env, never interpolated into the shell.
- **Windows MSI is a first-class, standalone install method.** A PyInstaller one-folder bundle (`installer/agitrack.spec` → `agitrack.exe` + `_internal/`) wrapped by a WiX **v5** perMachine MSI (`installer/agitrack.wxs`; `UpgradeCode` is the stable product identity and must NEVER change between releases). WiX v5 is required because the file harvest uses the `<Files>` element (added in v5; v4 had no `wix harvest`/`heat`); the wix tool and `WixToolset.UI.wixext` are pinned to the **same** version (a mismatch fails `wix build` with WIX0144), the `<ui:WixUI>` element needs the `xmlns:ui` namespace declared, `SourceDir` is passed as an absolute path so the `<Files>` glob is unambiguous, and the build passes `-arch x64` (the bundle is 64-bit; the WiX default x86 package's `ProgramFiles64Folder` doesn't resolve to `C:\Program Files`, so files would install to the wrong place — caught by the CI install smoke-test). It bundles its own Python (and its own `.dist-info` via `copy_metadata("agitrack")` in the spec, so `agitrack --version` reports the real version instead of the frozen-build `0.0.0` fallback), so it installs and runs `agitrack` on a machine with **no Python/pip at all**, adding `C:\Program Files\aGiTrack` to PATH and writing `HKLM\Software\aGiTrack\InstallDir`. The MSI is built and attached to the release **inside the release workflows themselves** — a `build-msi` job (`windows-latest`, `needs: release`) in both `release-patch.yml` (the normal merge-to-`main` path) and `release-tag.yml` (human `v*` tag) builds `agitrack-<version>-windows-x64.msi` and `gh release upload`s it. It must live in the same workflow run as the release, NOT a separate tag-triggered workflow: GitHub does not trigger workflows from a tag/release created with the default `GITHUB_TOKEN`, so the old standalone `release.yml` never once fired and no release ever got an MSI (the bug this fixed). The CI `build-msi` job (`ci.yml`, on every PR) guards the bundle against rot: it builds the MSI from the pyproject version and proves it installs by itself — silent `msiexec /i … /qn` perMachine install (the runner has an admin token), asserts the installed `agitrack.exe --version` equals the pyproject version, then a clean silent uninstall. The VSCode extension uses this same MSI as its **no-Python fallback**: `installAgitrack()` (`editors/vscode/src/extension.ts`) only reaches `installViaMsi()` on Windows when `planInstaller()` finds neither pipx nor pip, downloading the latest release's MSI asset (selection logic in the pure, unit-tested `editors/vscode/src/msi.ts`) and running `msiexec`. It also discovers a by-hand MSI install via `msiInstallCandidates()` (a GUI-launched VSCode doesn't inherit the PATH entry the MSI adds — issue #93).
- **MSI self-update** (the frozen Windows bundle updating itself in place; design in `docs/design/msi-self-update.md`, implements #124). `Updater._install_method()` returns `METHOD_MSI` when **both** `sys.frozen` and the `HKLM\Software\aGiTrack\InstallDir` registry key are present (a portable PyInstaller zip lacks the key → falls through to pip). `check()`/`apply()` route to `_check_msi`/`_apply_msi`: the check queries the **GitHub Releases API** (`/releases/latest`, repo from `AGITRACK_GH_REPO` or the `core-aix/agitrack` default — an MSI install has no source remote to read; 5-min + ETag in-process cache keeps under the anon rate limit) for the newest `agitrack-*-windows-x64.msi` asset and parses the version from its name; apply **downloads** it to `%TEMP%` (size-capped, sha256-verified when GitHub supplies a digest) and stashes `Updater.pending_msi_path` — it does **not** install (the MSI replaces the running `agitrack.exe`, so the install must happen after exit). The hand-off is in the runner: `_apply_update_and_restart` sets `_pending_msi_handoff` when a download is pending, and the teardown calls `_launch_msi_bootstrapper()` instead of `restart_agitrack`. To keep the relaunched agent at the **user's** integrity level (not admin), the hand-off uses two cooperating processes: an **elevated** bootstrapper (`installer/agitrack-update.cmd`, run via `proc.shell_execute_runas` → `ShellExecuteExW(lpVerb="runas")`, UAC) waits for our PID, runs `msiexec /i … /passive /norestart REINSTALL=ALL REINSTALLMODE=vomus`, and writes its exit code to a marker file; a **non-elevated** PowerShell relauncher (spawned detached before we exit) polls that marker and, on success, starts the new `agitrack.exe` with the saved args. Launch args survive the replace via `%LOCALAPPDATA%\aGiTrack\last-args.txt`, written each startup by `_write_msi_last_args` (frozen-Windows only). UAC declined / `runas` failure ⇒ `_launch_msi_bootstrapper` returns False, the teardown falls back to a normal re-exec of the **current** version, and `pending_manual_update` is set so the next startup reminds the user. The bootstrapper is committed (not part of the PyInstaller harvest) and installed into `INSTALLFOLDER` by the `UpdaterComponents` group in `agitrack.wxs`, so the same MSI that updates everything else updates the bootstrapper. Unit tests monkey-patch the GitHub HTTP, the registry read, and the download, so the whole path is covered on POSIX CI (`tests/test_updater.py`).
- **One version string, everywhere a person reads one** (`agitrack/versioning.py`). `version_line()` is the release version plus, on a source checkout, its commit — `0.6.13 (source a35f56a3-dirty)` — and it is what `agitrack --version`, the dashboard's `/state` poll, the version embedded in the page and a crash report all print. They used to compute it separately and disagreed: the CLI named the commit while the dashboard served the bare version, so one install answered "which version is this?" two ways. That is not cosmetic for the dashboard — the page compares this string across polls to notice its daemon was replaced, and between two releases every commit reports the same release version, so without the commit it could not notice at all. The release version stays FIRST and unadorned (`--version | cut -d' ' -f1` is unchanged). The git call is memoized per process (it names the code this process loaded, which cannot change under it; the successor after a restart computes its own) — `tests/conftest.py::_forget_the_resolved_source_commit` clears it between tests, the one place that assumption is false. **Machine-read fields keep the bare version**: the `agitrack_version:` commit trailer, the daemon registry's `version`, and the autotrack hook stamp are parsed or compared for equality.
- **A pip that belongs to another interpreter is never used to upgrade a virtualenv** (`Updater._pip_invocation`). The preferred route is the running interpreter's own `<python> -m pip`; the fallback to a `pip3` on `PATH` now applies only OUTSIDE a venv, where it plausibly is the same environment. Inside one it was worse than no update: a uv-created venv has no `pip` module, so a tracker running from one reached for Homebrew's `pip3`, was refused under PEP 668, and published "this Python is externally managed; run `pip install --upgrade agitrack`" into the global record for every dashboard on the machine — a diagnosis about an interpreter it does not run from, and a command that would have installed into that other interpreter rather than the venv it was complaining about. Such an install now reports that the venv has no pip and names the tool that can replace what is in it (`uv pip install --upgrade agitrack`).
- **The self-update record is a global CACHE, and it is never trusted as written** (`update/selfupdate.py`). One `~/.agitrack/self-update.json` per machine, written by whichever aGiTrack checked last — but a machine runs many instances (one tracker per repo, the dashboards, a TUI), they need not share an install, and a daemon keeps the code it imported at startup. Two ways that misled the user, both measured: (1) a FAILED attempt's record survives the update that later succeeds, so a dashboard nagged "0.6.13 has to be installed by you" while running 0.6.13; (2) a tracker whose venv wheel had been replaced by an editable install underneath it never saw its own install change again, stayed on 0.6.10 for days, and kept publishing that version's PEP 668 "upgrade it yourself" verdict for every other dashboard to display as its own. `SelfUpdateRecord.needs_user` therefore re-checks against the aGiTrack running now and ignores a package record naming a version this process is not. **Only versions may be compared**: a source install records commit SHAs in the same fields, and `_version_tuple` is lenient enough to turn `e4f5a6b` into `(0,)`, which read as "already newer" and silently suppressed every source checkout's notice — both sides must match `^\d+(\.\d+)+` or the recorded verdict stands.
- **On a repo dashboard the "install it yourself" notice speaks for THAT repo's instance** (`selfupdate.record_matches_instance`, used by `web._update_banner_html`). The instance holding a repo's single-writer lock records the install it loaded (`commit:<sha>` for a source checkout, `version:<x.y.z>` for a wheel), so the global record is shown only when it describes that install — a source-tracked repo does not carry a wheel install's complaint. A repo with no instance (dashboard only) has nothing to compare and still shows the global record. The other notice, "restart your session", was already repo-scoped.

## Testing

- Make it regular practice to **create temporary git repositories** to test aGiTrack functionality end-to-end against real git, rather than relying only on mocked inputs. Where a feature depends on backend behavior (transcripts, sessions, sub-agents, token usage), also run the actual backend CLIs (`claude`, `opencode`) in a temp repo to produce real data and verify against it. This is the established practice for branch/worktree concurrency, sub-agent token accounting, and token-count precision.
- Compute expected results independently from the real data and assert **exact** equality — especially for token counts, which must be precise (not more, not less).
- Capture the verified scenarios as permanent tests under `tests/` so the behavior stays locked in, and clean up any temporary repositories afterwards.
- **User-flow test matrix (`tests/FLOW_MATRIX.md`) — keep it complete.** It is the auditable index of every interactive sequence a user can drive (startup, prompt submission, the agent turn, interruption/follow-ups, copy-back, user/agent commits, switching, backend switch, background sessions, integration/merge/conflict, exit, sharing, self-update, the Windows specifics, AND the system-prerequisite/installation flows — missing git/gh, git identity, gh login, backend install). **Any change that adds or alters a user flow MUST, in the same change: (1) add or extend the covering test, (2) add/update its row in `tests/FLOW_MATRIX.md`, and (3) if a sequence can't be covered yet, list it under that file's "Known gaps / TODO" rather than leaving it implicit.** A flow change is not "done" until it is represented there. Prefer **real-git** tests (a real temp repo) over mocks for anything touching commit/merge/worktree/copy — mocks that stub `repo.commit` cannot catch real `git` failures (this is how the Windows cp1252 commit-encoding bug slipped through).
- **A test that touches `pty`/`tty`/`termios`/`PosixHostTerminal` needs `@_posix_only`** (`tests/test_proxy.py`). Those modules do not exist on Windows and the import fails at *call* time, inside the test body, so the local suite is completely green and only the Windows job goes red — a 17-minute round trip to learn something `grep` answers instantly. The decorator is `skipif`, so it prevents the import from ever running. Check any new test with `grep -nE 'import (pty|tty|termios)|PosixHostTerminal' tests/` before pushing.
- **No test may let aGiTrack self-update the checkout it runs from.** On a source install, applying an update MERGES that checkout — in CI, the job's own working tree — so a release landing upstream mid-run rewrites `pyproject.toml` underneath the already-imported `agitrack.__version__` and the build dies on a version mismatch that has nothing to do with the commit under test. It has come back twice after being "fixed", both times through a caller nobody had guarded: a `monkeypatch` cannot reach the daemon SUBPROCESS that does the merging, and `check_for_updates: false` gates only the tracker's own periodic check (the restart watcher's `self_update=True` reaches `attempt_self_update` by another route) and is lost the moment a test repoints `AGITRACK_CONFIG_DIR`. The guard that holds is the environment: `AGITRACK_NO_SELF_UPDATE=1`, set by `tests/conftest.py::_never_really_self_update` and by `ci.yml` workflow-wide, honoured in `selfupdate.self_update_enabled()` — the one function every install path passes through. **Put new refusals THERE, not in a caller.**
- `./scripts/check.sh` (ruff check, ruff format, mypy-vs-baseline, pytest + coverage) must pass before a change is considered done.

## Nothing may paint over the TUI, and a death must leave a trace

- **stderr IS the alternate screen while the TUI is up.** Python's default `threading.excepthook` prints a dying thread's traceback there, scribbling over the session and leaving the display out of step with the pyte model (indistinguishable, to the user, from aGiTrack breaking). `run()` installs `ProxyRunner._thread_excepthook` for the lifetime of the TUI (restored on teardown): it logs, writes a non-fatal crash report, and lets the session live. The known workers are guarded locally too (`commit_engine.start_parse`'s worker, the exit-share `push`).
- **A repaint never ends a session.** `_render` catches everything (`_render_frame` does the work), and is re-entrancy-guarded: a SIGWINCH lands on any bytecode boundary and `_resize_child` repaints, so without the guard two frames interleave on one fd, which is how a terminal ends up in a mode the user cannot get out of. The SIGWINCH handler itself catches everything as well (it used to catch only `OSError`, so anything else propagated into whatever the main thread was executing).
- **A reactor death is written down**: `agitrack/proxy/crash.py` puts the traceback plus context (version, terminal geometry, backend, scrollback depth) in `<base-repo>/.agitrack/crash-<timestamp>.log`, keeps the last 5, and `run()` prints the path AFTER the terminal is restored, when the user can actually read it. This exists because a scroll-related death nobody could reproduce cost several rounds of guesswork. The **base** repo, via `_crash_report_root()` — reports used to go to `self.repo`, which in worktree mode is the session worktree that teardown then deletes, so the crash destroyed its own evidence (same reason `_diag_path` puts the DEBUG_PROXY/DEBUG_RAW logs in the base repo).
- **A freeze is recorded too, not just a death** (`_note_phase` → `crash.write_stall_note` → `<base-repo>/.agitrack/stalls.log`). Any pass through the reactor's work phases taking longer than `STALL_WARN_SECONDS` writes one line naming the phase and the duration, **without DEBUG_PROXY having been set** — a stall nobody can reproduce on demand has to be caught on its first occurrence. It matters because while the reactor is inside a phase it is not reading stdin, so the terminal's ~1 KB queue fills and then discards: a stall surfaces to the user as *stray keystrokes and half a mouse report appearing all at once* when it unblocks. Reach for `stalls.log` when "the TUI froze / took ages / showed garbage" is reported.
- **The git worker must not crowd out the user** (`GIT_PASS_MIN_INTERVAL`, `_pipeline_lock_wanted`). The reactor sets `_git_wake` every loop iteration, so the worker's `wait` returned instantly and passes ran back to back — **~74 per second** while the backend is producing output — holding `_pipeline_lock` almost continuously for work whose own sub-checks are throttled to seconds. `_acquire_pipeline_lock_from_main` is on the SUBMIT path, and Python locks are not fair, so a worker that re-acquires the instant it releases barges past a thread already waiting: measured **1.8 s** of dead time after a keypress, now **0.26 s**. The floor is a sliced `time.sleep`, NOT `_git_wake.wait()` — the reactor re-sets that event immediately, which is exactly how the rate got so high.
- **An absent crash report is itself a diagnosis.** `run()` catches everything out of `_loop()` and `_thread_excepthook` catches every dying thread, so "it died and left no report" rules out an exception and points at a NORMAL exit path — most usefully `_relaunch_backend_or_exit` giving up after the backend exited three times in 12 s. Check the backend's liveness before looking for a traceback that was never going to exist.

## An empty dashboard when a reconstruction is available

- **`--backtrace commit`'s branch flag is `--backtrace-branch`, and a missing one is ASKED for, not refused.** `cli.py` parses with `parse_known_args` so backend flags pass through — which means an unknown option is NOT an error, it is silently collected as backend passthrough. So a user who typed the `--branch` spelling earlier guidance printed (or any typo) got "give the name of a NEW branch" back forever with nothing explaining why: the feature was unusable from the command line and no test covered the CLI wiring. Now: `--branch` survives as an undocumented alias, an unrecognized option is reported instead of swallowed, and a missing branch name is prompted for (the command is interactive anyway). Tests: `tests/test_backtrace_commit.py::test_the_branch_flag_actually_reaches_backtrace_commit` and the CLI-wiring tests beside it — unit-testing `backtrace_commit()` directly could never have caught this.
- **Never show an empty live dashboard when the backtrace view would have something.** A repo only has live-dashboard history once aGiTrack has committed in it, so anyone who coded with Claude/OpenCode BEFORE adopting aGiTrack sees an empty page while their own transcripts hold history `--backtrace` can reconstruct. That is the worst answer available: it says "nothing to see" when there is. The gate is **zero TOKENS**, not "no metadata": a repo whose commits carry only `commit_type: user` attribution shows a 100%-coverage bar over an empty story, which is no more useful than an empty page (`has_tracked_tokens` greps for a non-zero `tokens_since_last_commit_*`). `metrics/suggest.should_show_backtrace` gates it, and the dashboard defers — `agitrack -d` and the Ctrl-G `dashboard` command both start the reconstruction instead. Plain `agitrack` (the TUI) instead PROMPTS before the full-screen UI takes over, because the reconstruction can take minutes and cooked mode is the only place its progress bar and URL are readable.
- **"aGiTrack was present" ≠ "AI work is recorded here" — never test the first when you mean the second.** `METADATA_HEADER in body` answers the weaker question, and a plain USER commit made through aGiTrack carries an attribution-only block (`commit_type: user`, session id, system, version — no turn, no trace, no tokens) that satisfies it. Conflating the two broke `--backtrace commit` for exactly the users it exists for: someone who ran aGiTrack, committed the agent's work themselves, and has all their real history in the backend transcripts got `Nothing to add: every agent-made commit here is already tracked` and no way forward. `commits.carries_ai_history(body)` is the predicate for the stronger question — a block qualifies when it is agent/agent-merge (or has no `commit_type` at all, matching the dashboard's classifier) or carries a NON-ZERO `tokens_since_last_commit_*`; in-flight blocks never qualify. Two subtleties: a manual-mode user commit that FOLDED turns carries their agent blocks and still qualifies (this must never demote real history), and each block is cut at its first blank line so the NEXT turn's interaction trace — which in this repo constantly quotes these very field names — cannot be read as the block's own record. When `--backtrace commit` annotates such a commit it DROPS the hollow user block rather than leaving it beside the real one, since two blocks parse as a squash aggregate. Do NOT swap `is_fully_tracked_message` for this in `background._is_agitrack_tracked`: there the weaker question is the right one — a human commit must not be re-covered as AI work. Tests: `tests/test_commit_message.py::TestCarriesAiHistory`, `tests/test_backtrace_commit.py::test_a_plain_user_commit_does_not_make_the_repo_look_already_tracked` and the two beside it.
- **A `--backtrace commit` test must stamp the commit the reconstruction actually reads.** `repo_with_history` ends on a trailing USER commit, so `git commit --amend` there rewrites the wrong commit and the test passes green without exercising anything (this happened). Use `repo_ai_commit_at_head`, whose HEAD *is* the AI-made commit.
- **Both probes are cheap, and short-circuit in the common order.** `has_tracked_history` is one `git log --all --fixed-strings --grep '# aGiTrack Metadata' -n 1` (~20 ms, stops at the first hit — never builds the dashboard). `has_backtrace_history` only *discovers* sessions (~0.5 s, no export or parse) and runs ONLY when nothing is tracked, so a tracked repo pays the 20 ms and nothing more. `--all` matters: history tracked on a feature branch must not read as empty.
- **Both probes fail SAFE, in opposite directions** — a broken `git` reports "tracked" and a broken discovery reports "no sessions". Either way the failure can only leave the user with the dashboard they asked for; a probe must never silently redirect them somewhere else.
- **The TUI path must not block the reactor.** The Ctrl-G substitution spawns the DETACHED backtrace child and polls its handshake for `BACKTRACE_URL_WAIT` (3 s) only — the reconstruction exports every local session (OpenCode shells out per session) and can take minutes. A slow build just means the popup hands over `agitrack --backtrace status` instead of a URL; the daemon carries on regardless. Do NOT call `start_backtrace_daemon` from the TUI: it prints and draws a progress bar, which inside the alternate screen is both invisible and corrupting.
- **The message has to sell the upgrade, not just explain the substitution.** The reconstruction INFERS which conversation changed which files; committing through aGiTrack RECORDS it — prompts, replies and token counts tied to the exact lines. That contrast is the point of both notices.
- The startup prompt self-retires: the moment the user commits through aGiTrack the condition is false forever, so it needs no "don't ask again" flag. Tests: `tests/test_backtrace_suggestion.py`.

## Timing-dependent tests

- **The composition tests run on Windows too, and they did not used to.** `tests/harness.py`'s fakes were built on `os.pipe()`, which Windows `select` rejects, so the ONE suite that drives the real `run()`/reactor (`test_startup_composition.py`) was skipped there — the Windows CI leg's "full test suite" quietly meant "minus the composition layer", on the platform whose host I/O is the most unusual. The fakes now bridge through a `socketpair`, exactly as `platform/nt.py` does for the console and the ConPTY, so the sequence under test is the product's on both platforms. Anything added to that harness must stay socket-based.

- **A test whose PASS/FAIL depends on how fast the machine is does not belong in the default suite or in CI.** They are marked `@pytest.mark.timing` and deselected by `addopts = "-m 'not timing'"` in `pyproject.toml`, so a plain `pytest` — which is what both CI jobs run — never sees them. Run them deliberately when investigating a timing problem: `pytest -m timing`. They are kept, not deleted; they are the right tool for exactly that.
- **What earns the marker:** an assertion on MEASURED wall-clock elapsed time (`time.monotonic() - started < N`, `elapsed < N`) or a computed timeout compared against the bound it derives from. Comparing a timeout against a CONSTANT the runner set (`_select_timeout() == 30.0`) is not timing-dependent and stays in the suite.
- **The failure that prompted this**: `assert 0.0500000000001819 <= 0.05` on `windows-latest`. `_select_timeout()` returns `_input_tail_at + INPUT_TAIL_HOLD - monotonic()`, and with a coarse clock no time passes between the two calls, so float addition of two large timestamps lands a hair ABOVE the bound. Reproducible on macOS too (worst overshoot 4.7e-11 over 200k trials) — it was never a Windows quirk, just a tighter clock exposing it.
- **Prefer splitting over marking a whole test.** `test_a_held_escape_is_still_delivered_when_nothing_follows` had ONE fragile line among several behavioural ones; the timing assertion moved to its own marked test so the behaviour keeps running in CI. Marking the whole test would have silently dropped real coverage.
- **Counting instead of timing is not enough on its own — a wall-clock WINDOW is timing too.** `test_pressing_enter_does_not_ask_git_the_same_question_twice` counted git spawns (never elapsed time) but collected them "between the keystroke and the forward", and pressing Enter starts the git worker: that window catches however far the worker happened to get. It was green on Windows, red on Linux and red-with-a-different-set on macOS. The fix is to select by CAUSE, not by clock — only spawns whose stack goes through `_reactor_stdin_phase` are the user's wait — and to encode the invariant the code actually promises: a read may legitimately repeat once a write (from any thread) has dropped the cache, so the assertion allows a repeat after a write and forbids one before it.

## Exactly ONE reader may own stdin at a time

- **The stdin pump and the capability round trip must never read fd 0 together.** `run()` calls `_set_raw()` (which starts `PosixHostTerminal._pump`) and *then* `_detect_host_terminal()` — which wrote its OSC 10/11/4 + DA queries and read fd 0 **itself**. Two readers on one tty: every reply went to whichever got there first. Measured on a pty, the pump won 8/8 trials, taking all 461 bytes. That one race produced **both** reported symptoms: replies the pump swallowed never reached the capability cache, so `_answer_terminal_queries` had nothing to tell the backend and it fell back to a default theme (*"the TUI starts with different color rendering from time to time"*), **and** those same bytes were handed to the reactor as ordinary input — where the **BEL that terminates every OSC reply is 0x07, which is Ctrl-G, the menu key** (*"sometimes the Ctrl-G menu shows up at start"*). A full reply set carries 18 BELs. `PosixHostTerminal.detect_host_terminal` now pauses the pump for the round trip and waits on `_parked` before proceeding — setting `_paused` alone is not enough, because the pump can be inside its 0.2 s `select` and will still consume whatever that returns. `termios.tcflush` could never have helped: it flushes the tty, not the pump's in-memory buffer.
- **A terminal's ANSWER is not a keystroke — absorb it wherever it lands.** Detection waits a bounded time; a slower terminal (tmux relaying outward, a forwarded/remote session) answers afterwards and the answer arrives as input. `ProxyRunner._absorb_host_terminal_reply` (run in `_reactor_stdin_phase`, after the kitty decode) removes exactly the shapes aGiTrack asks for — `_HOST_TERMINAL_REPLY_RE`: OSC 10/11/4 reports plus `CSI ? … c` / `CSI ? … u` — and feeds them to the capability cache, so a late reply *repairs* the theme instead of typing at the agent. Keep it narrow and keep the guards: a bare `\x07` is a real Ctrl-G and must still open the palette; kitty **key** events are `CSI <code>;<mods> u` with no `?`, which is the only thing distinguishing them from the flags **reply**; and nothing is absorbed inside a bracketed paste, where a pasted terminal transcript is content the user copied. Tests: `tests/test_proxy.py::test_the_stdin_reader_does_not_race_the_capability_round_trip` and the absorption tests beside it.

## Selecting and copying text (who owns the mouse)

- **aGiTrack turns mouse reporting ON (`?1000h`) so the wheel scrolls its history, and that is what takes SELECTION away from the terminal.** A terminal that honours the mode stops doing its own selection and forwards the drag to the application instead. So the two behaviours are not independent: in every terminal where those reports arrive, aGiTrack's own drag-select-and-copy (`_track_selection` → `_copy_selection`) is the ONLY copy the user has. In terminals that keep selecting natively, a plain left drag is never forwarded, that code never runs, and nothing about them changes — no highlight, no "Copied N char(s)" message.
- **This was removed once, and it broke copying outright on Linux.** #112 dropped the handler on the reasoning that "the terminal owns selection" — true only for the reporter's terminal. Everywhere the drag IS forwarded (VTE/gnome-terminal, konsole, xterm, alacritty, foot — the common case on Linux) the terminal had already stood down and aGiTrack had stopped copying, so selecting text did nothing at all. Restoring the handler is what fixes it; the guards are what keep #112 fixed: only the plain left button (a Shift/Alt/Ctrl chord is the terminal's own override and is left alone), and a press+release on the SAME cell is a CLICK — it copies nothing and shows no message.
- **`_copy_to_clipboard` writes through a native helper AND OSC 52, deliberately, not first-one-wins.** Over SSH they reach DIFFERENT clipboards: the helper sets the one on the machine aGiTrack runs on, OSC 52 travels back down the terminal connection to the one the user will paste into. Locally they are the same clipboard and the same text. macOS has exactly one helper (`pbcopy`); **Linux needs `wl-copy` OR `xclip` OR `xsel` depending on Wayland/X11 and may have none**, which is why the list is tried in order and OSC 52 is a companion rather than a fallback.
- Tests: `test_mouse_drag_copies_the_selection`, `test_mouse_drag_copies_even_when_the_terminal_reports_no_motion` (mode 1000 reports press/release but NOT motion — keying the copy on motion would mean no copy at all in the mode aGiTrack actually asks for), `test_a_plain_click_copies_nothing`, `test_a_modified_drag_is_left_to_the_terminal`, `test_copy_to_clipboard_always_emits_osc52`, `test_linux_clipboard_falls_through_to_the_next_tool`.

## ProxyRunner is assembled from parts (`proxy/runner_host.py`)

- `runner.py` was a single 14,000-line class. Cohesive areas now live in their own modules as mixins on `ProxyRunner`: `sharing.py` (publishing/resuming shared sessions, auto-share), `updates.py` (aGiTrack's self-update and the backend CLI's), `manual_commits.py` (manual-commit mode + latent tracking), `branch_watch.py` (what moves under a session: branch drift, base edits, cwd drift). `textutil.py` holds the leaf helpers they share.
- **Mixins, not collaborator objects, and the reason is the interface.** These methods ARE runner behaviour — they read and write a dozen pieces of runner state and call back into the runner for rendering, popups and session switching. Handing all of that to a standalone class produces a wider interface than the code it moved. The split is by CONCERN: `self` is unchanged, and every method is still a `ProxyRunner` method to callers, to `getattr`, and to a test that patches one.
- **`runner_host.RunnerHost` declares the shared surface** — the state and methods the parts reach for — and both the runner and every part inherit it. It is EMPTY at runtime (the whole body is under `TYPE_CHECKING`), so a genuinely missing name still raises `AttributeError` instead of resolving to a do-nothing stub. It exists because a split class otherwise leaves the checker INFERRING an attribute's type from whichever assignment it sees first: a mixin assigning `self._update_check_thread = Thread(...)` made the runner's own `Thread | None = None` an error. Adding a name to it is a deliberate act ("this is now shared surface"); prefer moving the dependency with the code.
- **A mixin's module globals are its own.** A test that patched `runner_module.make_proxy_agent` to intercept a SHARING call had to move to `sharing_module` — the call resolves through the module where it now lives. Same rule for any future `monkeypatch.setattr(runner_module, …)`.

## Scrolling and repaint budget

- **stdin is drained by a THREAD, not by the reactor** (`PosixHostTerminal._pump`) — but it is NOT a complete cure, and the reason is the GIL. A terminal's input queue is ~1 KB and the kernel DISCARDS what will not fit, mid-escape-sequence. The reactor cannot out-read that inline (one `os.read(fd, 4096)` already empties the whole queue, so looping to EAGAIN just returns EAGAIN: 77% → 72% loss), so a thread drains the tty continuously. Windows has always worked this way (`NtHostTerminal`); POSIX was the odd one out.
  - **How much it helps depends entirely on how much the main thread yields**, because the reader needs the GIL to loop and a repaint holds it. Measured byte loss under the same burst, by what the main thread is doing:

    | main thread | loss |
    | --- | --- |
    | `time.sleep()` | 0.0% |
    | GIL held 100% of the time (repaints back to back) | 35.4% |
    | GIL held 50% | 0.0% |
    | GIL held 13% (~30 fps repaint budget) | 0.0% |

    So the thread wins comfortably at the designed repaint budget and loses badly when the reactor never lets go. **Lowering `sys.setswitchinterval` does not rescue it** — at 100% duty it barely moved (30.3% at 0.5 ms) and at 13% duty it made things WORSE (0.0% → 2.3%), because more GIL handoffs is more churn.
  - **BEWARE when measuring this**: `time.sleep()` RELEASES the GIL, so any harness that models "the reactor is busy" with a sleep measures a reader thread running freely and reports ~0% loss no matter how starved it would really be. That mistake is what let a 77% → 0.6% figure ship for a fix that still leaked in the wild. Model the busy main thread with real CPU work.
  - **The parse is bounded so the reactor keeps letting go** (`PARSE_MAX_BYTES`, `_drain_parse_carry`). This is what actually keeps the duty cycle in the safe region. `drain()` hands over up to 256 KB and pyte costs ~2.5 ms per 4 KB of coloured output, so an unbounded `_feed_child_output` held the GIL for **~107 ms** — three times the repaint budget `RENDER_MIN_INTERVAL` is so careful about — and the tty's ~1 KB queue (about 85 wheel reports) overflowed and discarded INSIDE a single feed. Output past the bound is carried, in order, to the next pass; `_select_timeout` returns 0 while any is owed, so the screen never lags the backend. Splitting between feeds is safe because pyte's parser keeps state across calls (verified: a sequence cut at any offset renders identically to one feed).
    - Consume the carry with an OFFSET, never `del buf[:n]` — that is O(remaining) and made a 400 KB backlog quadratic, pushing the worst pass to 46 ms, worse than the unbounded feed it replaced.
  - **The repaint was the other unbounded GIL hold, and the axis nobody had measured is COLOUR MODE.** Converting a cell's colour to SGR is a pure function of (colour, foreground, `color_mode`), but it was recomputed for every cell of every frame — 40×120 × 2 (fg+bg) = 9600 conversions per repaint. On a truecolor terminal that is just string formatting; on a 256- or 16-colour terminal every hex that is not an *exact* xterm-256 palette entry — which is every colour in a diff-coloured code block — fell through to `_nearest_256`, a 256-entry linear scan. 2.4 million inner iterations per frame. Measured with the real renderer over 4000 lines of scrollback:

    | content | truecolor | **256** | 16 |
    | --- | --- | --- | --- |
    | plain | 1.04 ms | 1.04 ms | 1.02 ms |
    | diff-coloured | 7.48 ms | **175.8 ms** | **190.0 ms** |

    `RENDER_MIN_INTERVAL` is 33 ms, so a 176 ms frame costs **5.3× the entire frame interval**: the throttle cannot help, the reactor renders back to back, and the GIL duty is ~100% — the exact row of the table above that loses 35% of the bytes. `_color_code`/`_hex_color_code` are now module-level `functools.lru_cache` functions (the distinct-colour count on a screen is tiny, ~13 for a diff), which makes the diff-coloured frame **1.67 ms — the same cost as plain text** and byte-for-byte identical output. Live, in a pty over a diff-coloured scrollback: `_render` 179 ms → 3.8 ms, and the reader thread's inter-read gap p50/p95/max went 6.3 / 14.8 / 30.9 ms → **1.0 / 1.0 / 7.3 ms**.
    - **This is why the user's trigger was "only over green/red code blocks", and why it only reproduced for them.** `detect_color_mode` returns `"256"` for **Apple Terminal** (it sets `TERM=xterm-256color` and no `COLORTERM`); iTerm2/ghostty set `COLORTERM=truecolor` and take the fast path. Any repaint benchmark that does not pin `color_mode` gets `ScreenRenderer`'s default — `"truecolor"` — and so measures the one mode where the bug does not exist. That is how an earlier round measured "3.75 ms, only 3.3× plain" for the very content that costs 176 ms on the reporter's machine. **When measuring the renderer, always sweep all three colour modes.**
    - Regression test: `test_render_frame_colour_conversion_is_bounded_by_distinct_colours` — it counts `_nearest_256` calls per frame rather than timing anything, so it is deterministic in CI: a repaint must convert each *distinct* colour once and a second repaint must convert none.
    - **The same argument applies one level up, to the whole cell.** `cell_sgr` is a pure function of the cell's STYLE, the canvas and the colour mode, and it runs once per cell of every frame — 9,552 times at 50×200. It was rebuilding the string each time (seven attribute probes, a list, two `color_code` hops through the runner's re-export, a join); cProfile put 4.2 of 5.1 s in `cell_sgr` and the `color_code` chain under it. It is now memoized on that style (`_cell_sgr`): **4.29 ms → 2.66 ms** for a coloured 50×200 frame, 3.98 → 2.65 ms plain. The glyph is deliberately NOT part of the key — it does not affect the SGR, and counted on a real captured codex screen (45×150) the difference is decisive: 6,750 cells, **217 distinct `Char`s, 13 distinct styles**. A key that dropped the canvas or the colour mode would paint a whole session in a stale colour, so `test_the_cell_sgr_cache_is_keyed_on_everything_that_changes_the_answer` pins both.
  - **Every per-chunk scan of backend output needs a cheap presence check in front of it.** `drain()` hands over up to 256 KB and heavy scroll output is megabytes per turn, so anything that scans the whole buffer pays for all of it on the reactor thread. `_answer_terminal_queries` always had such a guard; **`_sync_terminal_modes` did not** — it ran twelve mouse modes × two substring scans, plus three more modes × two, plus a regex: **thirty full passes over every chunk**, measured **4.46 ms per megabyte of output containing no escape sequence at all**. Everything it looks for is `ESC [` + one of `? > < =`, so one regex (`_TERMINAL_MODE_MARKER_RE`) decides it: **4.46 ms → 0.26 ms**. Use a regex with a leading literal rather than several `in` checks — four `in` checks cost 1.97 ms for the same buffer because each is its own full scan, while the regex memchrs for `ESC` once. Tests: `test_sync_terminal_modes_rejects_a_chunk_that_cannot_contain_a_mode`. Measured for the neighbours at the same 1.02 MB: `_answer_terminal_queries` 0.00 ms (guarded), `_forward_clipboard_osc` 0.26 ms, `_track_sync_update` 0.64 ms (two `rfind`s, already minimal — a guard would make the common case, output that DOES carry 2026 markers, cost three scans instead of two).
  - **The reactor's timers phase must stay O(1) in screen size.** Measured after the agent-theme service was removed: **0.003 ms per tick**, with no `_service_*` doing work proportional to the screen. The two that scale with SESSION count are bounded by design (`_service_commit_summaries` is three assignments per idle session; `_service_background_sessions` is throttled per session by `_background_poll_interval`), and `_debug_session_liveness` is both debug-gated and throttled to 5 s. Re-measure this number, not just the render path, whenever a service is added.
  - **A pty cannot reproduce the byte loss, so do not try.** Verified on macOS: the slave's input queue holds exactly 1022 bytes, and a *blocking* master write simply blocks until there is room (nothing is dropped) while a *non-blocking* one accepts exactly 1022 bytes and returns EAGAIN — short, mid-sequence, but again nothing is dropped. So a pty-driven harness delivers 100% of the bytes no matter how starved the reader is (measured: 0.0% loss at 11,600 wheel events/s *while* every frame cost 176 ms). Byte loss needs a real terminal emulator writing to the master and discarding what it cannot hand over. What a pty harness CAN measure honestly is the reader thread's inter-read gap under real render load — that is the quantity the 1022-byte queue divides into, so use it as the proxy.
  - **The debris filters below therefore remain the mechanism, not a backstop.** They cover what the thread still misses when the reactor holds the GIL through a burst.

- **A wheel flood cannot reach aGiTrack, so it was never the danger.** The tty's input queue is small — measured at ~590–1022 bytes on macOS — and `select`+`os.read(4096)` empties it every time, so ONE read can never hold more than ~50–85 wheel reports no matter how hard the trackpad is flicked. The earlier "one flick = 300 full frames / 1.55 MB" account is not physically reachable through a tty; the harness that "only delivered ~170 events per flick" was measuring that queue, not a harness limitation. Measured on the current code: a full render is **O(1) in scrollback depth** (~4.3 ms flat from 0 to 5000 lines of history) and the pyte model plateaus at ~120 MB per session, so neither repaint cost nor memory grows with session length. (Depth was the right answer for the wrong question: repaint cost scaled with *attribute density and colour mode* instead — see the colour-mode table above.)
- **What actually kills a session is what the tty DROPS, not what it delivers.** When the queue overflows — scrolling faster than aGiTrack drains stdin, which is exactly "scrolling extensively" — the tty discards the overflow, chopping a mouse report in half and losing its tail. `_hold_incomplete_tail` parks the orphan, the next read brings whole reports, `_SGR_MOUSE_RE` strips those, and the orphan is left over and forwarded: a **real Escape keypress** plus visible junk (`[<64;120;45`). Escape is destructive in both backends, and on Claude's native session picker it quits Claude — three backend exits inside 12 s and `_relaunch_backend_or_exit` stops relaunching and exits NORMALLY. That is the shape of "aGiTrack dies when scrolling extensively", and it explains the missing crash report: nothing ever raised, so there was nothing for `crash.py` to write.
  - `_strip_aborted_mouse_reports` (`_ABORTED_CSI_PREFIX_RE` / `_ABORTED_MOUSE_ESC_RE`) removes any truncated report — recognised by an ESC sitting where the report's own terminator belongs, which a complete report can never produce. It runs for EVERY backend (debris is not input a mouse-driving backend should see either) and is deliberately narrow enough that `ESC ESC`, `ESC [ A`, PageUp and bracketed paste all pass through untouched.
  - **The tty discards from the MIDDLE of the stream, not only at read boundaries**, so one read carries many headless report tails (`5;43;28M`, `;28M`, `8M`) interleaved with intact reports — 15 at once in one report. Holding a partial and resyncing a single orphan cannot cover that; `_strip_orphaned_report_tails` removes whole RUNS of them. Two guards keep it off real input: the read must contain at least one intact report (we only do this while demonstrably mid-burst), and the run must sit against a report. Judging fragments one at a time does NOT work — the first of a run has no report directly on either side, so it survives and takes the rest of the run with it.
  - **Validate arity, not just shape.** A fragment can end in a perfectly good `M` and still be junk: a held prefix joined to a headless tail gave `\x1b[<65;43;25;43;28M` — four parameters — which every "body followed by a non-body byte" rule accepts. Anything introduced by `ESC [ <` is kept only if it `fullmatch`es a whole report.
  - **Both halves of a split report have to be handled, not just the one we hold.** When the remainder does not arrive within the hold, the front half is dropped — correctly, since it may never come — and then the BACK half turns up as its own read *containing no ESC at all*, which nothing keyed on ESC can see. It reached the user's input box as literal text (`<65;80;26M`). `_arm_mouse_resync` / `_consume_mouse_resync` remember the prefix we gave up on and consume the bytes that complete it on the very next read, then disarm. The check is exact rather than heuristic — the two halves must add up to a whole, well-formed report — which is what stops it eating real input: a typed `m` is only consumed if the prefix was already `ESC [ < 65;80;26`, precisely where that `m` IS the terminator. Bracketed-paste markers resync the same way (fixed strings, so the suffix is exact). The X10 form deliberately does NOT: its remainder is 1-3 raw bytes indistinguishable from typing, and its leak carries no ESC, so leaking a couple of stray characters beats eating keystrokes.
  - **The join is validated as well as the split.** The mirror image of the above: the remainder never comes but the user TYPES inside the hold window, so prefix and keystrokes are joined and forwarded together (`\x1b[<65;80hello`) — the `[<35;124;48`-fragment shape again. `_ABORTED_SGR_BODY_RE` drops a mouse-report prefix followed by a byte that cannot continue it (a body is digits and `;` until its `M`/`m`). Valid join → join; invalid join → drop the prefix, keep the typing. Only the `<` form is decidable this way: `ESC [ A` is an arrow key and `\x1b[200h` is a legitimate sequence shape, so the bare `ESC [` arm is deliberately left alone.
  - Why not simply hold a mouse prefix longer instead of dropping it? Because we can never know the remainder is coming — the tty may have discarded it — and a prefix held across the gap gets glued to whatever the user types next, which is the original `[<35;124;48`-in-a-commit-trace bug. Dropping has to stay allowed; the resync is what makes dropping safe.
  - `_hold_incomplete_tail` also holds a **lone trailing ESC** now: one read in twelve ends exactly on a report's ESC, and forwarding it did the same damage. `INPUT_TAIL_HOLD` (50 ms, the classic ESC-disambiguation timeout) releases it if nothing follows, so the Escape KEY still works — `_select_timeout` returns the remaining hold and `_reactor_stdin_phase` flushes it on an empty read. A partial CSI that never completes is DROPPED at that point rather than glued to the user's next keystroke (which is how `[<35;124;48` fragments once reached commit traces).
- **Forwarding input to a backend must never block** (`BackendProcess.write` + `flush_input`, flushed each timers pass). A PTY's input queue is ~1 KB and the reactor is single-threaded, so a blocking `os.write` to a child that is behind stops aGiTrack draining that child's OUTPUT — the child then fills its own output queue and blocks in `write` too, and neither side moves again. That is a permanent wedge: screen frozen on the last frame, no crash report, only a kill gets out of it. It is reachable whenever the BACKEND owns the mouse (`child_mouse` — OpenCode enables mouse reporting, so every wheel event is forwarded to it): **255 forwarded wheel events were enough**, with the reactor's whole stack in `os_write`. The master fd is therefore non-blocking (`_ensure_nonblocking`) and anything the child will not take is queued (capped at `MAX_PENDING_INPUT`, newest kept) for the reactor to retry. `select` saying the master is writable is NOT enough on its own — it means *some* room, and the next chunk can still block.
  - Consequence for `drain()`: on a non-blocking fd "nothing to read yet" raises `BlockingIOError`, which must NOT be reported as `None`. `None` is the reactor's signal that the backend is GONE, so returning it for an empty read would fake a backend exit; `drain` returns `b""` for that and `None` only on genuine EOF/error.
- **Scrollback repaints are coalesced and throttled, like output repaints.** `_intercept_scroll` sums every wheel/PageUp/PageDown event in the chunk and moves the view ONCE (`_mouse_scroll_delta` returns a per-event delta instead of scrolling), and `ScreenRenderer.scroll(..., min_interval=RENDER_MIN_INTERVAL)` then paints at most one frame per frame budget, flagging `_render_pending` (+ `_wake_main_loop`) when it skips one so the last event of a flick still lands. Worth keeping — it bounds repaint cost — but it is not what the "dies when scrolling" reports were about.
- **A frame is written whole** (`renderer.write_frame`): `os.write` to a tty may write SHORT, and half a frame is a cut escape sequence, which is how a repaint storm ends in a terminal state the user cannot get out of. A terminal that has gone away (EPIPE/EIO) drops the frame instead of raising out of the middle of a redraw.

## Diagnostics & Debugging (DEBUG_PROXY / DEBUG_RAW)

aGiTrack ships two always-present, opt-in diagnostic switches for debugging the proxy reactor — input/output, terminal-mode mirroring, session switches, hangs, and leaks. They are **off by default**, gated so they cost nothing in normal use, and behave **identically on Windows and macOS/Linux** (same env vars, same log files, same format) — so a bug report from either platform produces the same artifacts. Keep them; they are the first thing to reach for when an interactive glitch is reported.

- **`DEBUG_PROXY`** — human-readable event log. Records the stdin parse pipeline (each chunk: raw bytes → after menu-key intercept → after kitty decode → feed result with `forwarded`/`command`/`capturing`), backend spawn/switch/restart decisions, session lifecycle, agent-parse worker start/finish, shutdown, and a throttled (~5 s) **idle heartbeat** showing the loop is alive when no keystroke arrives. `agitrack --verbose` implies it.
- **`DEBUG_RAW`** — byte-exact I/O capture for replaying an interactive glitch (mouse/keyboard escape sequences, a backend's native picker). **Implies `DEBUG_PROXY`.** Every record is `HH:MM:SS.mmm <TAG> b'<repr>'`, flushed line-by-line (open+write+close per line) so the log survives a hard kill when a leak has broken Ctrl-C / graceful exit. Tags: `>` host→backend input (includes bytes read inside popups/modals), `<` backend→host output, `M` a terminal-mode sequence mirrored to the host console (mouse/kitty/paste — `_sync_terminal_modes`), `EOF` the backend's pty/ConPTY closed.

**Setting them.** Each switch is read under THREE names (first found wins): the bare name (`DEBUG_RAW`), the project-prefixed `AGITRACK_DEBUG_RAW`, and the legacy `AGIT_DEBUG_RAW` (see `agitrack/env.py` + `ProxyRunner._debug_flag`). Truthy values are `1` / `true` / `yes` (case-insensitive). The bare form exists because these are throwaway switches a user sets ad hoc in a shell — reaching for `DEBUG_RAW` is the obvious move, and a prefixed-only flag silently produced no log.
  - macOS/Linux (bash/zsh): `DEBUG_RAW=1 agitrack` (one run) or `export DEBUG_RAW=1` (the shell session).
  - Windows (PowerShell): `$env:DEBUG_RAW = "1"; agitrack` — set it in the **same** terminal that launches aGiTrack (the VS Code extension launches a child shell, so set it in that integrated terminal or in the OS environment).

**Where the logs go.** One file per run, in the **base** repo's `.agitrack/` (never the session worktree's — the worktree is removed on exit, which would destroy the log): `<base-repo>/.agitrack/proxy-debug-<YYYYMMDD-HHMMSS>.log` and `proxy-raw-<YYYYMMDD-HHMMSS>.log` (`_diag_path`; the `<YYYYMMDD-HHMMSS>` run-stamp is shared by both files of a run). To inspect the latest run, sort that directory by name/mtime and read the newest `proxy-*` pair; share both when filing a report.

**Cross-platform parity / the one platform-specific detail.** The flags, both log files, and every record format are the same on all platforms. The only platform difference is *inside* the idle-heartbeat line: on Windows it appends the console→bridge **reader-thread** stats (`reader[alive=… reads=… empties=…]`, from `NtHostTerminal.stdin_reader_stats`) — diagnostic for the Windows-only blocking-`ReadFile` reader; on macOS/Linux there is no bridge thread (the reactor `select`s the tty fd directly), so the same line shows `reader[n/a]`. Everything else is identical.

## Applying Code Changes to a Running aGiTrack

- **A code fix on disk does not take effect until the running aGiTrack process is restarted.** Python loads modules into memory at process start, so a long-lived proxy keeps executing the code it started with even after the source file changes. This is the usual reason a just-merged fix "still doesn't work": the file is fixed; the live process is stale. The remedy is to **fully quit and relaunch aGiTrack** — not reinstall.
- The dev's `agitrack` command is typically a **pipx editable install**: `~/.local/bin/agitrack` → pipx venv whose `__editable__.agitrack-*.pth` maps the `agitrack` package to the base-repo working tree (`/Users/s.wang9/Code/agitrack/agitrack`). So a fix that aGiTrack auto-merges into the checked-out base branch is immediately on disk for the installed command — no reinstall needed, just a restart. (Editable/source-linked vs package installs are also what the Self-Update section keys off.)
- Confirm the base repo's checked-out branch before assuming a fix is live: aGiTrack auto-merges into whatever branch the base repo is on (often `dev`), and `main`/release tags can lag well behind. If the base repo is checked out to a branch without the fix, the editable install loads unfixed code. The pipx-recorded version number can also be stale relative to `agitrack --version`.
